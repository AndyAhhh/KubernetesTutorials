# 第 14 章：资源限制——CPU 和 Memory

前面我们学习了 Pod、Deployment、StatefulSet、Service、Ingress，以及 ConfigMap、Secret、PVC。

到这里开始进入 Kubernetes 生产环境中非常关键的一部分：

> **资源管理与调度。**

一个 Kubernetes 集群本质上是在管理有限的计算资源：

```
Cluster
├── Node A
│   ├── CPU
│   └── Memory
│
├── Node B
│   ├── CPU
│   └── Memory
│
└── Node C
    ├── CPU
    └── Memory
```

而 Pod 会不断申请这些资源：

```
Pod A → CPU / Memory
Pod B → CPU / Memory
Pod C → CPU / Memory
```

如果 Kubernetes 不知道一个 Pod 需要多少 CPU、多少内存，就很难合理地进行调度。

因此本章要解决四个核心问题：

```
Pod 需要多少资源？
        ↓
Requests

Pod 最多允许使用多少资源？
        ↓
Limits

Pod 应该调度到哪个 Node？
        ↓
Scheduler

资源不够时怎么办？
        ↓
Pending / OOM / Throttling
```

------

## 14.1 Kubernetes Resource

### 14.1.1 什么是 Kubernetes Resource

在 Kubernetes 中，Pod/Container 最重要的计算资源主要是：

```
CPU
Memory
```

例如一个应用：

```
.NET API
```

可能需要：

```
CPU：500m
Memory：512Mi
```

另一个应用：

```
MySQL
```

可能需要：

```
CPU：2
Memory：4Gi
```

Kubernetes Scheduler 会根据这些资源需求决定：

> **这个 Pod 能不能放到某个 Node 上。**

------

### 14.1.2 Node 也有资源容量

例如：

```
Node A
CPU:    8 cores
Memory: 32Gi
```

如果已经运行：

```
Pod A
requests:
  cpu: 2
  memory: 4Gi

Pod B
requests:
  cpu: 1
  memory: 2Gi
```

那么 Kubernetes 会认为：

```
CPU 已申请：3 cores
Memory 已申请：6Gi
```

还有：

```
CPU：5 cores
Memory：26Gi
```

可用于调度其他 Pod。

注意：

> Scheduler 主要根据 **Requests** 做资源可调度性判断，而不是简单看当前实际 CPU 使用率。

这一点非常重要。

------

### 14.1.3 查看 Node 资源

```
kubectl get nodes
```

查看详细资源：

```
kubectl describe node <node-name>
```

重点关注：

```
Capacity
Allocatable
Requests
Limits
```

例如：

```
Capacity:
  cpu:                8
  memory:             32Gi

Allocatable:
  cpu:                7800m
  memory:             30Gi
```

为什么 Allocatable 通常小于 Capacity？

因为 Node 本身也需要资源：

```
kubelet
container runtime
system processes
Kubernetes system components
```

所以：

> **Pod 并不能使用 Node 的全部物理资源。**

------

### 14.1.4 查看实际资源使用情况

如果集群安装了 Metrics Server，可以：

```
kubectl top nodes
```

例如：

```
NAME       CPU(cores)   CPU%   MEMORY(bytes)   MEMORY%
node-1     1500m        19%    8Gi             25%
node-2     3000m        38%    20Gi            62%
```

查看 Pod：

```
kubectl top pods
```

查看某个 Namespace：

```
kubectl top pods -n production
```

需要注意：

```
kubectl top
```

反映的是**实际使用量**。

而：

```
requests / limits
```

描述的是 Kubernetes 的资源管理约束。

两者不是同一个概念。

------

## 14.2 CPU

### 14.2.1 Kubernetes 中 CPU 怎么表示

CPU 通常使用：

```
CPU core
```

或者：

```
millicore
```

表示。

例如：

```
1 CPU = 1000m
```

因此：

```
500m = 0.5 CPU
250m = 0.25 CPU
100m = 0.1 CPU
```

------

### 14.2.2 CPU 示例

```
resources:
  requests:
    cpu: "500m"

  limits:
    cpu: "1"
```

表示：

```
Requests = 0.5 CPU
Limits   = 1 CPU
```

------

### 14.2.3 CPU 是可压缩资源

CPU 有一个非常重要的特征：

> **CPU 是 Compressible Resource（可压缩资源）。**

什么意思？

假设 Node 上：

```
CPU = 4 cores
```

同时有多个 Pod：

```
Pod A
Pod B
Pod C
```

如果 CPU 不够，Linux 可以进行 CPU 调度，让不同进程共享 CPU 时间。

因此 CPU 超过 Request：

```
requests.cpu = 500m
实际使用 = 800m
```

并不意味着 Pod 立即被杀掉。

如果 Node 有空闲 CPU：

```
Pod
 ↓
继续使用
```

但如果 CPU 竞争激烈，Container 可能受到 CPU 限制。

这就涉及：

> **CPU Throttling。**

后面会详细解释。

------

### 14.2.4 CPU 的常见误区

很多初学者会认为：

```
requests:
  cpu: "500m"
```

就意味着：

> “这个 Pod 永远只能使用 500m CPU。”

这是错误的。

它主要表示：

> **调度时，我希望至少为这个 Pod 预留 500m CPU 的资源额度。**

如果没有设置 CPU Limit，实际使用可以超过 500m，只要 Node 上有资源。

------

## 14.3 Memory

### 14.3.1 Memory 怎么表示

Memory 常见单位：

```
Mi
Gi
```

例如：

```
128Mi
256Mi
512Mi
1Gi
2Gi
4Gi
```

生产环境推荐使用：

```
Mi
Gi
```

而不是依赖模糊的：

```
M
G
```

------

### 14.3.2 Mi 和 Gi

Kubernetes 使用的是二进制单位。

例如：

```
1Gi = 1024Mi
2Gi = 2048Mi
512Mi ≈ 0.5Gi
```

------

### 14.3.3 Memory 示例

```
resources:
  requests:
    memory: "512Mi"

  limits:
    memory: "1Gi"
```

表示：

```
请求资源：512Mi
最大限制：1Gi
```

------

### 14.3.4 Memory 是不可压缩资源

Memory 与 CPU 有一个非常重要的区别：

> **Memory 是不可压缩资源（Non-compressible Resource）。**

CPU 不够：

```
降低 CPU 时间
```

还可以继续运行。

但是 Memory 不够：

```
Node 没有足够内存
```

不能简单地说：

```
“让这个 Pod 慢一点就行。”
```

因此 Linux/Kubernetes 最终可能触发：

```
OOM
```

即：

> Out Of Memory

Container 可能被杀掉。

------

## 14.4 Requests

### 14.4.1 Requests 是什么

Requests 表示：

> **Container 希望 Kubernetes 为它预留/保证的资源量。**

例如：

```
resources:
  requests:
    cpu: "500m"
    memory: "512Mi"
```

表示：

```
CPU Request    = 500m
Memory Request = 512Mi
```

------

### 14.4.2 Requests 最大作用：调度

假设 Node：

```
Allocatable CPU = 4
```

已经存在：

```
Pod A
requests.cpu = 2

Pod B
requests.cpu = 1
```

那么 Kubernetes 会认为：

```
已分配 = 3 CPU
剩余 = 1 CPU
```

此时：

```
Pod C
requests.cpu = 2
```

即使 Node 当前：

```
实际 CPU 使用率 = 20%
```

Pod C 也可能无法调度。

因为 Scheduler 看的是：

```
Requests
```

而不是简单看：

```
当前 CPU 使用率
```

------

### 14.4.3 为什么这样设计

因为实际 CPU 使用是动态变化的：

```
10%
20%
80%
30%
95%
```

如果 Scheduler 只根据当前使用率调度，很容易发生：

```
现在有资源
 ↓
同时调度很多 Pod
 ↓
突然所有 Pod 负载升高
 ↓
Node 资源不足
```

Requests 相当于告诉 Kubernetes：

> “这个 Pod 的资源预算是多少。”

这样 Scheduler 才能进行相对稳定的资源规划。

------

### 14.4.4 Requests 示例

```
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api
spec:
  replicas: 2

  selector:
    matchLabels:
      app: api

  template:
    metadata:
      labels:
        app: api

    spec:
      containers:
        - name: api
          image: nginx:1.27

          resources:
            requests:
              cpu: "500m"
              memory: "512Mi"
```

两个 Pod：

```
2 × 500m = 1000m CPU
```

因此 Scheduler 需要找到：

```
至少有 1 CPU 可供 Request 的节点资源空间
```

------

## 14.5 Limits

### 14.5.1 Limits 是什么

Limits 表示：

> **Container 允许使用的资源上限。**

例如：

```
resources:
  requests:
    cpu: "500m"
    memory: "512Mi"

  limits:
    cpu: "1"
    memory: "1Gi"
```

表示：

```
Request：
CPU    500m
Memory 512Mi

Limit：
CPU    1
Memory 1Gi
```

------

### 14.5.2 CPU Limit

CPU 超过 Limit 时：

```
实际 CPU 使用
      ↓
超过 limit
      ↓
CFS quota
      ↓
CPU Throttling
```

通常不会直接杀死 Container。

例如：

```
CPU Limit = 1 CPU
```

应用想使用：

```
2 CPU
```

Linux cgroup 会限制它。

最终表现为：

```
CPU Throttling
```

------

### 14.5.3 Memory Limit

Memory Limit 的行为不同。

例如：

```
limits:
  memory: "1Gi"
```

如果 Container 内存持续超过这个限制，可能触发：

```
OOMKilled
```

例如：

```
Container
   ↓
Memory usage
   ↓
> 1Gi
   ↓
OOM
   ↓
Container killed
```

------

### 14.5.4 Requests 和 Limits 的关系

可以理解成：

```
Requests
    ↓
“调度时我需要多少”

Limits
    ↓
“运行时最多允许多少”
```

例如：

```
resources:
  requests:
    cpu: "500m"
    memory: "512Mi"

  limits:
    cpu: "2"
    memory: "1Gi"
```

意思：

```
调度：
需要 500m CPU / 512Mi Memory

运行：
最多 2 CPU / 1Gi Memory
```

------

## 14.6 QoS Class

Kubernetes 会根据：

```
requests
limits
```

给 Pod 分配 QoS Class。

主要有三个：

```
Guaranteed
Burstable
BestEffort
```

它们非常重要，因为 Node 资源不足时，Kubernetes 需要决定：

> **到底优先牺牲哪些 Pod？**

------

## 14.7 Guaranteed

### 14.7.1 什么是 Guaranteed

如果 Pod 中的每个 Container 都满足：

```
CPU request == CPU limit
Memory request == Memory limit
```

那么 Pod 可以获得：

```
Guaranteed
```

例如：

```
resources:
  requests:
    cpu: "1"
    memory: "1Gi"

  limits:
    cpu: "1"
    memory: "1Gi"
```

------

### 14.7.2 完整示例

```
apiVersion: v1
kind: Pod
metadata:
  name: guaranteed-demo
spec:
  containers:
    - name: app
      image: nginx:1.27

      resources:
        requests:
          cpu: "1"
          memory: "1Gi"

        limits:
          cpu: "1"
          memory: "1Gi"
```

这个 Pod：

```
QoS = Guaranteed
```

------

### 14.7.3 Guaranteed 的特点

一般来说，在资源压力下：

```
Guaranteed
```

相对更受保护。

适合：

```
核心数据库
关键业务
重要基础设施组件
```

但不能理解为：

> Guaranteed Pod 永远不会被杀。

如果：

```
Node 整体发生严重内存压力
```

仍然可能出现各种资源压力处理。

所以：

> QoS 是 Kubernetes 的资源管理和驱逐优先级机制之一，不是绝对的“永不被杀”。

------

## 14.8 Burstable

### 14.8.1 什么是 Burstable

如果 Pod 设置了部分或全部资源 Request/Limit，但不满足 Guaranteed 的严格条件，通常属于：

```
Burstable
```

例如：

```
resources:
  requests:
    cpu: "500m"
    memory: "512Mi"

  limits:
    cpu: "2"
    memory: "1Gi"
```

因为：

```
Request != Limit
```

所以：

```
QoS = Burstable
```

------

### 14.8.2 为什么叫 Burstable

因为它允许：

```
正常需求
500m CPU
```

在资源充足时：

```
可以 Burst
↑
使用更多 CPU
```

例如：

```
Request = 500m
Limit = 2 CPU
```

应用平时：

```
300m
```

高峰：

```
1.5 CPU
```

如果 Node 有足够资源，它可以在 Limit 范围内使用更多 CPU。

------

### 14.8.3 生产环境中非常常见

大量普通业务服务：

```
.NET API
Java Spring
Node.js
Nginx
Go Service
```

都可能采用：

```
Burstable
```

例如：

```
resources:
  requests:
    cpu: "200m"
    memory: "256Mi"

  limits:
    cpu: "1"
    memory: "512Mi"
```

这通常比所有应用都设置成 Guaranteed 更灵活。

------

## 14.9 BestEffort

### 14.9.1 什么是 BestEffort

如果 Pod 中没有 Container 设置：

```
CPU requests
CPU limits
Memory requests
Memory limits
```

则 Pod 通常属于：

```
BestEffort
```

例如：

```
apiVersion: v1
kind: Pod
metadata:
  name: besteffort-demo
spec:
  containers:
    - name: app
      image: nginx:1.27
```

这里没有：

```
resources:
```

所以：

```
QoS = BestEffort
```

------

### 14.9.2 BestEffort 的风险

当 Node 资源压力较大时：

```
BestEffort
```

通常属于优先被驱逐的一类。

因此生产环境不建议关键业务完全不设置资源。

------

### 14.9.3 三种 QoS

可以记成：

```
Guaranteed
    ↑
资源约束最严格

Burstable
    ↑
有 Request/Limit，但不完全相等

BestEffort
    ↑
完全没有资源声明
```

一个非常重要的生产认知：

> **QoS 不是性能等级，而是 Kubernetes 在资源压力下进行管理和驱逐时使用的重要分类。**

------

## 14.10 OOMKilled

### 14.10.1 什么是 OOMKilled

OOM：

> Out Of Memory

当 Container 因内存不足被 Linux OOM Killer 杀死后，Kubernetes 经常会显示：

```
OOMKilled
```

例如：

```
kubectl get pod
```

可能看到：

```
NAME    READY   STATUS
api     0/1     OOMKilled
```

或者：

```
CrashLoopBackOff
```

同时 Container 的 Last State 中存在：

```
Reason: OOMKilled
```

------

### 14.10.2 查看 OOMKilled

```
kubectl describe pod <pod-name>
```

也可以：

```
kubectl get pod <pod-name> -o yaml
```

查看：

```
lastState:
  terminated:
    reason: OOMKilled
```

------

### 14.10.3 为什么会 OOMKilled

常见原因：

```
应用真实内存需求超过 limit
内存泄漏
缓存不断增长
大量请求并发
JVM/.NET/Node 内存配置不合理
内存瞬时峰值
Node 整体内存压力
```

例如：

```
limits:
  memory: "256Mi"
```

但应用高峰实际需要：

```
400Mi
```

可能发生：

```
256Mi
 ↓
超过 Limit
 ↓
OOM
 ↓
Container 被杀
```

------

### 14.10.4 OOMKilled 不一定等于应用内存泄漏

这是生产排障非常重要的一点。

看到：

```
OOMKilled
```

不要立即得出：

> “应用有内存泄漏。”

可能只是：

```
Limit 设置太小
```

例如应用正常运行：

```
350Mi
```

但 Limit：

```
256Mi
```

那么应用并没有泄漏。

只是资源配置不合理。

------

### 14.10.5 如何排查

先看：

```
kubectl describe pod <pod-name>
```

再看实际使用：

```
kubectl top pod <pod-name>
```

然后查看：

```
requests
limits
```

以及应用自身的：

```
GC
Heap
Cache
线程
连接池
请求并发
```

对于 .NET、Java、Node.js 等运行时，应该结合应用自身的内存指标进行分析。

------

## 14.11 CPU Throttling

### 14.11.1 什么是 CPU Throttling

当 Container 设置：

```
CPU Limit
```

Linux cgroup 会对 CPU 使用进行限制。

例如：

```
limits:
  cpu: "1"
```

应用突然需要：

```
2 CPU
```

系统不会让它无限使用，而是进行：

```
CPU Throttling
```

简单理解：

```
应用想跑
   ↓
超过 CPU Limit
   ↓
被限制运行时间
   ↓
请求处理变慢
```

------

### 14.11.2 CPU Throttling 与 OOM 的区别

非常重要：

```
CPU 超限
   ↓
Throttling
```

而：

```
Memory 超限
   ↓
OOMKilled
```

也就是说：

| 资源   | 超过 Limit 的典型行为 |
| ------ | --------------------- |
| CPU    | Throttling            |
| Memory | OOMKilled             |

------

### 14.11.3 CPU Throttling 的生产影响

例如：

```
API Pod
CPU limit = 500m
```

平时：

```
100m
```

高峰：

```
800m
```

那么 CPU Limit 可能导致：

```
CPU Throttling
 ↓
请求处理时间增加
 ↓
P99 延迟上升
 ↓
超时
```

尤其是：

```
低延迟 API
高并发服务
Java/.NET 服务
```

需要特别关注。

------

### 14.11.4 为什么 CPU Limit 需要谨慎

生产环境中经常会遇到一种情况：

```
requests.cpu = 500m
limits.cpu = 500m
```

应用正常：

```
200m
```

高峰：

```
800m
```

但是因为：

```
limit = 500m
```

它无法快速 Burst。

可能造成：

```
CPU throttling
```

因此：

> **CPU Limit 并不是越严格越好。**

具体策略应该根据应用负载、集群容量和稳定性目标决定。

------

## 14.12 Pod 为什么调度不上去

这是 Kubernetes 初学者非常容易遇到的问题：

```
Pod
STATUS = Pending
```

例如：

```
kubectl get pod
```

看到：

```
api-xxx   0/1   Pending
```

------

### 14.12.1 第一反应应该是什么

不要直接删除 Pod。

首先：

```
kubectl describe pod <pod-name>
```

看：

```
Events
```

------

### 14.12.2 典型错误

例如：

```
0/3 nodes are available:
3 Insufficient cpu.
```

意思：

> 3 个 Node 都没有足够的 CPU Request 空间。

例如：

```
Pod:
requests.cpu = 4
```

但是每个 Node：

```
剩余可调度 CPU < 4
```

所以：

```
Pending
```

------

### 14.12.3 Memory 不够

可能看到：

```
0/3 nodes are available:
3 Insufficient memory.
```

例如 Pod：

```
requests:
  memory: "8Gi"
```

但是：

```
Node A 可分配空间：2Gi
Node B 可分配空间：4Gi
Node C 可分配空间：6Gi
```

没有任何一个 Node 满足：

```
8Gi
```

因此 Pod 无法调度。

------

### 14.12.4 一个非常容易误解的情况

假设：

```
Node Memory = 16Gi
```

实际使用：

```
8Gi
```

看起来还有：

```
8Gi
```

但是 Pod：

```
requests.memory = 10Gi
```

仍然可能无法调度。

因为 Scheduler 主要考虑：

```
Allocatable
-
已有 Requests
```

而不是：

```
Allocatable
-
当前实际使用
```

所以：

> **“Node 还有很多空闲内存”不等于“Pod 一定能够调度进去”。**

------

### 14.12.5 其他调度失败原因

资源只是其中一种原因。

还可能是：

```
nodeSelector
nodeAffinity
taint / toleration
topology constraints
PVC topology
Pod anti-affinity
```

所以排查 Pending Pod 时：

```
kubectl describe pod <pod-name>
```

是非常重要的第一步。

------

## 14.13 如何合理设置 Requests / Limits

这是生产环境最需要经验的部分。

不能简单规定：

```
所有 Pod：
CPU = 1
Memory = 1Gi
```

因为不同应用完全不同。

------

### 14.13.1 不要拍脑袋设置

例如：

```
requests:
  cpu: "1"
  memory: "2Gi"
```

如果真实应用只需要：

```
CPU：100m
Memory：200Mi
```

那么会产生：

```
资源浪费
```

Scheduler 会认为：

```
Pod 需要 1 CPU + 2Gi
```

导致：

```
Node 可调度 Pod 数量下降
集群利用率下降
扩容成本增加
```

------

### 14.13.2 设置过小也有问题

例如：

```
requests:
  memory: "128Mi"

limits:
  memory: "256Mi"
```

但实际应用：

```
正常：300Mi
高峰：500Mi
```

那么就可能：

```
OOMKilled
```

因此：

> Request 太大浪费资源，太小会导致调度和容量规划失真；Limit 太小可能导致应用被限制或 OOM。

------

### 14.13.3 推荐通过实际数据确定

生产环境应该观察：

```
CPU usage
Memory usage
CPU P95/P99
Memory P95/P99
业务高峰
启动阶段
批处理阶段
GC 行为
```

例如经过一段时间观察：

```
CPU：
P50 = 100m
P95 = 300m
P99 = 500m

Memory：
P50 = 300Mi
P95 = 450Mi
P99 = 550Mi
```

可以考虑：

```
requests:
  cpu: "300m"
  memory: "512Mi"

limits:
  cpu: "1"
  memory: "768Mi"
```

这只是示例，实际数值必须根据应用测试和生产监控确定。

------

### 14.13.4 Requests 应该关注稳定运行需求

可以粗略理解：

```
Request
≈
正常/稳定运行所需要的资源
```

而不是：

```
历史最高瞬间值
```

否则：

```
Request 过高
 ↓
调度效率下降
```

------

### 14.13.5 Memory Request 要特别谨慎

Memory 与 CPU 不一样。

假设：

```
应用通常使用 500Mi
偶尔使用 1Gi
```

如果：

```
request = 500Mi
limit = 1Gi
```

可以允许一定 Burst。

但如果应用经常：

```
900Mi
1Gi
1.2Gi
```

那么：

```
limit = 1Gi
```

很可能过小。

所以 Memory Limit 应该结合：

```
真实峰值
运行时行为
GC
缓存
并发
```

来确定。

------

### 14.13.6 CPU Limit 不要机械设置

这是生产环境非常重要的经验。

很多团队以前习惯：

```
requests:
  cpu: "500m"

limits:
  cpu: "500m"
```

这种配置非常严格。

如果应用存在明显突发 CPU 需求：

```
500m
 ↓
800m
 ↓
1 CPU
```

就可能受到 CPU Throttling。

因此是否设置 CPU Limit，需要结合：

```
集群资源隔离需求
应用类型
CPU Burst
延迟要求
多租户场景
```

进行设计。

------

## 14.14 生产环境资源管理策略

到了生产环境，资源管理不能只是：

```
resources:
```

这么简单。

应该形成完整的资源治理体系。

------

### 14.14.1 所有生产业务尽量设置 Requests

生产环境建议避免核心业务完全没有：

```
requests
```

例如：

```
resources:
  requests:
    cpu: "200m"
    memory: "256Mi"
```

这样 Scheduler 才能正确进行资源规划。

------

### 14.14.2 LimitRange

Namespace 可以通过：

```
LimitRange
```

设置默认资源或者限制资源范围。

例如：

```
apiVersion: v1
kind: LimitRange
metadata:
  name: default-resources
  namespace: production
spec:
  limits:
    - type: Container
      defaultRequest:
        cpu: "200m"
        memory: "256Mi"
      default:
        cpu: "1"
        memory: "512Mi"
```

这样 Namespace 中没有显式设置资源的 Container，可以获得默认值。

查看：

```
kubectl get limitrange -n production
```

------

### 14.14.3 ResourceQuota

ResourceQuota 用于限制 Namespace 总资源。

例如：

```
apiVersion: v1
kind: ResourceQuota
metadata:
  name: production-quota
  namespace: production
spec:
  hard:
    requests.cpu: "20"
    requests.memory: "40Gi"
    limits.cpu: "40"
    limits.memory: "80Gi"
```

意思可以理解为：

```
production Namespace
最多申请：
CPU Requests = 20
Memory Requests = 40Gi

最多 Limit：
CPU = 40
Memory = 80Gi
```

查看：

```
kubectl get resourcequota -n production
```

------

### 14.14.4 为什么需要 ResourceQuota

假设一个 Namespace：

```
team-a
```

突然部署：

```
100 个 Pod
```

每个：

```
requests:
  cpu: 2
  memory: 4Gi
```

可能直接：

```
CPU = 200 cores
Memory = 400Gi
```

如果集群没有足够的资源治理机制，一个团队就可能消耗大量集群容量。

因此生产环境通常会使用：

```
ResourceQuota
LimitRange
```

配合：

```
Requests / Limits
```

进行多租户资源治理。

------

### 14.14.5 资源监控

生产环境不能只配置资源，还必须监控。

至少应该关注：

```
CPU Usage
Memory Usage
CPU Requests
Memory Requests
CPU Limits
Memory Limits
CPU Throttling
OOMKilled
Pod Pending
Node Memory Pressure
Node CPU Saturation
```

应用层还应该结合：

```
QPS
Latency
P95/P99
Error Rate
GC
线程池
连接池
```

否则你只看到：

```
CPU = 80%
```

却不知道：

```
为什么 80%
```

以及：

```
是否影响业务
```

------

### 14.14.6 资源配置应该和 HPA 配合

生产环境常见架构：

```
             HPA
              │
              ▼
        Deployment
              │
        ┌─────┼─────┐
        ▼     ▼     ▼
      Pod   Pod    Pod
       │      │      │
       └── Requests ─┘
```

HPA 可以根据：

```
CPU
Memory
Custom Metrics
```

决定：

```
增加 Pod
减少 Pod
```

因此 Requests 设置是否合理，也会影响自动扩缩容的效果。

例如：

```
requests.cpu = 1 CPU
实际使用 = 500m
```

那么 CPU 利用率约：

```
50%
```

如果：

```
requests.cpu = 250m
实际使用 = 500m
```

则：

```
200%
```

同一个应用，只因为 Request 不同，HPA 看到的 CPU 利用率就可能完全不同。

所以：

> **Requests 不只是 Scheduler 使用，HPA 等机制也可能依赖它来判断资源利用率。**

------

### 14.14.7 生产环境不要追求“所有 Pod 都 Guaranteed”

Guaranteed 看起来很安全，但并不是：

```
Guaranteed = 最佳
Burstable = 不好
BestEffort = 错误
```

实际生产环境往往是：

```
核心关键组件
    ↓
更严格的资源配置

普通业务
    ↓
Burstable

临时任务
    ↓
可以根据需要采用更宽松策略
```

关键是：

> **根据业务重要性、负载特征和资源成本进行设计。**

------

### 14.14.8 资源管理的完整思路

生产环境可以形成：

```
开发
 ↓
压测
 ↓
观察真实资源使用
 ↓
设置 Requests
 ↓
设置合理 Limits
 ↓
监控
 ↓
HPA
 ↓
持续调整
```

而不是：

```
写一个 YAML
 ↓
永远不修改
```

因为应用负载会变化：

```
用户增长
流量增长
代码变化
依赖变化
业务高峰
```

资源配置也应该持续优化。

------

### 14.14.9 一个比较完整的生产示例

例如一个普通 API：

```
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api
  namespace: production
spec:
  replicas: 3

  selector:
    matchLabels:
      app: api

  template:
    metadata:
      labels:
        app: api

    spec:
      containers:
        - name: api
          image: example/api:1.0.0

          resources:
            requests:
              cpu: "300m"
              memory: "512Mi"

            limits:
              cpu: "1"
              memory: "1Gi"

          ports:
            - containerPort: 8080
```

可以理解成：

```
每个 Pod：

正常资源预算：
CPU    300m
Memory 512Mi

最大资源：
CPU    1
Memory 1Gi
```

三个 Pod：

```
Requests：
CPU    900m
Memory 1536Mi

Limits：
CPU    3
Memory 3Gi
```

Scheduler 会主要依据：

```
900m CPU
1536Mi Memory
```

进行调度。

------

## 本章核心知识

本章最重要的是建立下面这张关系图：

```
                       Node
                        │
                ┌───────┴───────┐
                │               │
             CPU / Memory    Allocatable
                │
                ▼
               Pod
                │
          ┌─────┴─────┐
          ▼           ▼
      Requests      Limits
          │           │
          │           │
          ▼           ▼
      Scheduler    Runtime
          │           │
          │      ┌────┴─────┐
          │      │          │
          │      ▼          ▼
          │    CPU       Memory
          │      │          │
          │      ▼          ▼
          │ Throttling   OOMKilled
          │
          ▼
        QoS Class
          │
     ┌────┼────┐
     ▼    ▼    ▼
Guaranteed Burstable BestEffort
```

最关键的概念可以这样记：

| 概念           | 核心作用                      |
| -------------- | ----------------------------- |
| CPU            | 计算资源                      |
| Memory         | 内存资源                      |
| Requests       | 调度时需要的资源              |
| Limits         | 运行时允许的最大资源          |
| Guaranteed     | Request = Limit 的严格 QoS    |
| Burstable      | 有资源声明但不满足 Guaranteed |
| BestEffort     | 没有资源声明                  |
| OOMKilled      | 内存不足导致 Container 被杀   |
| CPU Throttling | CPU 超过限制后被限制运行      |
| Scheduler      | 根据资源等条件选择 Node       |

最后记住两个生产环境中极其重要的区别：

```
Requests
    ↓
主要回答：
“这个 Pod 能不能调度到这个 Node？”
```

而：

```
Limits
    ↓
主要回答：
“这个 Container 运行时最多允许使用多少资源？”
```

以及：

```
CPU 超限
    ↓
Throttle
Memory 超限
    ↓
OOMKilled
```

**真正的生产资源管理目标不是“把 Requests/Limits 填上去”，而是让 Kubernetes 知道每个应用真实需要多少资源，并通过监控、Quota、LimitRange、HPA 等机制持续控制整个集群的资源使用。**

# 第 15 章：Kubernetes 调度机制

上一章我们解决了一个核心问题：

> **Pod 需要多少 CPU 和 Memory？**

这一章解决另一个核心问题：

> **Pod 应该运行在哪一个 Node 上？**

假设集群有：

```
Cluster
│
├── node-01
│
├── node-02
│
├── node-03
│
└── node-04
```

当你执行：

```
kubectl apply -f deployment.yaml
```

Deployment 创建 Pod 后，并不会直接决定：

```
api-xxx → node-02
```

而是由 Kubernetes Scheduler 根据一系列规则选择合适的 Node。

整个过程可以简单理解为：

```
Pod 创建
   │
   ▼
Scheduler
   │
   ├── 哪些 Node 不符合条件？
   │
   ├── 哪些 Node 符合条件？
   │
   ├── 哪个 Node 更合适？
   │
   ▼
选择 Node
   │
   ▼
kubelet 创建 Pod
```

------

## 15.1 Scheduler

### 15.1.1 Scheduler 是什么

Kubernetes Scheduler 是 Kubernetes 控制平面中的调度组件。

它负责：

> **为尚未绑定 Node 的 Pod 选择合适的 Node。**

例如：

```
Pod
  ↓
Pending
  ↓
Scheduler
  ↓
node-02
```

Scheduler 最终会把 Pod 与某个 Node 建立绑定关系。

------

### 15.1.2 为什么需要 Scheduler

假设集群有：

```
Node A：CPU 8 / Memory 32Gi
Node B：CPU 8 / Memory 32Gi
Node C：CPU 8 / Memory 32Gi
```

现在有：

```
Pod A
requests:
  cpu: 2
  memory: 4Gi
```

Kubernetes 必须决定：

```
Pod A
  ↓
Node A / B / C？
```

如果完全随机：

```
Pod A → Node A
Pod B → Node A
Pod C → Node A
...
```

很容易出现：

```
Node A：过载
Node B：空闲
Node C：空闲
```

Scheduler 的作用就是根据各种约束和优先级，让 Pod 尽可能合理地分布。

------

### 15.1.3 Scheduler 考虑什么

Scheduler 并不是只考虑 CPU 和 Memory。

它可能综合考虑：

```
资源 Requests
Node Selector
Node Affinity
Pod Affinity
Pod Anti-Affinity
Taints / Tolerations
Topology Spread Constraints
Volume 拓扑
Node 状态
其他调度约束
```

因此：

> **Kubernetes 调度本质上是一个“约束 + 优选”的问题。**

------

### 15.1.4 调度的大致过程

可以简化为：

```
所有 Node
   │
   ▼
过滤不符合条件的 Node
   │
   ▼
剩余可用 Node
   │
   ▼
根据各种偏好进行评分
   │
   ▼
选择分数较高的 Node
```

例如：

```
Node A
CPU 不够
    ↓
淘汰

Node B
符合资源要求
    ↓
保留

Node C
符合资源要求
    ↓
保留

Node D
不满足 Node Affinity
    ↓
淘汰
```

最后：

```
Node B / Node C
       ↓
评分
       ↓
选择 Node C
```

这就是理解后面各种调度机制的基础。

------

## 15.2 Node Selector

### 15.2.1 Node Selector 是什么

`nodeSelector` 是 Kubernetes 最简单的 Node 调度约束方式。

它的意思是：

> **Pod 只能调度到具有指定 Label 的 Node。**

例如：

```
Node A
labels:
  disktype=ssd

Node B
labels:
  disktype=hdd
```

Pod：

```
spec:
  nodeSelector:
    disktype: ssd
```

那么：

```
Pod
 ↓
只能选择
 ↓
Node A
```

------

### 15.2.2 给 Node 添加 Label

例如：

```
kubectl label node node-01 disktype=ssd
```

查看：

```
kubectl get nodes --show-labels
```

也可以：

```
kubectl get node node-01 --show-labels
```

------

### 15.2.3 使用 Node Selector

完整示例：

```
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 2

  selector:
    matchLabels:
      app: web

  template:
    metadata:
      labels:
        app: web

    spec:
      nodeSelector:
        disktype: ssd

      containers:
        - name: web
          image: nginx:1.27
```

这样 Pod 只能运行在：

```
disktype=ssd
```

的 Node 上。

------

### 15.2.4 Node Selector 的优点

非常简单：

```
nodeSelector
```

适合明确的硬性要求。

例如：

```
GPU Node
SSD Node
特定硬件
特定 Node 类型
```

------

### 15.2.5 Node Selector 的局限

它只能表达比较简单的：

```
key = value
```

例如：

```
disktype=ssd
```

但是生产环境经常需要：

```
必须是 SSD
或者 NVMe

优先 SSD
但没有 SSD 时也可以使用其他节点

区域必须是 zone-a 或 zone-b
```

这时候：

> `nodeAffinity` 比 `nodeSelector` 更灵活。

------

## 15.3 Node Affinity

### 15.3.1 什么是 Node Affinity

Node Affinity 可以理解为：

> **更强大、更灵活的 Node Selector。**

它允许使用：

```
In
NotIn
Exists
DoesNotExist
Gt
Lt
```

等表达方式。

例如：

```
disktype In [ssd,nvme]
```

------

### 15.3.2 Required Node Affinity

`requiredDuringSchedulingIgnoredDuringExecution` 表示：

> **这是硬性条件。**

如果没有符合条件的 Node：

```
Pod
 ↓
无法调度
 ↓
Pending
```

例如：

```
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 2

  selector:
    matchLabels:
      app: web

  template:
    metadata:
      labels:
        app: web

    spec:
      affinity:
        nodeAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            nodeSelectorTerms:
              - matchExpressions:
                  - key: disktype
                    operator: In
                    values:
                      - ssd
                      - nvme

      containers:
        - name: web
          image: nginx:1.27
```

意思：

```
Node 必须满足：

disktype = ssd
或者
disktype = nvme
```

------

### 15.3.3 Preferred Node Affinity

还有：

```
preferredDuringSchedulingIgnoredDuringExecution
```

意思是：

> **这是偏好，不是绝对要求。**

例如：

```
affinity:
  nodeAffinity:
    preferredDuringSchedulingIgnoredDuringExecution:
      - weight: 100
        preference:
          matchExpressions:
            - key: disktype
              operator: In
              values:
                - ssd
```

意思：

```
优先选择 SSD Node
```

但是：

```
如果没有 SSD
↓
仍然可以选择其他符合条件的 Node
```

------

### 15.3.4 Required 与 Preferred

非常重要：

```
required
   ↓
必须满足
preferred
   ↓
尽量满足
```

可以类比：

```
required = 硬规则
preferred = 偏好
```

------

### 15.3.5 IgnoredDuringExecution 是什么意思

这个名字很长：

```
requiredDuringSchedulingIgnoredDuringExecution
```

拆开：

```
DuringScheduling
```

表示：

> **调度 Pod 时检查。**

```
IgnoredDuringExecution
```

表示：

> **Pod 已经运行后，如果 Node Label 后续发生变化，不会因为这个变化自动把 Pod 驱逐出去。**

这是一个很重要的概念。

------

## 15.4 Pod Affinity

### 15.4.1 Pod Affinity 是什么

前面的：

```
Node Affinity
```

是：

> Pod 与 Node 的关系。

而：

```
Pod Affinity
```

是：

> **Pod 与 Pod 之间的调度关系。**

例如：

```
API Pod
   ↓
希望和
   ↓
Cache Pod
   ↓
运行在相同 Node / Zone
```

为什么？

因为：

```
API → Cache
```

如果网络距离更近，可能降低网络延迟。

------

### 15.4.2 示例

假设已经存在：

```
cache Pod
labels:
  app=cache
```

现在 API：

```
affinity:
  podAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      - labelSelector:
          matchExpressions:
            - key: app
              operator: In
              values:
                - cache

        topologyKey: kubernetes.io/hostname
```

意思：

> API Pod 必须调度到存在 `app=cache` Pod 的同一个 Node。

------

### 15.4.3 topologyKey

这里出现了一个非常重要的概念：

```
topologyKey
```

它定义：

> **“相同位置”到底是什么意思。**

例如：

```
kubernetes.io/hostname
```

通常代表：

```
同一个 Node
```

如果：

```
topology.kubernetes.io/zone
```

则通常表示：

```
同一个 Availability Zone
```

因此：

```
topologyKey = hostname
```

可以理解为：

```
同 Node
```

而：

```
topologyKey = zone
```

可以理解为：

```
同 AZ
```

具体前提是这些 Node 上存在对应的标准 Label。

------

## 15.5 Pod Anti-Affinity

### 15.5.1 什么是 Pod Anti-Affinity

Pod Anti-Affinity 与 Pod Affinity 相反。

它表示：

> **希望某些 Pod 不要放在一起。**

这是生产环境非常重要的高可用机制。

例如：

```
api-1
api-2
api-3
```

如果全部运行在：

```
Node A
```

那么：

```
Node A
 ↓
故障
 ↓
三个 API Pod 全部消失
```

所以可以设置：

```
API Pod
不要和
其他 API Pod
运行在同一个 Node
```

------

### 15.5.2 Required Anti-Affinity

例如：

```
affinity:
  podAntiAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      - labelSelector:
          matchExpressions:
            - key: app
              operator: In
              values:
                - api

        topologyKey: kubernetes.io/hostname
```

意思：

```
app=api
的 Pod
不能出现在同一个 Node
```

例如：

```
Node A
api-1

Node B
api-2

Node C
api-3
```

这样比：

```
Node A
api-1
api-2
api-3
```

具有更好的 Node 级别故障容忍能力。

------

### 15.5.3 Anti-Affinity 的风险

假设：

```
Node 数量 = 2
```

但：

```
replicas = 3
```

同时设置：

```
required Anti-Affinity
```

要求每个 Pod 必须在不同 Node。

那么：

```
Pod 1 → Node A
Pod 2 → Node B
Pod 3 → 无位置
```

第三个 Pod：

```
Pending
```

所以：

> **硬性的 Anti-Affinity 必须与集群容量一起设计。**

------

## 15.6 Taints

### 15.6.1 Taints 是什么

Taints 是 Node 级别的：

> **排斥机制。**

可以理解成：

```
Node
贴一个“禁止进入”的标记
```

例如：

```
GPU Node
```

只希望 GPU Pod 使用。

可以给 Node 添加：

```
kubectl taint nodes gpu-node gpu=true:NoSchedule
```

现在：

```
普通 Pod
 ↓
没有对应 Toleration
 ↓
不能调度到 gpu-node
```

------

### 15.6.2 Taint 的结构

例如：

```
gpu=true:NoSchedule
```

可以拆成：

```
key      = gpu
value    = true
effect   = NoSchedule
```

------

### 15.6.3 NoSchedule

```
NoSchedule
```

表示：

> **没有匹配 Toleration 的新 Pod，不会被调度到这个 Node。**

例如：

```
Node A
taint:
  gpu=true:NoSchedule
```

普通 Pod：

```
没有 toleration
```

那么：

```
不能调度
```

------

### 15.6.4 PreferNoSchedule

```
PreferNoSchedule
```

表示：

> **尽量不要调度到这个 Node。**

它属于偏好，而不是绝对禁止。

可以理解为：

```
NoSchedule
    ↓
强烈禁止

PreferNoSchedule
    ↓
尽量避免
```

------

### 15.6.5 NoExecute

`NoExecute` 比 `NoSchedule` 更强。

它不仅影响：

```
新 Pod
```

还可能影响：

```
已经运行的 Pod
```

如果 Pod 没有对应 Toleration：

```
Node 添加 NoExecute Taint
        ↓
已有 Pod
        ↓
可能被驱逐
```

这是生产环境非常重要的区别。

------

## 15.7 Tolerations

### 15.7.1 Toleration 是什么

Taint 是：

```
Node：
“我不希望普通 Pod 进来。”
```

Toleration 是：

```
Pod：
“我允许自己进入这种 Node。”
```

例如 Node：

```
kubectl taint nodes gpu-node gpu=true:NoSchedule
```

Pod：

```
tolerations:
  - key: gpu
    operator: Equal
    value: "true"
    effect: NoSchedule
```

那么：

```
Pod
 ↓
拥有 Toleration
 ↓
可以进入 gpu-node
```

------

### 15.7.2 完整示例

```
apiVersion: v1
kind: Pod
metadata:
  name: gpu-app
spec:
  tolerations:
    - key: gpu
      operator: Equal
      value: "true"
      effect: NoSchedule

  containers:
    - name: app
      image: nginx:1.27
```

但是这里有一个非常重要的认知：

> **Toleration 只是允许 Pod 调度到 Node，并不代表 Pod 一定会被调度到这个 Node。**

例如：

```
Node A
gpu=true:NoSchedule

Node B
普通 Node
```

Pod 有 GPU Toleration 后：

```
Node A → 可以
Node B → 也可以
```

Scheduler 仍然可能选择 Node B。

如果你希望：

```
一定去 GPU Node
```

通常还需要配合：

```
Node Affinity
```

这就是：

```
Taint/Toleration
+
Node Affinity
```

的典型生产用法。

------

## 15.8 Topology Spread Constraints

### 15.8.1 为什么需要它

前面的 Pod Anti-Affinity 可以实现：

```
Pod 不要在同一个 Node
```

但是生产环境往往需要更加精细的：

> **均匀分布。**

例如：

```
Zone A
Node A1
Node A2

Zone B
Node B1
Node B2

Zone C
Node C1
Node C2
```

我们有：

```
6 个 API Pod
```

理想情况：

```
Zone A → 2
Zone B → 2
Zone C → 2
```

而不是：

```
Zone A → 6
Zone B → 0
Zone C → 0
```

这时候可以使用：

```
Topology Spread Constraints
```

------

### 15.8.2 基本概念

它关注的是：

```
topology
```

例如：

```
Node
Zone
Region
```

然后控制：

```
Pod 在不同 topology domain 之间的分布差异
```

------

### 15.8.3 示例：跨 Node 均匀分布

```
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api
spec:
  replicas: 3

  selector:
    matchLabels:
      app: api

  template:
    metadata:
      labels:
        app: api

    spec:
      topologySpreadConstraints:
        - maxSkew: 1

          topologyKey: kubernetes.io/hostname

          whenUnsatisfiable: DoNotSchedule

          labelSelector:
            matchLabels:
              app: api

      containers:
        - name: api
          image: nginx:1.27
```

------

### 15.8.4 maxSkew

这是最核心的参数之一：

```
maxSkew: 1
```

可以粗略理解为：

> **不同 topology domain 之间的 Pod 数量差距尽量不要超过 1。**

例如：

```
Node A → 2
Node B → 1
Node C → 1
```

差距：

```
2 - 1 = 1
```

符合：

```
maxSkew = 1
```

------

### 15.8.5 topologyKey

例如：

```
topologyKey: kubernetes.io/hostname
```

表示：

```
按 Node 分布
```

如果：

```
topologyKey: topology.kubernetes.io/zone
```

则表示：

```
按 Zone 分布
```

所以：

```
hostname
    ↓
Node 级别

zone
    ↓
Availability Zone 级别
```

------

### 15.8.6 whenUnsatisfiable

常见：

```
DoNotSchedule
ScheduleAnyway
```

`DoNotSchedule`：

> 如果无法满足分布要求，就不要调度。

`ScheduleAnyway`：

> 尽量满足，但即使无法满足也可以调度。

所以：

```
DoNotSchedule
```

更加严格。

------

## 15.9 多可用区部署

### 15.9.1 什么是 Availability Zone

云厂商通常会把一个 Region 划分为多个：

```
Availability Zone
```

例如：

```
Region
│
├── Zone A
├── Zone B
└── Zone C
```

每个 Zone 通常代表一个相对独立的基础设施故障域。

------

### 15.9.2 为什么生产环境需要跨 AZ

如果所有 Pod：

```
Zone A
 ↓
所有业务
```

一旦：

```
Zone A
故障
```

整个应用可能不可用。

更好的方式：

```
Zone A
  ├── API
  └── API

Zone B
  ├── API
  └── API

Zone C
  ├── API
  └── API
```

这样某一个 Zone 故障：

```
Zone A
 ↓
故障
```

仍然可以：

```
Zone B + Zone C
 ↓
继续提供服务
```

------

### 15.9.3 Node 必须有 Zone Label

通常云环境 Node 会带有类似：

```
topology.kubernetes.io/zone
```

例如：

```
node-a
zone=ap-east-1a

node-b
zone=ap-east-1b

node-c
zone=ap-east-1c
```

可以检查：

```
kubectl get nodes \
  -L topology.kubernetes.io/zone
```

------

### 15.9.4 使用 Topology Spread

例如：

```
topologySpreadConstraints:
  - maxSkew: 1

    topologyKey: topology.kubernetes.io/zone

    whenUnsatisfiable: DoNotSchedule

    labelSelector:
      matchLabels:
        app: api
```

这意味着：

```
API Pod
 ↓
尽可能均匀分布
 ↓
多个 AZ
```

这比简单地：

```
nodeSelector
```

更加适合生产高可用场景。

------

## 15.10 高可用调度

生产环境所谓的高可用调度，本质上是在解决：

> **不要让一个基础设施故障同时杀死所有副本。**

例如：

```
Deployment
replicas = 3
```

错误的分布：

```
Node A
 ├── api-1
 ├── api-2
 └── api-3
```

Node A：

```
故障
```

结果：

```
3 个 Pod
全部不可用
```

------

### 15.10.1 更合理的分布

```
Node A
 └── api-1

Node B
 └── api-2

Node C
 └── api-3
```

如果 Node A 故障：

```
api-2
api-3
```

仍然可以服务。

------

### 15.10.2 更进一步：跨 AZ

生产环境通常希望：

```
Zone A
 └── api-1

Zone B
 └── api-2

Zone C
 └── api-3
```

这样：

```
Node 故障
```

影响有限。

甚至：

```
一个 AZ 故障
```

仍然能够保留部分副本。

------

### 15.10.3 高可用调度常见组合

实际生产环境经常组合：

```
Requests
+
Topology Spread Constraints
+
Pod Anti-Affinity
+
Node Affinity
+
Taints / Tolerations
```

例如：

```
业务 Pod
 │
 ├── Requests
 │      ↓
 │   保证有资源
 │
 ├── Node Affinity
 │      ↓
 │   选择特定 Node
 │
 ├── Topology Spread
 │      ↓
 │   跨 Node / AZ 均匀分布
 │
 └── Anti-Affinity
        ↓
     避免 Pod 扎堆
```

------

## 15.11 如何让 Pod 不要集中到同一个 Node

这是生产环境非常典型的问题。

假设：

```
Deployment
replicas: 6
```

集群：

```
Node A
Node B
Node C
```

如果没有额外调度约束，最终可能出现：

```
Node A → 4 Pod
Node B → 1 Pod
Node C → 1 Pod
```

甚至：

```
Node A → 6 Pod
Node B → 0 Pod
Node C → 0 Pod
```

具体结果取决于调度器当时的资源和其他约束，并不能假设 Kubernetes 会天然做到严格均匀分布。

------

### 15.11.1 方法一：Pod Anti-Affinity

例如：

```
affinity:
  podAntiAffinity:
    preferredDuringSchedulingIgnoredDuringExecution:
      - weight: 100
        podAffinityTerm:
          topologyKey: kubernetes.io/hostname

          labelSelector:
            matchLabels:
              app: api
```

这里使用：

```
preferred
```

表示：

> 尽量不要让 API Pod 与 API Pod 在同一个 Node。

它不会因为无法做到完全分散而导致 Pod 永久 Pending。

------

### 15.11.2 方法二：Topology Spread

生产环境更推荐使用：

```
topologySpreadConstraints:
  - maxSkew: 1
    topologyKey: kubernetes.io/hostname
    whenUnsatisfiable: ScheduleAnyway
    labelSelector:
      matchLabels:
        app: api
```

它表达的是：

> **尽量让 API Pod 在 Node 之间均匀分布。**

------

### 15.11.3 Anti-Affinity 和 Topology Spread 怎么选

简单理解：

```
Pod Anti-Affinity
```

更像：

> **不要和某些 Pod 放在一起。**

而：

```
Topology Spread
```

更像：

> **让 Pod 尽可能均匀分布。**

如果你的目标明确是：

```
“不要扎堆”
```

Topology Spread Constraints 往往更加直接。

------

### 15.11.4 一个生产示例

例如：

```
3 个 Node
3 个 Pod
```

配置：

```
topologySpreadConstraints:
  - maxSkew: 1
    topologyKey: kubernetes.io/hostname
    whenUnsatisfiable: DoNotSchedule

    labelSelector:
      matchLabels:
        app: api
```

理想：

```
Node A → 1
Node B → 1
Node C → 1
```

如果扩容到：

```
replicas = 6
```

则理想：

```
Node A → 2
Node B → 2
Node C → 2
```

这就是非常典型的生产调度策略。

## 15.12 调度失败排查

这是本章最终要掌握的实战能力。

当：

```
kubectl get pods
```

看到：

```
api-xxx   0/1   Pending
```

不要马上修改 YAML。

首先：

```
kubectl describe pod api-xxx
```

重点看：

```
Events
```

------

### 15.12.1 CPU / Memory 不足

例如：

```
0/3 nodes are available:
3 Insufficient cpu
```

说明：

```
没有 Node 能满足 Pod 的 CPU Request。
```

检查：

```
kubectl describe node <node-name>
```

以及：

```
kubectl top nodes
```

如果 Metrics Server 已安装。

------

### 15.12.2 Node Selector 不匹配

例如 Pod：

```
nodeSelector:
  disktype: ssd
```

但所有 Node：

```
disktype=hdd
```

那么：

```
没有符合条件的 Node
```

Pod：

```
Pending
```

检查：

```
kubectl get nodes --show-labels
```

------

### 15.12.3 Node Affinity 不匹配

例如：

```
requiredDuringSchedulingIgnoredDuringExecution:
```

要求：

```
zone=a
```

但集群只有：

```
zone=b
zone=c
```

那么：

```
Pod
 ↓
Pending
```

此时重点检查：

```
kubectl describe pod <pod-name>
```

Events 中通常会给出调度失败原因。

------

### 15.12.4 Taint 导致无法调度

例如 Node：

```
gpu=true:NoSchedule
```

Pod：

```
没有 Toleration
```

那么：

```
Pod
 ↓
不能进入 Node
```

查看 Node Taint：

```
kubectl describe node <node-name>
```

查看 Pod：

```
kubectl get pod <pod-name> -o yaml
```

检查：

```
spec:
  tolerations:
```

------

### 15.12.5 Anti-Affinity 导致 Pending

例如：

```
replicas = 3
```

但是：

```
Node = 2
```

并且：

```
required Pod Anti-Affinity
```

要求：

```
每个 Pod 必须在不同 Node
```

那么：

```
Pod 1 → Node A
Pod 2 → Node B
Pod 3 → Pending
```

此时不要误以为：

> “Kubernetes Scheduler 出故障了。”

实际上：

> **Scheduler 正确执行了你的硬性调度规则。**

------

### 15.12.6 Topology Spread 导致 Pending

例如：

```
whenUnsatisfiable: DoNotSchedule
```

如果集群无法满足：

```
maxSkew
```

Pod 就可能无法调度。

生产排查时重点检查：

```
replicas
Node 数量
Zone 数量
topologyKey
labelSelector
maxSkew
whenUnsatisfiable
```

------

### 15.12.7 PVC 也可能影响调度

如果 Pod 使用：

```
PersistentVolumeClaim
```

还可能受到：

```
StorageClass
PV topology
Volume zone
```

影响。

尤其云盘通常存在：

```
Volume
 ↓
Zone A
```

但是 Pod 被要求：

```
Zone B
```

那么就可能出现：

```
Volume 与 Node topology 不匹配
```

导致调度失败。

所以生产环境遇到 Pending：

> **不要只检查 CPU / Memory。**

------

### 15.12.8 推荐的调度故障排查流程

可以形成固定习惯：

```
Pod Pending
    │
    ▼
kubectl describe pod
    │
    ▼
Events
    │
    ├── Insufficient CPU
    │
    ├── Insufficient Memory
    │
    ├── nodeSelector
    │
    ├── nodeAffinity
    │
    ├── taint
    │
    ├── podAffinity
    │
    ├── podAntiAffinity
    │
    ├── topologySpread
    │
    └── volume topology
```

然后再检查 Node：

```
kubectl get nodes
kubectl describe node <node-name>
```

查看 Label：

```
kubectl get nodes --show-labels
```

查看 Taint：

```
kubectl describe nodes
```

查看资源：

```
kubectl top nodes
```

查看 Pod：

```
kubectl get pod <pod-name> -o yaml
```

## 本章核心知识

Kubernetes 调度可以用一句话概括：

> **Scheduler 从所有 Node 中先排除不符合硬性条件的 Node，再根据各种调度偏好选择更合适的 Node。**

几个核心机制需要区分清楚：

| 机制              | 解决什么问题                     |
| ----------------- | -------------------------------- |
| Scheduler         | 决定 Pod 去哪个 Node             |
| Node Selector     | Pod 必须去具有指定 Label 的 Node |
| Node Affinity     | 更灵活地选择 Node                |
| Pod Affinity      | 希望 Pod 和某些 Pod 靠近         |
| Pod Anti-Affinity | 希望 Pod 和某些 Pod 分开         |
| Taint             | Node 排斥某些 Pod                |
| Toleration        | Pod 容忍 Node 的 Taint           |
| Topology Spread   | 让 Pod 尽量均匀分布              |
| 多 AZ             | 避免单个可用区故障影响全部副本   |

最容易混淆的是：

```
Node Affinity
```

和：

```
Taint / Toleration
```

可以这样记：

```
Node Affinity：

Pod：
“我想去这种 Node。”
```

而：

```
Taint：

Node：
“我不欢迎普通 Pod。”
```

因此生产环境经常组合：

```
Taint
+
Toleration
+
Node Affinity
```

例如 GPU Node：

```
GPU Node
│
├── Taint
│     gpu=true:NoSchedule
│
└── Label
      accelerator=nvidia
```

GPU Pod：

```
Toleration
    ↓
允许进入 GPU Node

Node Affinity
    ↓
要求进入 GPU Node
```

最终实现：

```
普通 Pod
   ↓
不能进入 GPU Node

GPU Pod
   ↓
可以进入 GPU Node
   ↓
并且明确选择 GPU Node
```

而对于高可用业务：

```
Deployment
replicas: 3
       │
       ▼
Topology Spread
       │
       ├── Zone A
       ├── Zone B
       └── Zone C
```

再结合：

```
Requests
+
Pod Anti-Affinity / Topology Spread
+
多 AZ
```

最终目标就是：

```
              Cluster
                 │
       ┌─────────┼─────────┐
       ▼         ▼         ▼
    Zone A     Zone B     Zone C
       │         │         │
     Node       Node       Node
       │         │         │
     API-1     API-2     API-3
```

这样 Kubernetes 不仅知道：

> **Pod 需要多少资源。**

还知道：

> **Pod 应该放在哪里，以及哪些 Pod 应该靠近、哪些应该分开、哪些 Node 不应该使用，以及如何在 Node / AZ 故障时尽可能保持业务可用。**

# 第 16 章：Pod 生命周期与健康检查

前面我们学习了 **Pod 应该运行在哪个 Node**。

但 Pod 被调度到 Node 之后，还有一个非常重要的问题：

> **Kubernetes 怎么知道这个 Pod 是正常的？什么时候启动？什么时候重启？什么时候可以接收流量？应用关闭时又应该怎么退出？**

生产环境中，一个应用即使：

```
Pod = Running
```

也不代表：

```
应用 = 正常
```

例如：

```
Pod
└── Container
    └── .NET API
         ↓
       进程还活着
         ↓
       但数据库连接全部失败
```

此时 Pod 可能仍然显示：

```
Running
```

但是业务实际上已经无法正常工作。

所以 Kubernetes 提供了：

```
Pod Lifecycle
Container Lifecycle
Restart Policy
Startup Probe
Liveness Probe
Readiness Probe
Graceful Shutdown
```

这一整套机制。

------

## 16.1 Pod Lifecycle

### 16.1.1 Pod 生命周期是什么

Pod 生命周期描述的是：

> **Pod 从创建，到运行，再到结束的整个过程。**

Pod 常见的 Phase 有：

```
Pending
Running
Succeeded
Failed
Unknown
```

可以简单理解为：

```
创建 Pod
   │
   ▼
Pending
   │
   │ 调度 + 创建容器
   ▼
Running
   │
   ├──────────────┐
   │              │
   ▼              ▼
Succeeded       Failed
```

------

### 16.1.2 Pending

`Pending` 表示：

> Pod 已经被 Kubernetes 接受，但还没有完成运行准备。

可能包括：

```
还没有调度到 Node
镜像还没有拉下来
Volume 还没有准备好
容器还没有启动
```

例如：

```
kubectl get pods
```

看到：

```
NAME        READY   STATUS    RESTARTS
api-xxx     0/1     Pending   0
```

这时首先可以：

```
kubectl describe pod api-xxx
```

重点查看：

```
Events
```

------

### 16.1.3 Running

`Running` 表示：

> Pod 已经被绑定到 Node，并且至少有一个容器正在运行或正在启动。

注意：

> **Running 不等于应用健康。**

例如：

```
Pod
Status: Running

Container
Process: running

Application
Database connection: broken
```

所以不能单纯使用：

```
STATUS=Running
```

判断业务是否正常。

------

### 16.1.4 Succeeded

如果 Pod 中的容器正常执行完成：

```
exit code = 0
```

Pod 可能进入：

```
Succeeded
```

典型场景：

```
Job
一次性数据处理
数据库初始化
批处理
```

例如：

```
apiVersion: v1
kind: Pod
metadata:
  name: batch
spec:
  restartPolicy: Never

  containers:
    - name: batch
      image: busybox:1.36
      command:
        - sh
        - -c
        - echo "job completed"
```

执行：

```
kubectl apply -f batch.yaml
```

之后可能看到：

```
NAME     READY   STATUS      RESTARTS
batch    0/1     Completed   0
```

`Completed` 是 `kubectl` 对 Succeeded 状态的一种常见显示方式。

------

### 16.1.5 Failed

如果 Pod 中容器因为错误退出，并且 Pod 最终没有成功完成，就可能进入：

```
Failed
```

例如：

```
程序 exit 1
```

------

### 16.1.6 Pod Phase 与 Container State 不一样

这是初学者非常容易混淆的地方。

Pod 有：

```
Phase
```

Container 有：

```
State
```

Container State 常见：

```
Waiting
Running
Terminated
```

例如：

```
Pod
Phase = Running

Container
State = Running
```

也可能：

```
Pod
Phase = Running

Container
State = Waiting
```

因为 Pod 中可能有多个容器。

因此排查时：

```
kubectl get pod
```

只是第一步。

进一步应该：

```
kubectl describe pod <pod-name>
```

或者：

```
kubectl get pod <pod-name> -o yaml
```

------

## 16.2 Container Lifecycle

### 16.2.1 Container Lifecycle 是什么

Container Lifecycle 描述的是：

> **容器从创建、启动、运行到退出的过程。**

一个简化过程：

```
Container
   │
   ▼
Created
   │
   ▼
Running
   │
   ▼
Terminated
```

如果容器异常退出：

```
Running
   │
   ▼
Terminated
   │
   ▼
Restart Policy
   │
   ▼
重新启动
```

------

### 16.2.2 容器为什么会退出

常见原因：

```
应用正常退出
应用异常退出
OOMKilled
Liveness Probe 失败
Node 故障
Pod 被删除
Deployment 滚动更新
```

例如：

```
.NET API
   ↓
Unhandled Exception
   ↓
Process Exit
   ↓
Container Terminated
```

如果 Restart Policy 允许：

```
Container
   ↓
Restart
```

------

### 16.2.3 查看 Container 状态

```
kubectl get pod <pod-name> -o wide
```

进一步：

```
kubectl describe pod <pod-name>
```

也可以：

```
kubectl get pod <pod-name> -o jsonpath='{.status.containerStatuses[*]}'
```

生产环境排查重启问题时，尤其关注：

```
restartCount
lastState
reason
exitCode
finishedAt
```

------

## 16.3 Restart Policy

### 16.3.1 Restart Policy 是什么

`restartPolicy` 决定：

> **Pod 中容器退出后，Kubernetes 是否尝试重新启动它。**

常见值：

```
Always
OnFailure
Never
```

------

### 16.3.2 Always

```
restartPolicy: Always
```

表示：

> 容器退出后会被重新启动。

这是 Deployment / StatefulSet 等长期运行应用最常见的策略。

例如：

```
API Server
   ↓
进程崩溃
   ↓
Container Exit
   ↓
Kubernetes Restart
   ↓
API Server 恢复
```

------

### 16.3.3 OnFailure

```
restartPolicy: OnFailure
```

表示：

> 只有容器以非 0 状态码退出时才重启。

常用于：

```
Job
```

例如：

```
任务成功
exit 0
 ↓
不需要继续运行

任务失败
exit 1
 ↓
重新执行
```

------

### 16.3.4 Never

```
restartPolicy: Never
```

表示：

> 容器退出后不重新启动。

同样常见于一次性任务。

------

### 16.3.5 Restart Policy 与 Deployment

生产环境中需要记住：

> Deployment 并不是通过不断创建新 Pod 来处理容器进程崩溃的。

例如：

```
Deployment
   ↓
Pod
   ↓
Container crash
   ↓
kubelet restart container
```

只有 Pod 本身因为某些原因消失，Deployment 的 ReplicaSet 才会确保副本数重新满足期望。

------

### 16.3.6 CrashLoopBackOff

如果容器不断启动：

```
启动
 ↓
崩溃
 ↓
启动
 ↓
崩溃
 ↓
启动
 ↓
崩溃
```

Kubernetes 会逐渐增加重启之间的等待时间。

你可能看到：

```
CrashLoopBackOff
```

例如：

```
kubectl get pods
```

显示：

```
api-xxx   0/1   CrashLoopBackOff   8   10m
```

这不是根本错误。

它表达的是：

> **容器反复失败，Kubernetes 正在退避等待后再次尝试。**

排查：

```
kubectl logs api-xxx
```

以及：

```
kubectl logs api-xxx --previous
```

`--previous` 非常重要，因为它可以查看：

> **上一次已经崩溃的容器日志。**

------

## 16.4 Startup Probe

### 16.4.1 Startup Probe 是什么

Startup Probe 用来解决：

> **应用启动比较慢的问题。**

例如一个 Java / .NET 应用：

```
Container 启动
   ↓
加载配置
   ↓
初始化依赖
   ↓
加载模型
   ↓
连接数据库
   ↓
初始化缓存
   ↓
启动完成
```

可能需要：

```
30 秒
60 秒
甚至几分钟
```

如果直接使用 Liveness Probe：

```
启动后 5 秒
 ↓
健康检查失败
 ↓
Kubernetes 认为应用异常
 ↓
重启
```

结果：

```
永远启动不起来
```

这就是典型的：

> **Liveness Probe 把慢启动应用误杀。**

------

### 16.4.2 Startup Probe 的作用

配置：

```
startupProbe:
  httpGet:
    path: /health/startup
    port: 8080

  periodSeconds: 5
  failureThreshold: 30
```

意思大致是：

```
每 5 秒检查一次
最多允许连续失败 30 次
```

也就是给应用大约：

```
5 × 30 = 150 秒
```

启动时间。

------

### 16.4.3 Startup Probe 成功后

非常重要：

> **Startup Probe 成功之后，Liveness Probe 和 Readiness Probe 才开始正常发挥作用。**

可以理解成：

```
Container Start
      │
      ▼
Startup Probe
      │
      ├── 失败 → 继续等待
      │
      └── 成功
            │
            ├── Liveness Probe
            └── Readiness Probe
```

因此三者可以形成：

```
Startup
   ↓
Liveness + Readiness
```

------

## 16.5 Liveness Probe

### 16.5.1 Liveness Probe 是什么

Liveness Probe 用来回答：

> **这个容器里的应用还活着吗？**

如果 Kubernetes 判断：

```
应用已经无法正常运行
```

可能会：

```
重启 Container
```

------

### 16.5.2 为什么需要 Liveness Probe

假设 API 进程还活着：

```
PID 1
 ↓
Running
```

但是应用内部已经：

```
死锁
线程池耗尽
事件循环卡死
内部状态异常
```

进程没有退出。

如果没有 Liveness Probe：

```
Kubernetes：
“进程还在，应该没问题。”
```

但是：

```
用户：
“API 已经不能用了。”
```

Liveness Probe 可以帮助 Kubernetes 识别这种情况。

------

### 16.5.3 Liveness Probe 失败后

例如：

```
livenessProbe:
  httpGet:
    path: /health/live
    port: 8080

  periodSeconds: 10
  failureThreshold: 3
```

连续检查失败达到条件后：

```
Liveness Failed
       ↓
Kubernetes
       ↓
Restart Container
```

注意：

> Liveness Probe 失败通常意味着“重启容器”，而不是简单地把 Pod 从 Service 流量中摘除。

真正控制：

> **是否接收流量**

的是 Readiness Probe。

------

## 16.6 Readiness Probe

### 16.6.1 Readiness Probe 是什么

Readiness Probe 用来回答：

> **这个 Pod 现在是否准备好接收业务流量？**

这是生产环境非常重要的 Probe。

------

### 16.6.2 为什么需要 Readiness Probe

假设：

```
Pod 已经启动
```

但是：

```
应用正在初始化缓存
数据库连接还没有建立
依赖服务暂时不可用
正在执行启动任务
```

此时：

```
进程 = 活着
Pod = Running
```

但是：

```
不能接收流量
```

Readiness Probe 就是为此设计的。

------

### 16.6.3 Readiness 失败会发生什么

例如：

```
Pod
 ↓
Readiness Probe Failed
```

Kubernetes 会让这个 Pod：

```
Ready = False
```

然后 Service 不再把新的正常流量发送给它。

所以：

```
Liveness
 ↓
决定是否需要重启

Readiness
 ↓
决定是否应该接收流量
```

这是必须牢记的区别。

------

## 16.7 三种 Probe 的区别

这是本章最核心的知识之一。

| Probe     | 核心问题             | 失败后主要结果                     |
| --------- | -------------------- | ---------------------------------- |
| Startup   | 应用启动完成了吗？   | 阻止 Liveness / Readiness 提前执行 |
| Liveness  | 应用还活着吗？       | 重启 Container                     |
| Readiness | 应用现在能接流量吗？ | 从 Service 可用后端中暂时移除      |

可以记成：

```
Startup
“你启动好了吗？”

Liveness
“你还活着吗？”

Readiness
“你现在能接客吗？”
```

------

### 16.7.1 一个完整示例

假设 .NET API：

```
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api
spec:
  replicas: 3

  selector:
    matchLabels:
      app: api

  template:
    metadata:
      labels:
        app: api

    spec:
      containers:
        - name: api
          image: my-api:1.0

          ports:
            - containerPort: 8080

          startupProbe:
            httpGet:
              path: /health/startup
              port: 8080
            periodSeconds: 5
            failureThreshold: 30

          livenessProbe:
            httpGet:
              path: /health/live
              port: 8080
            periodSeconds: 10
            timeoutSeconds: 2
            failureThreshold: 3

          readinessProbe:
            httpGet:
              path: /health/ready
              port: 8080
            periodSeconds: 5
            timeoutSeconds: 2
            failureThreshold: 3
```

整个逻辑：

```
Container 启动
      │
      ▼
Startup Probe
      │
      │ 成功
      ▼
┌───────────────┐
│               │
▼               ▼
Liveness      Readiness
│               │
│               ├── Ready
│               │      ↓
│               │   接收流量
│               │
│               └── Not Ready
│                      ↓
│                   不接流量
│
└── Failed
       ↓
    Restart
```

------

## 16.8 HTTP Probe

### 16.8.1 HTTP Probe 是什么

HTTP Probe 通过 HTTP 请求检查应用。

例如：

```
livenessProbe:
  httpGet:
    path: /health/live
    port: 8080
```

Kubernetes 会类似执行：

```
GET /health/live
```

如果返回符合成功条件的 HTTP 状态码：

```
2xx
3xx
```

通常认为 Probe 成功。

------

### 16.8.2 为什么生产环境常用 HTTP Probe

因为 Web API 通常天然提供：

```
/health
/health/live
/health/ready
```

例如：

```
GET /health/live
```

可以只检查：

```
应用进程本身是否正常
```

而：

```
GET /health/ready
```

可以检查：

```
数据库
Redis
消息队列
关键依赖
```

但这里需要谨慎设计。

------

### 16.8.3 Liveness 不要检查太多外部依赖

例如错误设计：

```
/health/live
 ↓
检查数据库
 ↓
检查 Redis
 ↓
检查 MQ
 ↓
检查第三方 API
```

如果 Redis 暂时故障：

```
Readiness Failed
```

通常合理。

但如果：

```
Liveness Failed
```

然后：

```
Kubernetes
 ↓
不断重启 API
```

可能造成：

```
Redis 故障
 ↓
所有 API Liveness 失败
 ↓
所有 API 重启
 ↓
重启风暴
```

因此通常：

> **Liveness 更应该关注应用自身是否还能工作；Readiness 才适合考虑关键依赖是否满足接流量条件。**

------

## 16.9 TCP Probe

### 16.9.1 TCP Probe 是什么

TCP Probe 只检查：

> **指定端口能不能建立 TCP 连接。**

例如：

```
livenessProbe:
  tcpSocket:
    port: 8080

  periodSeconds: 10
```

如果：

```
TCP 8080
 ↓
连接成功
```

则 Probe 成功。

------

### 16.9.2 TCP Probe 的优点

简单：

```
不需要 HTTP endpoint
不需要应用实现健康检查 API
```

适合：

```
数据库
TCP 服务
非 HTTP 应用
```

------

### 16.9.3 TCP Probe 的局限

它只能说明：

```
端口有人监听
```

不能证明：

```
业务正常
```

例如：

```
8080
 ↓
TCP 能连接
```

但是应用：

```
内部线程死锁
数据库全部不可用
API 请求全部返回 500
```

TCP Probe 仍然可能成功。

所以：

> **TCP Probe 比较适合判断“服务端口是否还活着”，不适合判断复杂业务健康状态。**

------

## 16.10 Exec Probe

### 16.10.1 Exec Probe 是什么

Exec Probe 会在容器内部执行命令。

例如：

```
livenessProbe:
  exec:
    command:
      - cat
      - /tmp/healthy
```

如果命令：

```
exit code = 0
```

则成功。

非 0：

```
失败
```

------

### 16.10.2 示例

```
readinessProbe:
  exec:
    command:
      - sh
      - -c
      - test -f /tmp/ready
```

如果：

```
/tmp/ready
```

存在：

```
exit 0
```

Readiness 成功。

------

### 16.10.3 Exec Probe 的问题

它依赖：

```
容器内部存在对应命令
```

例如：

```
sh
cat
curl
wget
```

并不是所有镜像都包含这些工具。

尤其是：

```
distroless
scratch
极简镜像
```

可能没有 Shell。

因此：

> **不要因为“Exec Probe 很方便”就默认所有容器都使用它。**

对于 HTTP API，通常优先考虑 HTTP Probe。

------

## 16.11 Graceful Shutdown

### 16.11.1 什么是 Graceful Shutdown

Graceful Shutdown：

> **优雅关闭应用。**

不是：

```
kill -9
```

而是：

```
停止接收新请求
       ↓
等待已有请求完成
       ↓
关闭连接
       ↓
释放资源
       ↓
进程退出
```

------

### 16.11.2 为什么生产环境需要

假设 API 正在处理：

```
POST /payment
```

突然 Pod 被删除。

如果直接强制终止：

```
请求
 ↓
中途断开
```

可能造成：

```
客户端失败
数据库事务异常
消息重复
数据不一致
```

所以生产环境需要：

> **应用能够正确处理 Kubernetes 发出的终止信号。**

------

### 16.11.3 Kubernetes 删除 Pod 的大致过程

当执行：

```
kubectl delete pod api-xxx
```

不是简单：

```
立刻 kill
```

通常会经历类似：

```
删除请求
   │
   ▼
Pod 进入 Terminating
   │
   ├── 从正常流量路径中逐步移除
   │
   ├── 执行 preStop（如果配置）
   │
   ├── 向容器主进程发送 SIGTERM
   │
   ├── 等待 terminationGracePeriodSeconds
   │
   └── 如果仍未退出 → 强制终止
```

这里的具体时序在不同 Kubernetes/container runtime 与 EndpointSlice 流量处理场景下可能存在细节差异，但生产设计的核心目标不变：

> **让 Pod 有机会停止接收新流量并完成正在处理的工作。**

------

## 16.12 `preStop`

### 16.12.1 preStop 是什么

`preStop` 是 Container Lifecycle Hook。

它允许 Kubernetes 在终止容器前执行一个动作。

例如：

```
lifecycle:
  preStop:
    exec:
      command:
        - /bin/sh
        - -c
        - sleep 10
```

意思：

```
Pod 准备终止
   ↓
执行 preStop
   ↓
sleep 10
   ↓
继续终止流程
```

------

### 16.12.2 为什么需要 preStop

典型用途：

> **给流量切换和应用关闭留出时间。**

例如：

```
Pod
 ↓
准备退出
 ↓
不再适合接收新流量
 ↓
等待流量切换
 ↓
应用停止
```

实际生产中，`preStop` 可以用于：

```
通知应用进入 draining 状态
执行关闭脚本
等待连接排空
```

但：

> **不要把 `sleep 30` 当成万能优雅退出方案。**

真正可靠的 Graceful Shutdown 应该由：

```
Kubernetes 生命周期
+
应用自身 SIGTERM 处理
+
Readiness
+
合理的 terminationGracePeriodSeconds
```

共同完成。

------

## 16.13 `terminationGracePeriodSeconds`

### 16.13.1 是什么

这个参数定义：

> **Kubernetes 给 Pod 正常终止预留的宽限时间。**

例如：

```
terminationGracePeriodSeconds: 30
```

可以理解为：

```
开始终止
   ↓
给应用机会正常退出
   ↓
最多等待约 30 秒
   ↓
仍未退出
   ↓
强制终止
```

默认值通常为：

```
30 秒
```

------

### 16.13.2 为什么不能随便设置

例如：

```
terminationGracePeriodSeconds: 1
```

对于一个需要：

```
10 秒
```

才能完成请求的 API：

```
Pod Termination
 ↓
1 秒
 ↓
强制终止
```

显然不合理。

反过来：

```
terminationGracePeriodSeconds: 600
```

也可能带来问题：

```
滚动发布
 ↓
旧 Pod 长时间不退出
 ↓
发布速度变慢
```

因此需要根据应用实际情况设置。

------

### 16.13.3 如何估算

例如业务最长正常请求：

```
5 秒
```

可以考虑：

```
terminationGracePeriodSeconds: 15
```

留出：

```
流量切换
+
请求完成
+
应用清理
```

的余量。

实际值应该通过生产压测和真实请求耗时确定，而不是机械地使用某个固定数字。

------

## 16.14 应用优雅退出

### 16.14.1 Kubernetes 负责什么

Kubernetes 可以：

```
通知 Pod 终止
执行 lifecycle hook
发送终止信号
等待 grace period
最终强制终止
```

但是 Kubernetes 并不知道你的应用应该：

```
关闭数据库连接
停止 HTTP Server
等待请求
停止后台 Worker
提交/回滚事务
```

这些必须由：

> **应用自身实现。**

------

### 16.14.2 .NET 应用

对于 ASP.NET Core，应用应该正确处理 Host 的停止流程。

例如：

```
SIGTERM
  ↓
.NET Host 收到停止请求
  ↓
停止接收新请求
  ↓
等待已有请求
  ↓
执行 Hosted Service StopAsync
  ↓
释放资源
  ↓
进程退出
```

因此生产环境不要简单使用：

```
kill -9
```

式的思维来设计 Kubernetes 应用。

------

### 16.14.3 Node.js 应用

Node.js 通常可以监听：

```
process.on('SIGTERM', async () => {
  // stop accepting requests
  // close server
  // close database
  // cleanup
  process.exit(0);
});
```

核心思想一样：

```
收到 SIGTERM
   ↓
停止接收新请求
   ↓
等待旧请求完成
   ↓
关闭依赖
   ↓
退出
```

------

### 16.14.4 Java / Spring Boot

Spring Boot 同样应该让应用正常响应：

```
SIGTERM
```

并执行：

```
Graceful Shutdown
```

重点不是 Kubernetes 强行“替你关闭应用”，而是：

> **Kubernetes 发出终止请求，应用负责配合完成优雅退出。**

------

## 16.15 K8S 如何避免把流量发送给异常 Pod

这是本章最后一个非常重要的问题。

假设：

```
Service
   │
   ├── Pod A Ready
   ├── Pod B Ready
   └── Pod C Not Ready
```

Kubernetes 的服务发现体系会根据 Pod 的就绪状态维护可用后端。

于是正常情况下：

```
Client
  ↓
Service
  ├── Pod A
  └── Pod B
```

而：

```
Pod C
NotReady
```

不会作为正常可用后端接收 Service 流量。

------

### 16.15.1 Readiness 是核心

例如：

```
readinessProbe:
  httpGet:
    path: /health/ready
    port: 8080

  periodSeconds: 5
  failureThreshold: 3
```

当：

```
/health/ready
```

失败：

```
Pod
 ↓
Ready=False
```

Service 后端集合会相应更新。

可以理解成：

```
Pod
 ↓
Readiness Failed
 ↓
EndpointSlice 不再把它作为 Ready 后端
 ↓
Service 不再正常发送新流量
```

------

### 16.15.2 Deployment 滚动更新为什么不会简单地“一刀切”

假设：

```
旧版本
api-v1
api-v1
api-v1
```

更新到：

```
api-v2
```

滚动更新过程中：

```
api-v1   Ready
api-v1   Ready
api-v2   Starting
```

此时：

```
api-v2
Readiness = False
```

所以：

```
Service
 ↓
继续使用 Ready 的 api-v1
```

等：

```
api-v2
Readiness = True
```

之后：

```
Service
 ↓
开始将流量发送给 api-v2
```

这就是为什么：

> **Readiness Probe 是生产环境滚动发布的关键机制之一。**

------

### 16.15.3 Liveness 和 Readiness 配合

假设：

```
Pod A
```

发生：

```
应用内部死锁
```

那么：

```
Liveness
 ↓
失败
 ↓
Container Restart
```

如果应用暂时：

```
启动成功
但还没有准备好处理业务
```

则：

```
Readiness
 ↓
False
 ↓
不接收 Service 流量
```

最终形成：

```
              Pod
               │
       ┌───────┴────────┐
       │                │
       ▼                ▼
   Liveness          Readiness
       │                │
       ▼                ▼
需要不需要重启？     能不能接流量？
```

------

### 16.15.4 一个生产级健康检查设计

对于一个典型 API：

```
/health/live
/health/ready
```

可以设计成：

```
Startup Probe
    ↓
/health/startup
    ↓
只判断应用是否完成启动

Liveness Probe
    ↓
/health/live
    ↓
主要判断应用自身是否还能正常工作

Readiness Probe
    ↓
/health/ready
    ↓
判断当前是否具备接收业务流量的条件
```

例如：

```
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api
spec:
  replicas: 3

  selector:
    matchLabels:
      app: api

  template:
    metadata:
      labels:
        app: api

    spec:
      terminationGracePeriodSeconds: 30

      containers:
        - name: api
          image: my-api:1.0
          ports:
            - containerPort: 8080

          startupProbe:
            httpGet:
              path: /health/startup
              port: 8080
            periodSeconds: 5
            timeoutSeconds: 2
            failureThreshold: 30

          livenessProbe:
            httpGet:
              path: /health/live
              port: 8080
            periodSeconds: 10
            timeoutSeconds: 2
            failureThreshold: 3

          readinessProbe:
            httpGet:
              path: /health/ready
              port: 8080
            periodSeconds: 5
            timeoutSeconds: 2
            failureThreshold: 3

          lifecycle:
            preStop:
              exec:
                command:
                  - /bin/sh
                  - -c
                  - sleep 5
```

整个生产运行过程可以理解为：

```
                 Container Start
                       │
                       ▼
                Startup Probe
                       │
                 启动完成
                       │
            ┌──────────┴──────────┐
            ▼                     ▼
       Liveness               Readiness
            │                     │
      应用是否活着？         是否能接流量？
            │                     │
        Failed                   False
            │                     │
            ▼                     ▼
      Restart Container      Service 不发流量
                                  │
                                True
                                  │
                                  ▼
                             接收流量
```

当 Pod 被终止：

```
kubectl delete pod
        │
        ▼
Pod Terminating
        │
        ▼
流量逐步停止发送
        │
        ▼
preStop
        │
        ▼
SIGTERM
        │
        ▼
应用 Graceful Shutdown
        │
        ▼
请求完成 / 资源释放
        │
        ▼
Container Exit
```

如果应用一直不退出：

```
terminationGracePeriodSeconds
        │
        ▼
超时
        │
        ▼
强制终止
```

因此生产环境真正可靠的 Pod 生命周期设计，不是简单地添加一个：

```
livenessProbe:
```

而是把：

```
Startup
+
Liveness
+
Readiness
+
Graceful Shutdown
+
preStop
+
terminationGracePeriodSeconds
```

作为一个完整体系来设计。

最重要的几个判断可以最终记成：

```
Startup Probe
→ “我启动完了吗？”

Liveness Probe
→ “我是不是已经死掉/卡死了？”

Readiness Probe
→ “我现在能不能接业务流量？”

preStop
→ “我要退出了，先执行退出前动作。”

terminationGracePeriodSeconds
→ “你还有多少时间可以优雅退出？”

SIGTERM / Graceful Shutdown
→ “应用自己如何正确关闭？”
```

而 Kubernetes 避免把流量发送给异常 Pod 的关键链路是：

```
Readiness Probe
      ↓
Ready / NotReady
      ↓
EndpointSlice
      ↓
Service
      ↓
只把正常流量发送给可用后端
```

这也是生产环境中 **健康检查、滚动发布和无损发布** 能够协同工作的基础。
