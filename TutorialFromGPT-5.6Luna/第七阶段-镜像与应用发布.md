# 第 19 章：Docker 镜像与 Kubernetes

在前面的章节中，我们经常看到这样的 Kubernetes 配置：

```
containers:
  - name: api
    image: nginx:1.27
```

这里的：

```
nginx:1.27
```

就是一个 **Container Image（容器镜像）**。

Kubernetes 本身并不负责构建镜像，它主要负责：

```
获取镜像
   ↓
启动 Container
   ↓
管理 Pod
   ↓
根据声明维持应用运行
```

所以要把 Kubernetes 应用真正部署到生产环境，必须理解：

```
代码
 ↓
Docker Image
 ↓
Registry
 ↓
Kubernetes Node
 ↓
Container
 ↓
Pod
```

------

## 19.1 Image 基础

### 19.1.1 Image 是什么

Docker Image（容器镜像）可以理解成：

> **运行一个 Container 所需要的软件、依赖、文件系统和元数据的只读模板。**

例如一个 .NET API：

```
.NET API Image
├── Linux 基础文件
├── .NET Runtime
├── Application DLL
├── appsettings.json
└── 其他依赖
```

启动后：

```
Image
  ↓
Container
```

可以把它简单理解成：

```
Image = 安装好的应用模板
Container = Image 的运行实例
```

------

### 19.1.2 Image 与 Container 的关系

例如：

```
nginx:1.27
```

是一份 Image。

可以启动多个 Container：

```
nginx:1.27
    │
    ├── Container A
    ├── Container B
    └── Container C
```

Kubernetes 中：

```
Deployment
    ↓
Pod
    ↓
Container
    ↓
Image
```

例如：

```
containers:
  - name: api
    image: nginx:1.27
```

Kubernetes 会让 Node 上的 Container Runtime 获取：

```
nginx:1.27
```

然后启动 Container。

------

### 19.1.3 Image 通常包含什么

一个镜像通常包含：

```
Application
Runtime
Libraries
System utilities
Configuration defaults
Metadata
```

例如 Node.js 应用：

```
Node.js Image
├── Linux filesystem
├── Node.js runtime
├── npm
├── Application source/build output
└── dependencies
```

而对于生产环境，通常不会直接把开发环境全部塞进去。

例如：

```
TypeScript
 ↓
npm install
 ↓
npm run build
 ↓
dist/
```

最终运行镜像可能只需要：

```
Node.js runtime
+
dist/
+
production dependencies
```

这就是后面多阶段构建和镜像优化的基础。

------

## 19.2 Registry

### 19.2.1 Registry 是什么

Registry 是：

> **存放和分发 Container Image 的镜像仓库。**

可以理解成：

```
Git Repository
    ↓
保存源代码

Container Registry
    ↓
保存 Container Image
```

例如：

```
Developer
   ↓
docker build
   ↓
Image
   ↓
docker push
   ↓
Registry
```

Kubernetes：

```
Registry
   ↓
Node
   ↓
Image
   ↓
Container
```

------

### 19.2.2 为什么 Kubernetes 需要 Registry

假设你有：

```
Node-1
Node-2
Node-3
```

而应用镜像是：

```
my-api:1.0.0
```

如果镜像只存在开发人员电脑：

```
Developer PC
└── my-api:1.0.0
```

Kubernetes Node 无法直接使用。

所以需要：

```
Developer
    ↓
Registry
    ↓
┌───────┬───────┬───────┐
Node-1 Node-2 Node-3
```

每个 Node 都可以从 Registry 拉取镜像。

------

### 19.2.3 Push 与 Pull

开发人员：

```
docker push registry.example.com/my-api:1.0.0
```

意味着：

```
本地 Image
    ↓
Registry
```

Kubernetes：

```
registry.example.com/my-api:1.0.0
```

意味着 Node 需要：

```
Registry
    ↓
Node
```

也就是 Pull。

------

## 19.3 Docker Hub

### 19.3.1 Docker Hub 是什么

Docker 提供的 Docker Hub 是非常常见的公共 Container Registry。

它可以存储：

```
Public Images
Private Images
```

例如：

```
nginx
redis
postgres
```

等大量公共镜像。

------

### 19.3.2 Kubernetes 使用 Docker Hub

例如：

```
containers:
  - name: nginx
    image: nginx:1.27
```

如果没有指定 Registry：

```
nginx:1.27
```

通常表示：

```
docker.io/library/nginx:1.27
```

Kubernetes Node 会尝试从 Docker Hub 拉取。

------

### 19.3.3 Docker Hub 适合什么场景

非常适合：

```
学习
测试
个人项目
公共基础镜像
```

例如：

```
image: nginx:1.27
```

学习 Kubernetes 时非常方便。

但是生产环境通常不会简单依赖：

```
公网 Docker Hub
```

而会考虑：

```
企业私有 Registry
镜像缓存
镜像代理
Harbor
云厂商 Registry
```

------

## 19.4 Harbor

### 19.4.1 Harbor 是什么

Harbor 是一个开源的企业级 Container Registry。

它可以部署在企业内部：

```
Developer
   │
   ▼
 Harbor
   │
   ├── Project A
   ├── Project B
   └── Project C
```

相比简单的 Registry，Harbor 通常提供更加完整的企业能力，例如：

```
用户权限
Project
镜像管理
镜像扫描
Replication
审计
访问控制
```

------

### 19.4.2 为什么生产环境常见 Harbor

假设企业有：

```
10 个团队
100 个服务
1000 个镜像版本
```

如果全部依赖：

```
Docker Hub
```

会产生：

```
权限管理
镜像安全
网络访问
审计
镜像生命周期
```

等问题。

使用 Harbor：

```
开发环境
       │
       ▼
    Harbor
       │
 ┌─────┼─────┐
 ▼     ▼     ▼
K8S-1 K8S-2 K8S-3
```

可以把企业镜像集中管理。

------

### 19.4.3 Harbor 项目

例如：

```
Harbor
└── Project: production
    ├── order-api
    ├── user-api
    └── payment-api
```

镜像可能是：

```
harbor.example.com/production/order-api:1.0.0
```

Kubernetes：

```
containers:
  - name: order-api
    image: harbor.example.com/production/order-api:1.0.0
```

------

## 19.5 私有 Registry

### 19.5.1 为什么需要私有 Registry

生产环境通常需要：

```
企业内部镜像
```

例如：

```
registry.example.com/backend/order-api:1.0.0
```

而不是：

```
docker.io/andy/order-api:1.0.0
```

主要原因包括：

```
安全
权限
网络
合规
镜像访问速度
供应链控制
```

------

### 19.5.2 私有 Registry 的基本架构

```
CI/CD
  │
  │ docker push
  ▼
Private Registry
  │
  │ image pull
  ▼
Kubernetes
  │
  ├── Node-1
  ├── Node-2
  └── Node-3
```

------

### 19.5.3 私有 Registry 必须考虑 HTTPS

生产环境不要简单使用：

```
http://registry.example.com
```

而应该：

```
https://registry.example.com
```

原因是镜像本身可能包含：

```
业务代码
依赖
配置
内部组件
```

并且 Registry 的认证信息也需要安全传输。

------

## 19.6 ImagePullSecrets

### 19.6.1 为什么需要 ImagePullSecrets

如果 Registry 是私有的：

```
harbor.example.com
```

Kubernetes Node：

```
docker pull
```

需要认证。

例如：

```
Username
Password
```

Kubernetes 可以使用：

```
imagePullSecrets
```

保存 Registry 认证信息。

------

### 19.6.2 创建 Registry Secret

例如：

```
kubectl create secret docker-registry harbor-secret \
  --docker-server=harbor.example.com \
  --docker-username=admin \
  --docker-password='YOUR_PASSWORD'
```

查看：

```
kubectl get secret harbor-secret
```

注意：

> Secret 本身并不会神奇地让密码变成不可读取的密文。

这一点后面会继续涉及。

------

### 19.6.3 Pod 使用 ImagePullSecrets

```
apiVersion: v1
kind: Pod
metadata:
  name: api

spec:
  imagePullSecrets:
    - name: harbor-secret

  containers:
    - name: api
      image: harbor.example.com/production/api:1.0.0
```

如果使用 Deployment：

```
spec:
  template:
    spec:
      imagePullSecrets:
        - name: harbor-secret

      containers:
        - name: api
          image: harbor.example.com/production/api:1.0.0
```

------

### 19.6.4 推荐绑定到 ServiceAccount

如果一个 Namespace 中大量 Pod 都需要访问同一个 Registry，可以考虑：

```
apiVersion: v1
kind: ServiceAccount
metadata:
  name: app-sa
imagePullSecrets:
  - name: harbor-secret
```

然后：

```
spec:
  serviceAccountName: app-sa
```

这样可以减少每个 Deployment 重复配置。

------

## 19.7 Image Tag

### 19.7.1 Tag 是什么

例如：

```
nginx:1.27
```

这里：

```
nginx
```

是 Repository。

```
1.27
```

是 Tag。

完整形式：

```
registry/repository:tag
```

例如：

```
harbor.example.com/production/order-api:1.2.3
```

------

### 19.7.2 Tag 的作用

Tag 通常用于标记：

```
版本
环境
发布批次
```

例如：

```
order-api:1.0.0
order-api:1.1.0
order-api:2.0.0
```

也可以：

```
order-api:production
order-api:staging
```

但生产环境更推荐使用明确的不可变版本标识。

------

## 19.8 `latest` 的问题

### 19.8.1 `latest` 是什么

例如：

```
image: my-api:latest
```

它只是一个 Tag。

并不代表：

```
最新代码
```

也不代表：

```
生产环境最新稳定版本
```

它只是：

```
一个叫 latest 的标签
```

------

### 19.8.2 为什么生产环境不推荐 latest

假设今天：

```
latest → Image A
```

Deployment：

```
image: my-api:latest
```

明天：

```
latest → Image B
```

但是 Kubernetes YAML 完全没变化。

这会造成：

```
昨天部署：
latest = A

今天部署：
latest = B
```

从 YAML 很难判断实际运行的到底是哪一个 Image。

------

### 19.8.3 回滚困难

假设：

```
latest → v2
```

v2 有 Bug。

你想回滚：

```
v1
```

但是：

```
latest
```

这个名字本身没有表达版本。

因此生产环境推荐：

```
image: harbor.example.com/production/order-api:1.8.3
```

而不是：

```
image: harbor.example.com/production/order-api:latest
```

------

## 19.9 Image Digest

### 19.9.1 Digest 是什么

Image Tag：

```
my-api:1.0.0
```

实际上最终对应一个镜像内容摘要：

```
sha256:xxxxxxxxxxxxxxxx...
```

例如：

```
my-api@sha256:abcdef123456...
```

Digest 可以理解为：

> **镜像内容的唯一标识。**

------

### 19.9.2 Tag 与 Digest 的区别

Tag：

```
my-api:1.0.0
```

是人为定义的名字。

Digest：

```
my-api@sha256:abc...
```

对应具体的镜像内容。

因此：

```
Tag → 可以被重新指向
Digest → 对应确定内容
```

例如：

```
1.0.0 → Image A
```

理论上 Registry 管理者可以重新修改：

```
1.0.0 → Image B
```

但是：

```
sha256:AAA
```

仍然对应原来的 Image A。

------

### 19.9.3 生产环境为什么重视 Digest

如果要求：

```
今天部署的镜像
=
明天部署的镜像
=
任何 Node 拉取的镜像
```

那么 Digest 非常有价值。

例如：

```
image: harbor.example.com/production/order-api@sha256:abcdef...
```

这样可以实现更加严格的：

```
Image Immutability
```

和部署可追踪性。

------

## 19.10 镜像版本管理

### 19.10.1 推荐使用明确版本

例如：

```
order-api:1.0.0
order-api:1.0.1
order-api:1.1.0
order-api:2.0.0
```

不要：

```
order-api:latest
```

------

### 19.10.2 不推荐覆盖同一个生产 Tag

例如：

```
order-api:prod
```

今天：

```
prod → v1
```

明天：

```
prod → v2
```

这会降低部署可追踪性。

更好的方式：

```
order-api:1.0.0
order-api:1.1.0
```

Deployment：

```
image: harbor.example.com/production/order-api:1.1.0
```

------

### 19.10.3 CI/CD 推荐版本策略

例如 Git：

```
Commit
 ↓
CI Build
 ↓
Image
```

可以使用：

```
order-api:<git-sha>
```

例如：

```
order-api:8f3a9d2
```

也可以结合正式版本：

```
order-api:1.4.2
```

生产环境常见做法：

```
Git Commit
     ↓
Build
     ↓
Image
     ↓
Scan
     ↓
Push Registry
     ↓
Deploy
```

这样可以追溯：

```
Pod
 ↓
Image
 ↓
Image Digest
 ↓
Git Commit
```

## 19.11 多阶段构建

### 19.11.1 为什么需要多阶段构建

假设一个 .NET 应用：

```
Source Code
 ↓
dotnet restore
 ↓
dotnet build
 ↓
dotnet publish
```

构建过程需要：

```
SDK
Compiler
NuGet
Build tools
```

但是运行应用可能只需要：

```
.NET Runtime
```

如果全部放进最终镜像：

```
Image
├── SDK
├── Compiler
├── Build tools
├── Source
└── Application
```

镜像会非常大。

------

### 19.11.2 Multi-stage Build

Docker 支持：

```
Build Stage
       ↓
Runtime Stage
```

例如 .NET：

```
FROM mcr.microsoft.com/dotnet/sdk:8.0 AS build

WORKDIR /src

COPY . .

RUN dotnet restore

RUN dotnet publish \
    -c Release \
    -o /app/publish \
    --no-restore


FROM mcr.microsoft.com/dotnet/aspnet:8.0 AS runtime

WORKDIR /app

COPY --from=build /app/publish .

ENTRYPOINT ["dotnet", "MyApi.dll"]
```

最终：

```
Build Image
├── SDK
├── Source
└── Compiler

        ↓ COPY --from

Runtime Image
├── Runtime
└── Published Application
```

最终镜像不需要包含 SDK。

------

### 19.11.3 Node.js 示例

```
FROM node:22 AS build

WORKDIR /app

COPY package*.json ./

RUN npm ci

COPY . .

RUN npm run build


FROM node:22-slim AS runtime

WORKDIR /app

COPY --from=build /app/dist ./dist
COPY --from=build /app/node_modules ./node_modules
COPY package*.json ./

CMD ["node", "dist/server.js"]
```

核心思想仍然是：

```
Build Environment
       ↓
编译
       ↓
Runtime Environment
```

------

## 19.12 镜像大小优化

镜像越大，通常意味着：

```
Pull 时间更长
网络流量更多
Node 磁盘占用更多
Pod 启动更慢
```

因此生产环境应该合理控制镜像大小。

------

### 19.12.1 选择合适的 Base Image

例如：

```
FROM node:22
```

通常比：

```
FROM node:22-slim
```

更大。

可以根据应用需求选择：

```
完整镜像
Slim
Alpine
Distroless
```

但不能机械地认为：

> Alpine 一定最好。

因为某些应用依赖：

```
glibc
native libraries
```

使用 Alpine 的 musl libc 可能产生兼容性问题。

所以应该：

> **以应用兼容性和安全性为前提进行优化。**

------

### 19.12.2 `.dockerignore`

如果项目：

```
node_modules/
.git/
dist/
logs/
```

不需要进入 Build Context，可以：

```
.dockerignore
```

例如：

```
node_modules
.git
dist
coverage
*.log
.env
```

然后：

```
COPY . .
```

就不会把这些文件发送给 Docker Build Context。

------

### 19.12.3 删除无用文件

例如不要在生产镜像里保留：

```
测试文件
Git 历史
文档
编译缓存
开发依赖
日志
临时文件
```

------

### 19.12.4 不要把 Secret 打进 Image

非常重要。

错误做法：

```
ENV DB_PASSWORD=123456
```

或者：

```
COPY .env .
```

这样 Secret 可能进入 Image Layer。

即使之后：

```
RUN rm .env
```

也不一定真正从历史 Layer 中消失。

正确思路是：

```
Image
 ↓
不包含 Secret
 ↓
Kubernetes Secret
 ↓
Pod
```

也就是：

```
应用镜像
+
运行时配置
=
Container
```

而不是：

```
Secret
+
Image
=
新 Image
```

------

## 19.13 K8S 拉取镜像失败排查

这是生产环境非常常见的问题。

例如：

```
kubectl get pods
```

发现：

```
NAME                       STATUS
order-api-xxx              ImagePullBackOff
```

或者：

```
ErrImagePull
```

------

### 19.13.1 第一步：查看 Pod

```
kubectl get pod
```

例如：

```
NAME              READY   STATUS             RESTARTS
order-api-xxx     0/1     ImagePullBackOff    0
```

------

### 19.13.2 第二步：查看 Pod Events

最重要的命令之一：

```
kubectl describe pod order-api-xxx
```

重点查看：

```
Events:
```

例如：

```
Failed to pull image
```

------

### 19.13.3 常见错误一：镜像不存在

例如：

```
manifest unknown
```

通常意味着：

```
Repository 不存在
```

或者：

```
Tag 不存在
```

检查：

```
image: harbor.example.com/production/order-api:1.0.0
```

确认 Registry 中是否真的存在：

```
order-api
1.0.0
```

------

### 19.13.4 常见错误二：认证失败

例如：

```
unauthorized
authentication required
```

说明 Node 没有正确认证 Registry。

检查：

```
kubectl get secret
```

然后：

```
kubectl describe pod <pod-name>
```

确认：

```
imagePullSecrets:
  - name: harbor-secret
```

是否正确。

------

### 19.13.5 常见错误三：Secret 不存在

例如：

```
secret "harbor-secret" not found
```

检查：

```
kubectl get secret harbor-secret
```

如果不存在：

```
kubectl create secret docker-registry harbor-secret \
  --docker-server=harbor.example.com \
  --docker-username=YOUR_USERNAME \
  --docker-password='YOUR_PASSWORD'
```

------

### 19.13.6 常见错误四：Registry 网络无法访问

例如：

```
dial tcp ... timeout
```

可能是：

```
Node
 ↓
Registry
```

之间网络不通。

检查：

```
kubectl get nodes -o wide
```

然后从对应 Node 的运行环境检查 Registry：

```
curl -vk https://harbor.example.com/v2/
```

如果需要认证，返回：

```
401 Unauthorized
```

反而可能说明：

```
Registry 网络已经可以访问
```

因为 Registry 已经响应请求，只是需要认证。

------

### 19.13.7 常见错误五：TLS Certificate 问题

例如：

```
x509: certificate signed by unknown authority
```

通常意味着：

```
Node / Container Runtime
```

不信任 Registry 使用的 CA。

例如企业 Harbor 使用：

```
内部 CA
```

那么每个 Kubernetes Node 的 Container Runtime 都需要正确配置 CA 信任。

这是生产私有 Registry 非常重要的一环。

------

### 19.13.8 常见错误六：HTTP Registry

例如 Registry：

```
http://harbor.example.com
```

而 Container Runtime 默认要求 HTTPS。

可能出现：

```
http: server gave HTTP response to HTTPS client
```

生产环境推荐直接解决：

```
HTTPS
+
正确 CA
```

而不是简单把 Registry 配置成 insecure registry。

------

### 19.13.9 常见错误七：镜像架构不匹配

例如你的镜像只构建了：

```
linux/amd64
```

但是 Kubernetes Node 是：

```
linux/arm64
```

可能出现：

```
no matching manifest
```

检查 Node：

```
kubectl get nodes -o wide
```

更准确可以：

```
kubectl get nodes \
  -o custom-columns=NAME:.metadata.name,ARCH:.status.nodeInfo.architecture
```

例如：

```
NAME       ARCH
node-1     amd64
node-2     arm64
```

如果集群是混合架构，镜像最好构建多架构版本。

例如：

```
docker buildx build \
  --platform linux/amd64,linux/arm64 \
  -t harbor.example.com/production/order-api:1.0.0 \
  --push .
```

这样 Registry 中可以包含：

```
linux/amd64
linux/arm64
```

Kubernetes Node 会选择匹配自己架构的镜像。

### 19.13.10 常见错误八：磁盘空间不足

Node 如果磁盘快满：

```
No space left on device
```

可能无法继续拉取镜像。

查看：

```
df -h
```

以及 Kubernetes：

```
kubectl describe node <node-name>
```

检查：

```
DiskPressure
```

例如：

```
Conditions:
  DiskPressure   True
```

这说明 Node 存储压力已经比较严重。

生产环境需要关注：

```
Container Image
Container Logs
containerd
/var/lib/containerd
/var/lib/kubelet
```

等空间使用情况。

### 19.13.12 一套完整排查流程

遇到：

```
ImagePullBackOff
```

不要直接猜。

按照下面顺序：

```
kubectl get pod <pod-name>
```

然后：

```
kubectl describe pod <pod-name>
```

重点：

```
Events
```

然后确认 Image：

```
kubectl get pod <pod-name> \
  -o jsonpath='{.spec.containers[*].image}'
```

检查 Secret：

```
kubectl get secret
```

检查 Pod：

```
kubectl get pod <pod-name> -o yaml
```

确认：

```
image:
imagePullSecrets:
```

再检查 Node：

```
kubectl get pod <pod-name> -o wide
```

找到 Pod 所在 Node 后：

```
kubectl describe node <node-name>
```

重点检查：

```
DiskPressure
Architecture
Conditions
```

最终把问题归类：

```
ImagePullBackOff
       │
       ├── Image 不存在
       ├── Tag 不存在
       ├── Registry 认证失败
       ├── imagePullSecrets 错误
       ├── DNS 问题
       ├── 网络问题
       ├── TLS / CA 问题
       ├── 镜像架构问题
       ├── Registry 权限问题
       └── Node 磁盘问题
```

## 本章核心知识

这一章最重要的是建立完整的 **Image 生命周期**：

```
源代码
  │
  ▼
Dockerfile
  │
  ▼
docker build
  │
  ▼
Image
  │
  │ docker push
  ▼
Registry
  │
  │ image pull
  ▼
Kubernetes Node
  │
  ▼
Container
  │
  ▼
Pod
```

生产环境推荐的基本原则可以浓缩成：

```
① 不使用 latest 作为生产版本
② 使用明确、可追踪的 Image Tag
③ 更严格的场景使用 Image Digest
④ 私有镜像使用 ImagePullSecrets
⑤ 生产环境使用企业级 Registry
⑥ 镜像尽量小
⑦ 使用 Multi-stage Build
⑧ 不把 Secret 打进 Image
⑨ 构建并验证正确的 CPU Architecture
⑩ ImagePullBackOff 优先看 kubectl describe pod 的 Events
```

尤其要记住一个生产环境非常重要的关系：

```
Tag
 ↓
Digest
 ↓
具体 Image 内容
```

以及：

```
Kubernetes YAML
        ↓
image: registry/app:1.2.3
        ↓
Registry
        ↓
具体 Image
        ↓
Container
```

**镜像不是 Kubernetes 创建出来的，Kubernetes 的职责是使用和管理镜像运行出来的 Container。**
