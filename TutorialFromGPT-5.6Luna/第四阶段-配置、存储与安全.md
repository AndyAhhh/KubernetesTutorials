# 第 11 章：ConfigMap——管理应用配置

在前面的章节中，我们已经学习了：

```
Deployment
   ↓
Pod
   ↓
Container
```

应用真正运行时，通常不仅需要代码和镜像，还需要大量**配置**，例如：

```
应用端口
日志级别
数据库地址
Redis 地址
第三方 API 地址
功能开关
时区
运行环境
```

如果把这些配置全部写死在 Docker 镜像里面，就会出现一个很实际的问题：

```
开发环境镜像
    ↓
测试环境镜像
    ↓
生产环境镜像
```

每换一个环境，就可能需要重新构建镜像。

Kubernetes 提供了 **ConfigMap** 来解决这类问题：

```
应用镜像
   +
ConfigMap
   ↓
运行中的应用
```

核心思想就是：

> **代码和配置分离。**

------

## 11.1 ConfigMap 是什么

### 11.1.1 ConfigMap 的定义

ConfigMap 是 Kubernetes 中用于保存**非敏感配置数据**的 API 对象。

例如：

```
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
data:
  APP_ENV: production
  LOG_LEVEL: info
  SERVER_PORT: "8080"
```

创建：

```
kubectl apply -f configmap.yaml
```

查看：

```
kubectl get configmap
```

查看具体内容：

```
kubectl get configmap app-config -o yaml
```

------

### 11.1.2 ConfigMap 保存什么

典型数据：

```
配置项              示例
--------------------------------
运行环境             production
日志级别             info
服务地址             http://api
端口                 8080
功能开关             true
配置文件             application.yaml
```

例如：

```
data:
  LOG_LEVEL: info
  API_URL: https://api.example.com
  FEATURE_X_ENABLED: "true"
```

------

### 11.1.3 ConfigMap 不应该保存什么

ConfigMap **不是 Secret**。

不要把下面的数据放进 ConfigMap：

```
数据库密码
JWT Secret
API Key
Access Token
私钥
TLS Private Key
```

例如：

```
data:
  DB_PASSWORD: "123456"
```

技术上可能可以这样做，但生产环境不应该这么设计。

敏感信息应该使用：

```
Secret
```

或者更成熟的外部 Secret 管理系统。

------

### 11.1.4 ConfigMap 的核心价值

ConfigMap 最重要的作用可以概括成：

```
Docker Image
     │
     │ 不包含环境相关配置
     ▼
Application
     ▲
     │
ConfigMap
```

同一个镜像：

```
myapp:v1.0.0
```

可以运行在：

```
开发环境
测试环境
生产环境
```

只是加载不同的 ConfigMap。

例如：

```
开发环境
myapp:v1.0.0
     +
app-config-dev

测试环境
myapp:v1.0.0
     +
app-config-test

生产环境
myapp:v1.0.0
     +
app-config-prod
```

这就是**配置与镜像解耦**。

------

## 11.2 环境变量

ConfigMap 最简单、最常见的使用方式之一，就是将配置注入成 Container 的环境变量。

例如 ConfigMap：

```
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
data:
  APP_ENV: production
  LOG_LEVEL: info
  API_URL: http://backend
```

Pod：

```
apiVersion: v1
kind: Pod
metadata:
  name: config-demo
spec:
  containers:
    - name: app
      image: nginx:1.27
      env:
        - name: APP_ENV
          valueFrom:
            configMapKeyRef:
              name: app-config
              key: APP_ENV

        - name: LOG_LEVEL
          valueFrom:
            configMapKeyRef:
              name: app-config
              key: LOG_LEVEL
```

Container 启动后可以看到：

```
APP_ENV=production
LOG_LEVEL=info
```

------

### 11.2.1 为什么环境变量很常用

因为大量应用本身就支持环境变量配置。

例如：

```
.NET
Spring Boot
Node.js
Go
Python
```

都可以通过环境变量读取配置。

这样 Kubernetes 只负责：

```
ConfigMap
   ↓
Environment Variable
   ↓
Application
```

而不需要理解应用内部的配置格式。

------

### 11.2.2 查看 Pod 中的环境变量

可以进入 Container：

```
kubectl exec -it config-demo -- sh
```

然后：

```
env
```

或者：

```
echo $APP_ENV
```

应该看到：

```
production
```

------

### 11.2.3 一个容易忽略的问题

ConfigMap 中的值本质上是字符串。

例如：

```
data:
  PORT: "8080"
  ENABLED: "true"
```

即使看起来像：

```
8080
true
```

对于 ConfigMap 来说仍然是字符串数据。

应用最终如何解析：

```
"8080" → int
"true" → bool
```

由应用程序自己负责。

------

## 11.3 配置文件

并不是所有应用都喜欢：

```
Environment Variable
```

有些应用使用：

```
application.yaml
application.yml
appsettings.json
config.yaml
nginx.conf
```

等配置文件。

ConfigMap 同样可以保存完整的配置文件。

例如：

```
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
data:
  application.yaml: |
    server:
      port: 8080

    logging:
      level: INFO

    redis:
      host: redis
      port: 6379
```

这里：

```
application.yaml: |
```

后面的内容就是一个完整的文件。

------

### 11.3.1 为什么配置文件方式很重要

假设应用启动时需要：

```
/etc/myapp/application.yaml
```

那么可以：

```
ConfigMap
    ↓
Volume
    ↓
/etc/myapp/application.yaml
    ↓
Application
```

这样应用就可以继续使用原来的配置文件机制。

不需要为了 Kubernetes 而大幅修改应用代码。

------

### 11.3.2 配置文件和环境变量如何选择

可以简单按照这个原则：

| 场景                 | 推荐方式     |
| -------------------- | ------------ |
| 少量简单配置         | 环境变量     |
| 大量配置             | 配置文件     |
| 应用本身使用配置文件 | Volume Mount |
| 需要不同环境配置     | ConfigMap    |
| 敏感配置             | Secret       |

实际项目中两种方式也可以同时使用。

------

## 11.4 ConfigMap YAML

### 11.4.1 基本 YAML

最简单：

```
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
data:
  APP_ENV: production
  LOG_LEVEL: info
```

应用：

```
apiVersion: apps/v1
kind: Deployment
metadata:
  name: config-demo
spec:
  replicas: 2
  selector:
    matchLabels:
      app: config-demo
  template:
    metadata:
      labels:
        app: config-demo
    spec:
      containers:
        - name: app
          image: nginx:1.27
          env:
            - name: APP_ENV
              valueFrom:
                configMapKeyRef:
                  name: app-config
                  key: APP_ENV

            - name: LOG_LEVEL
              valueFrom:
                configMapKeyRef:
                  name: app-config
                  key: LOG_LEVEL
```

------

### 11.4.2 使用 kubectl 创建 ConfigMap

也可以不用手写 YAML。

从字面量创建：

```
kubectl create configmap app-config \
  --from-literal=APP_ENV=production \
  --from-literal=LOG_LEVEL=info
```

查看：

```
kubectl get configmap app-config
```

------

### 11.4.3 从文件创建

假设有：

```
application.yaml
```

可以：

```
kubectl create configmap app-config \
  --from-file=application.yaml
```

查看：

```
kubectl get configmap app-config -o yaml
```

会看到：

```
data:
  application.yaml: |
    ...
```

------

### 11.4.4 从目录创建

例如：

```
config/
├── application.yaml
├── logging.yaml
└── feature.yaml
```

可以：

```
kubectl create configmap app-config \
  --from-file=config/
```

ConfigMap 中会包含这些文件。

------

## 11.5 `env`

`env` 用于把 ConfigMap 中的**指定配置项**注入到指定的环境变量。

例如：

```
env:
  - name: LOG_LEVEL
    valueFrom:
      configMapKeyRef:
        name: app-config
        key: LOG_LEVEL
```

这里有三个重要部分：

```
name
  ↓
Container 环境变量名称

configMapKeyRef.name
  ↓
ConfigMap 名称

configMapKeyRef.key
  ↓
ConfigMap 中的 key
```

对应关系：

```
ConfigMap

LOG_LEVEL=info
     │
     ▼
configMapKeyRef
     │
     ▼
Container

LOG_LEVEL=info
```

------

### 11.5.1 可以修改环境变量名称

例如：

```
env:
  - name: MY_LOG_LEVEL
    valueFrom:
      configMapKeyRef:
        name: app-config
        key: LOG_LEVEL
```

那么：

```
ConfigMap:
LOG_LEVEL=info
```

最终 Container：

```
MY_LOG_LEVEL=info
```

所以：

> ConfigMap 的 key 和 Container 的环境变量名称不要求相同。

------

### 11.5.2 `optional`

如果 ConfigMap 或 key 不存在，默认可能导致 Pod 无法正常创建对应容器配置。

如果希望配置不存在时允许继续运行，可以：

```
env:
  - name: LOG_LEVEL
    valueFrom:
      configMapKeyRef:
        name: app-config
        key: LOG_LEVEL
        optional: true
```

不过生产环境需要谨慎。

因为：

```
配置缺失
   ↓
应用继续启动
```

有时候比：

```
应用启动失败
```

更危险。

例如生产环境缺少：

```
DATABASE_URL
```

如果应用仍然启动，可能直到真正收到请求时才失败。

因此：

> 核心配置通常不建议随意设置 `optional: true`。

------

## 11.6 `envFrom`

如果 ConfigMap 有很多配置：

```
data:
  APP_ENV: production
  LOG_LEVEL: info
  API_URL: http://backend
  FEATURE_A: "true"
  FEATURE_B: "false"
```

逐个写：

```
env:
  - name: APP_ENV
    ...
  - name: LOG_LEVEL
    ...
  - name: API_URL
    ...
```

会比较繁琐。

这时候可以使用：

```
envFrom
```

------

### 11.6.1 基本用法

```
envFrom:
  - configMapRef:
      name: app-config
```

完整：

```
apiVersion: apps/v1
kind: Deployment
metadata:
  name: config-demo
spec:
  replicas: 2
  selector:
    matchLabels:
      app: config-demo
  template:
    metadata:
      labels:
        app: config-demo
    spec:
      containers:
        - name: app
          image: nginx:1.27
          envFrom:
            - configMapRef:
                name: app-config
```

ConfigMap：

```
data:
  APP_ENV: production
  LOG_LEVEL: info
  API_URL: http://backend
```

最终 Container 会得到：

```
APP_ENV=production
LOG_LEVEL=info
API_URL=http://backend
```

------

### 11.6.2 `env` 与 `envFrom` 的区别

可以简单理解：

```
env
 ↓
精确选择某一个 key

envFrom
 ↓
批量导入 ConfigMap
```

例如：

```
env:
  - name: LOG_LEVEL
    valueFrom:
      configMapKeyRef:
        name: app-config
        key: LOG_LEVEL
```

只导入：

```
LOG_LEVEL
```

而：

```
envFrom:
  - configMapRef:
      name: app-config
```

会批量导入 ConfigMap 中符合要求的配置项。

------

### 11.6.3 生产环境的一个注意点

`envFrom` 很方便，但也可能造成配置命名冲突。

例如：

```
ConfigMap A
LOG_LEVEL=info

ConfigMap B
LOG_LEVEL=debug
```

如果同时：

```
envFrom:
  - configMapRef:
      name: config-a
  - configMapRef:
      name: config-b
```

就可能产生覆盖和理解困难。

生产环境更推荐：

> 对核心应用配置保持明确、稳定的命名规范，不要无脑把大量 ConfigMap 全部 `envFrom`。

------

## 11.7 Volume Mount

如果应用需要配置文件，可以把 ConfigMap 挂载成 Volume。

例如：

```
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
data:
  application.yaml: |
    server:
      port: 8080
    logging:
      level: INFO
```

Pod：

```
apiVersion: v1
kind: Pod
metadata:
  name: config-file-demo
spec:
  containers:
    - name: app
      image: nginx:1.27
      volumeMounts:
        - name: config
          mountPath: /etc/myapp

  volumes:
    - name: config
      configMap:
        name: app-config
```

最终 Container 内：

```
/etc/myapp/application.yaml
```

内容来自 ConfigMap。

------

### 11.7.1 工作原理

结构：

```
ConfigMap
    │
    ▼
Pod Volume
    │
    ▼
Volume Mount
    │
    ▼
/etc/myapp/application.yaml
```

因此应用看到的是一个普通文件。

应用甚至不需要知道：

```
“这个文件来自 Kubernetes”
```

------

### 11.7.2 指定文件名

可以使用 `items`：

```
volumes:
  - name: config
    configMap:
      name: app-config
      items:
        - key: application.yaml
          path: application.yaml
```

挂载：

```
volumeMounts:
  - name: config
    mountPath: /etc/myapp
```

最终：

```
/etc/myapp/application.yaml
```

------

### 11.7.3 挂载单个配置文件

例如应用原本有：

```
/etc/myapp/appsettings.json
```

可以：

```
volumes:
  - name: config
    configMap:
      name: app-config
      items:
        - key: appsettings.json
          path: appsettings.json
```

然后：

```
volumeMounts:
  - name: config
    mountPath: /etc/myapp
```

这样就可以让 Kubernetes 提供：

```
/etc/myapp/appsettings.json
```

------

### 11.7.4 `subPath` 的重要注意事项

例如：

```
volumeMounts:
  - name: config
    mountPath: /etc/myapp/appsettings.json
    subPath: appsettings.json
```

这种方式看起来很方便，但有一个重要问题：

> **使用 `subPath` 挂载 ConfigMap 文件时，ConfigMap 后续更新不会像普通 ConfigMap Volume 那样自动反映到挂载文件。**

因此如果生产环境需要依赖 ConfigMap 的动态更新：

```
普通 ConfigMap Volume
```

通常比：

```
subPath
```

更合适。

------

## 11.8 ConfigMap 更新机制

这是 ConfigMap 最容易被误解的地方之一。

很多人会认为：

```
修改 ConfigMap
    ↓
所有 Pod 立即读取新配置
```

实际上并不是这么简单。

------

### 11.8.1 修改 ConfigMap

例如：

```
kubectl edit configmap app-config
```

或者：

```
kubectl apply -f configmap.yaml
```

把：

```
LOG_LEVEL: info
```

改成：

```
LOG_LEVEL: debug
```

ConfigMap 本身会立即更新。

但是：

> **已经注入成环境变量的 Pod，不会自动更新环境变量。**

------

### 11.8.2 为什么环境变量不会自动更新

例如：

```
ConfigMap
LOG_LEVEL=info
      │
      ▼
Pod 创建
      │
      ▼
Environment
LOG_LEVEL=info
```

之后：

```
ConfigMap
LOG_LEVEL=debug
```

已经运行的 Container 里面仍然可能是：

```
LOG_LEVEL=info
```

因为环境变量是在 Container 创建时注入的。

------

### 11.8.3 怎么让环境变量配置生效

通常需要重新创建 Pod。

例如：

```
kubectl rollout restart deployment config-demo
```

然后：

```
kubectl rollout status deployment config-demo
```

Deployment 会逐步替换旧 Pod。

新 Pod 启动时读取新的 ConfigMap：

```
ConfigMap
LOG_LEVEL=debug
      │
      ▼
新 Pod
      │
      ▼
LOG_LEVEL=debug
```

------

### 11.8.4 ConfigMap Volume 更新机制

如果 ConfigMap 是以普通 Volume 的方式挂载：

```
ConfigMap
   ↓
Volume
   ↓
文件
```

Kubernetes 通常会在 ConfigMap 更新后，将新的内容逐步反映到挂载文件。

但是存在一些重要条件和延迟：

```
ConfigMap 更新
      ↓
Kubernetes 同步
      ↓
Volume 文件更新
```

不是瞬间完成。

应用是否能看到变化，还取决于：

```
应用是否重新读取文件
```

------

### 11.8.5 文件更新 ≠ 应用自动重新加载

这是生产环境非常重要的一点。

假设：

```
ConfigMap
    ↓
/etc/myapp/application.yaml
```

ConfigMap 更新后：

```
application.yaml
```

可能已经变成新内容。

但如果应用：

```
启动时读取一次
```

之后永远不重新读取，那么：

```
文件已经更新
```

不代表：

```
应用配置已经生效
```

所以需要区分：

```
Kubernetes 配置更新
```

和：

```
应用配置热加载
```

它们是两件事情。

------

### 11.8.6 生产环境常见做法

如果应用不能自动 reload ConfigMap，最简单可靠的方式通常是：

```
更新 ConfigMap
      ↓
触发 Deployment Rolling Update
      ↓
新 Pod 启动
      ↓
读取新配置
```

也就是：

```
kubectl apply -f configmap.yaml
kubectl rollout restart deployment myapp
```

更成熟的 GitOps 环境通常会自动完成这一过程。

------

## 11.9 配置与镜像解耦

这是本章最核心的设计思想。

### 11.9.1 错误做法：配置写进镜像

例如 Dockerfile：

```
FROM myapp
COPY appsettings.production.json /app/
```

那么：

```
生产配置
    ↓
Docker Image
```

如果测试环境不同：

```
测试配置
    ↓
重新构建 Image
```

最后可能产生：

```
myapp:dev
myapp:test
myapp:prod
```

代码其实完全一样，只是配置不同。

这是非常不理想的。

------

### 11.9.2 推荐做法

镜像只包含：

```
Application
Dependencies
Runtime
```

配置由 Kubernetes 提供：

```
                    ┌── ConfigMap-dev
                    │
Application Image ──┼── ConfigMap-test
                    │
                    └── ConfigMap-prod
```

例如同一个：

```
myapp:1.0.0
```

开发环境：

```
myapp:1.0.0
+
app-config-dev
```

生产环境：

```
myapp:1.0.0
+
app-config-prod
```

这样：

> **同一个镜像可以在不同环境中运行。**

------

### 11.9.3 这对生产发布有什么意义

假设：

```
版本 v1.8.0
```

已经通过测试。

那么生产环境可以直接部署：

```
myapp:v1.8.0
```

而不需要重新编译、重新构建。

只有：

```
ConfigMap
```

根据生产环境不同而变化。

这可以减少：

```
构建差异
环境差异
发布风险
```

并提高发布的一致性。

------

## 11.10 Spring/.NET/Node.js 等应用配置实践

不同技术栈的配置机制不同，但 Kubernetes 的思想基本一致：

```
Kubernetes
     │
     ▼
ConfigMap
     │
     ├── Environment Variable
     │
     └── Config File
              │
              ▼
          Application
```

------

### 11.10.1 Spring Boot

Spring Boot 对环境变量配置支持很好。

例如配置：

```
server:
  port: 8080

logging:
  level:
    root: INFO
```

可以转换成环境变量：

```
SERVER_PORT=8080
LOGGING_LEVEL_ROOT=INFO
```

ConfigMap：

```
apiVersion: v1
kind: ConfigMap
metadata:
  name: spring-config
data:
  SERVER_PORT: "8080"
  LOGGING_LEVEL_ROOT: INFO
```

Deployment：

```
envFrom:
  - configMapRef:
      name: spring-config
```

Spring Boot 启动后即可读取。

------

### 11.10.2 Spring Boot 配置文件方式

如果项目本身依赖：

```
application.yml
```

也可以：

```
apiVersion: v1
kind: ConfigMap
metadata:
  name: spring-config
data:
  application.yml: |
    server:
      port: 8080

    logging:
      level:
        root: INFO
```

挂载：

```
volumes:
  - name: config
    configMap:
      name: spring-config

volumeMounts:
  - name: config
    mountPath: /config
```

然后让 Spring Boot 使用：

```
/config/application.yml
```

具体启动参数取决于应用本身的启动方式。

------

### 11.10.3 .NET / ASP.NET Core

.NET 应用通常支持：

```
appsettings.json
appsettings.Production.json
```

同时也支持：

```
Environment Variables
```

例如：

```
ConnectionStrings__Default
Logging__LogLevel__Default
MyApp__FeatureEnabled
```

这里需要特别注意 .NET 的配置层级映射：

```
:
```

层级通常可以使用：

```
__
```

例如：

```
MyApp
  └── Feature
       └── Enabled
```

可以通过：

```
MyApp__Feature__Enabled=true
```

注入。

apiVersion: apps/v1

## 常见生产实践

### 配置分层

不要把所有配置都堆进一个巨大的 ConfigMap：

```
app-config
  ↓
几百个配置项
```

可以根据应用和职责合理拆分：

```
app-runtime-config
app-feature-config
app-nginx-config
```

但也不要拆得过度，否则会增加管理复杂度。

------

### ConfigMap 不保存 Secret

牢记：

```
ConfigMap
    ↓
非敏感配置

Secret
    ↓
敏感配置
```

例如：

```
LOG_LEVEL
API_URL
APP_ENV
```

可以放 ConfigMap。

而：

```
DB_PASSWORD
JWT_SECRET
API_KEY
```

应该考虑 Secret。

------

### 配置变更需要考虑发布策略

不要简单认为：

```
kubectl apply -f configmap.yaml
```

就代表应用一定使用了新配置。

需要判断：

```
环境变量？
    ↓
需要重建 Pod

Volume？
    ↓
文件可能更新

应用是否支持热加载？
    ↓
决定是否需要重启
```

------

### 生产环境配置应该进入版本控制

例如 Git 仓库：

```
k8s/
├── base/
│   ├── deployment.yaml
│   └── configmap.yaml
│
├── overlays/
│   ├── dev/
│   ├── test/
│   └── prod/
```

这样：

```
配置变更
    ↓
Git
    ↓
审核
    ↓
CI/CD / GitOps
    ↓
Kubernetes
```

比直接在生产服务器执行：

```
kubectl edit configmap ...
```

更加可追踪。

## 本章核心知识

ConfigMap 可以浓缩成一句话：

> **ConfigMap 是 Kubernetes 用来保存非敏感应用配置，并将配置提供给 Pod 的机制。**

最常见的两种使用方式：

```
ConfigMap
   │
   ├──────────────┐
   ▼              ▼
env / envFrom    Volume
   │              │
   ▼              ▼
环境变量         配置文件
   │              │
   └───────┬──────┘
           ▼
       Application
```

需要特别记住：

| 知识点           | 核心结论                                |
| ---------------- | --------------------------------------- |
| ConfigMap        | 保存非敏感配置                          |
| `env`            | 精确注入指定配置                        |
| `envFrom`        | 批量注入配置                            |
| Volume Mount     | 将配置作为文件提供                      |
| 环境变量更新     | 已运行 Pod 不会自动更新                 |
| ConfigMap Volume | 文件内容通常可以随 ConfigMap 更新而变化 |
| `subPath`        | ConfigMap 更新不会自动反映到该挂载文件  |
| 配置与镜像解耦   | 同一个镜像运行不同环境                  |
| Secret           | 用于敏感信息，不应使用 ConfigMap 代替   |
| 生产环境         | 配置应该可审计、可版本控制、可自动发布  |

最终形成这样的生产思维：

```
                 Docker Image
              Application + Runtime
                       │
                       │
             ┌─────────┴─────────┐
             │                   │
             ▼                   ▼
        ConfigMap             Secret
       非敏感配置             敏感配置
             │                   │
             └─────────┬─────────┘
                       ▼
                      Pod
                       │
              ┌────────┴────────┐
              ▼                 ▼
         Environment         Config Files
              │                 │
              └────────┬────────┘
                       ▼
                  Application
```

其中最重要的生产原则是：

> **镜像负责“运行什么”，ConfigMap 负责“怎么运行”，Secret 负责“敏感信息是什么”。**

# 第 12 章：Secret——管理敏感信息

上一章我们学习了 ConfigMap，它解决的是：

> **如何把非敏感配置从应用镜像中分离出来。**

但是生产环境还有一类更加重要的数据：

```
数据库密码
Redis 密码
JWT Secret
API Key
OAuth Client Secret
TLS 私钥
Docker Registry 凭证
```

这些数据不能简单按照普通配置处理。

Kubernetes 提供了 **Secret** 对象。

------

## 12.1 Secret 是什么

### 12.1.1 Secret 的定义

Secret 是 Kubernetes 用来保存和向 Pod 提供**敏感数据**的一种 API 对象。

最简单的 Secret：

```
apiVersion: v1
kind: Secret
metadata:
  name: app-secret
type: Opaque
stringData:
  DB_USERNAME: app
  DB_PASSWORD: my-password
```

创建：

```
kubectl apply -f secret.yaml
```

查看：

```
kubectl get secret
```

查看详细信息：

```
kubectl describe secret app-secret
```

注意：

```
kubectl get secret app-secret -o yaml
```

仍然可以看到经过 Base64 编码的数据。

这意味着：

> **Secret 并不等于“加密后的密码”。**

后面会专门解释这一点。

------

### 12.1.2 Secret 的核心用途

Secret 的作用主要是：

```
Secret
   │
   ├── 环境变量
   │
   ├── Volume 文件
   │
   ├── Docker Registry 认证
   │
   └── TLS Certificate
```

例如：

```
             Secret
                │
       ┌────────┼────────┐
       ▼        ▼        ▼
   Env Var    Volume    Registry
       │        │        │
       ▼        ▼        ▼
   Application TLS      Image Pull
```

------

### 12.1.3 Secret 与应用的关系

Secret 并不会自动改变应用行为。

Kubernetes 只是负责：

> **保存 Secret，并把 Secret 提供给 Pod。**

应用仍然需要自己读取。

例如：

```
Secret
DB_PASSWORD=123456
       │
       ▼
Environment Variable
       │
       ▼
Application
       │
       ▼
process.env.DB_PASSWORD
```

或者：

```
Secret
   │
   ▼
Volume
   │
   ▼
/etc/secrets/password
   │
   ▼
Application
```

------

## 12.2 Secret 与 ConfigMap 的区别

两者的使用模型非常类似：

```
ConfigMap ──→ Pod
Secret ─────→ Pod
```

但语义不同。

| 项目             | ConfigMap | Secret             |
| ---------------- | --------- | ------------------ |
| 主要用途         | 普通配置  | 敏感数据           |
| 密码             | ❌         | ✅                  |
| API Key          | ❌         | ✅                  |
| TLS 私钥         | ❌         | ✅                  |
| 普通 URL         | ✅         | 可以，但通常没必要 |
| 日志级别         | ✅         | ❌                  |
| 环境变量         | ✅         | ✅                  |
| Volume           | ✅         | ✅                  |
| 默认 Base64 表示 | 是        | 是                 |
| Base64 是否加密  | 否        | **也不是**         |

最重要的区别不是：

```
ConfigMap = 明文
Secret = 加密
```

这是错误理解。

更准确地说：

```
ConfigMap
    ↓
普通配置

Secret
    ↓
敏感配置
```

Secret 在 Kubernetes 中具有专门的语义，并可以配合 Kubernetes 的安全机制和外部 Secret 管理系统使用。

------

## 12.3 Secret 类型

Secret 并不只有一种用途。

Kubernetes 提供了一些内置 Secret 类型：

```
Opaque
kubernetes.io/dockerconfigjson
kubernetes.io/tls
kubernetes.io/basic-auth
kubernetes.io/ssh-auth
kubernetes.io/service-account-token
```

其中生产环境最常遇到的是：

```
Opaque
Docker Registry Secret
TLS Secret
```

------

### 12.3.1 Secret 类型的意义

Secret 的 `type` 用于告诉 Kubernetes：

> **这个 Secret 保存的是什么类型的数据。**

例如：

```
type: Opaque
```

表示普通自定义 Secret。

而：

```
type: kubernetes.io/tls
```

表示 TLS 证书 Secret。

------

## 12.4 `Opaque`

### 12.4.1 什么是 Opaque

`Opaque` 是最常见的通用 Secret 类型。

例如：

```
apiVersion: v1
kind: Secret
metadata:
  name: database-secret
type: Opaque
stringData:
  username: app
  password: my-password
```

这里：

```
username
password
```

完全由你的应用定义。

Kubernetes 不会要求：

```
必须叫 password
```

你可以定义：

```
stringData:
  DB_PASSWORD: xxx
  REDIS_PASSWORD: xxx
  JWT_SECRET: xxx
```

------

### 12.4.2 `data` 和 `stringData`

Secret 最容易遇到的两个字段：

```
data:
```

和：

```
stringData:
```

#### `data`

要求数据使用 Base64：

```
apiVersion: v1
kind: Secret
metadata:
  name: app-secret
type: Opaque
data:
  username: YXBw
  password: bXktcGFzc3dvcmQ=
```

例如：

```
echo -n 'app' | base64
```

得到：

```
YXBw
```

------

#### `stringData`

可以直接写字符串：

```
apiVersion: v1
kind: Secret
metadata:
  name: app-secret
type: Opaque
stringData:
  username: app
  password: my-password
```

Kubernetes API Server 会处理它。

对于手写 YAML 来说：

> **通常更推荐使用 `stringData`，避免自己手工进行 Base64 编码。**

------

### 12.4.3 为什么不建议手工 Base64

因为这样：

```
echo -n 'my-password' | base64
```

然后：

```
data:
  password: bXktcGFzc3dvcmQ=
```

容易让人误以为：

```
Base64 = 加密
```

实际上只是编码。

所以开发和运维过程中：

```
stringData:
```

通常更加直观。

------

## 12.5 Docker Registry Secret

在生产环境中，经常会使用私有 Docker Registry：

```
Harbor
GitHub Container Registry
GitLab Container Registry
云厂商镜像仓库
企业内部 Registry
```

例如：

```
registry.example.com/myteam/myapp:1.0.0
```

Kubernetes 节点拉取这个镜像时，需要认证。

这时就需要：

```
imagePullSecrets
```

------

### 12.5.1 创建 Registry Secret

例如：

```
kubectl create secret docker-registry registry-secret \
  --docker-server=registry.example.com \
  --docker-username=myuser \
  --docker-password='mypassword' \
  --docker-email='admin@example.com'
```

查看：

```
kubectl get secret registry-secret
```

类型应该是：

```
kubernetes.io/dockerconfigjson
```

------

### 12.5.2 Deployment 使用 Registry Secret

```
apiVersion: apps/v1
kind: Deployment
metadata:
  name: private-app
spec:
  replicas: 2
  selector:
    matchLabels:
      app: private-app

  template:
    metadata:
      labels:
        app: private-app

    spec:
      imagePullSecrets:
        - name: registry-secret

      containers:
        - name: app
          image: registry.example.com/myteam/myapp:1.0.0
```

工作流程：

```
Pod
 │
 │ imagePull
 ▼
Node
 │
 │ authentication
 ▼
Private Registry
 │
 ▼
Container Image
```

------

### 12.5.3 常见问题

如果 Secret 配置错误，Pod 可能出现：

```
ImagePullBackOff
ErrImagePull
```

查看：

```
kubectl describe pod <pod-name>
```

重点查看 Events。

例如：

```
Failed to pull image
unauthorized
authentication required
```

通常检查：

```
Registry 地址
用户名
密码
Secret 类型
imagePullSecrets
```

## 12.6 TLS Secret

HTTPS 是生产环境的基本要求。

例如：

```
https://api.example.com
```

服务器通常需要：

```
TLS Certificate
Private Key
```

Kubernetes 可以使用：

```
kubernetes.io/tls
```

类型的 Secret 保存它们。

------

### 12.6.1 TLS Secret 结构

典型 TLS Secret：

```
apiVersion: v1
kind: Secret
metadata:
  name: example-tls
type: kubernetes.io/tls
data:
  tls.crt: <base64-certificate>
  tls.key: <base64-private-key>
```

两个关键字段：

```
tls.crt
    ↓
证书

tls.key
    ↓
私钥
```

------

### 12.6.2 使用 kubectl 创建 TLS Secret

假设已有：

```
tls.crt
tls.key
```

可以：

```
kubectl create secret tls example-tls \
  --cert=tls.crt \
  --key=tls.key
```

查看：

```
kubectl get secret example-tls
```

------

### 12.6.3 Ingress 使用 TLS Secret

例如：

```
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: app-ingress
spec:
  tls:
    - hosts:
        - api.example.com
      secretName: example-tls

  rules:
    - host: api.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: api-service
                port:
                  number: 80
```

流量：

```
用户
 │
 │ HTTPS
 ▼
Ingress Controller
 │
 │ TLS Certificate
 ▼
Service
 │
 ▼
Pod
```

这里的：

```
example-tls
```

就是 Secret。

------

## 12.7 Secret 环境变量

这是应用使用 Secret 最常见的方式之一。

例如：

```
apiVersion: v1
kind: Secret
metadata:
  name: database-secret
type: Opaque
stringData:
  DB_USERNAME: app
  DB_PASSWORD: my-password
```

Deployment：

```
apiVersion: apps/v1
kind: Deployment
metadata:
  name: database-client
spec:
  replicas: 2

  selector:
    matchLabels:
      app: database-client

  template:
    metadata:
      labels:
        app: database-client

    spec:
      containers:
        - name: app
          image: myapp:1.0.0

          env:
            - name: DB_USERNAME
              valueFrom:
                secretKeyRef:
                  name: database-secret
                  key: DB_USERNAME

            - name: DB_PASSWORD
              valueFrom:
                secretKeyRef:
                  name: database-secret
                  key: DB_PASSWORD
```

------

### 12.7.1 `secretKeyRef`

结构和 ConfigMap 的：

```
configMapKeyRef
```

非常类似。

Secret：

```
valueFrom:
  secretKeyRef:
    name: database-secret
    key: DB_PASSWORD
```

ConfigMap：

```
valueFrom:
  configMapKeyRef:
    name: app-config
    key: LOG_LEVEL
```

可以记成：

```
ConfigMap → configMapKeyRef

Secret    → secretKeyRef
```

------

### 12.7.2 `envFrom`

Secret 也支持：

```
envFrom:
  - secretRef:
      name: database-secret
```

例如：

```
containers:
  - name: app
    image: myapp:1.0.0
    envFrom:
      - secretRef:
          name: database-secret
```

那么：

```
DB_USERNAME
DB_PASSWORD
```

都会被注入。

生产环境需要注意命名冲突问题，因此对于核心 Secret，精确的 `secretKeyRef` 往往更加清晰。

------

### 12.7.3 应用中的读取

Node.js：

```
const password = process.env.DB_PASSWORD;
```

.NET：

```
var password = builder.Configuration["DB_PASSWORD"];
```

Spring Boot：

```
DB_PASSWORD
```

可以通过 Spring 的 Environment / Configuration 机制读取。

因此 Kubernetes 本身不需要知道应用是什么语言。

------

## 12.8 Secret Volume

Secret 除了环境变量，还可以作为文件挂载。

例如：

```
apiVersion: v1
kind: Secret
metadata:
  name: app-secret
type: Opaque
stringData:
  username: app
  password: my-password
```

Pod：

```
apiVersion: v1
kind: Pod
metadata:
  name: secret-demo
spec:
  containers:
    - name: app
      image: nginx:1.27

      volumeMounts:
        - name: secret
          mountPath: /etc/secrets
          readOnly: true

  volumes:
    - name: secret
      secret:
        secretName: app-secret
```

Container 内：

```
/etc/secrets/
├── username
└── password
```

读取：

```
cat /etc/secrets/username
```

输出：

```
app
```

------

### 12.8.1 Secret Volume 的工作原理

可以理解为：

```
Secret
   │
   ▼
Kubernetes Volume
   │
   ▼
/etc/secrets
   │
   ├── username
   └── password
```

每一个 Secret key 默认对应一个文件。

例如：

```
stringData:
  username: app
  password: my-password
```

对应：

```
username → /etc/secrets/username
password → /etc/secrets/password
```

------

### 12.8.2 为什么有时候更适合使用 Volume

有些软件要求：

```
私钥文件
证书文件
认证文件
配置文件
```

例如：

```
TLS private key
SSH key
Cloud credential file
```

这时候：

```
Secret → Volume
```

比环境变量更加自然。

------

### 12.8.3 Secret Volume 默认权限

Secret Volume 中的文件默认具有受限制的权限设置，但生产环境仍然需要结合：

```
securityContext
runAsUser
fsGroup
容器用户权限
```

进行整体设计。

不要因为：

```
“这是 Secret”
```

就认为 Container 内任何进程都无法读取它。

如果某个进程能够访问对应文件，它就可能读取 Secret。

------

## 12.9 Secret 的安全问题

这是本章非常重要的部分。

很多初学者认为：

```
Secret
    ↓
安全
```

这是错误的。

更准确的理解是：

> Secret 是 Kubernetes 中专门用于敏感数据的对象，但它本身不是完整的 Secret 管理系统。

------

### 12.9.1 RBAC 权限非常重要

假设某个用户拥有：

```
get secrets
```

那么他可能直接读取 Secret。

例如：

```
kubectl get secret database-secret -o yaml
```

然后进一步解码。

所以生产环境必须认真控制：

```
谁可以读取 Secret？
哪个 ServiceAccount 可以读取？
哪个 Namespace 可以读取？
```

------

### 12.9.2 不要给过大的权限

例如不应该轻易给普通应用：

```
verbs:
  - "*"
resources:
  - "*"
```

特别是：

```
secrets
```

应该谨慎授权。

遵循：

> **Least Privilege（最小权限原则）**

例如一个应用只需要读取：

```
database-secret
```

就不应该允许它读取整个 Namespace 的所有 Secret。

------

### 12.9.3 Secret 可能出现在日志中

例如程序：

```
console.log(process.env);
```

可能把：

```
DB_PASSWORD
API_KEY
JWT_SECRET
```

打印出来。

或者：

```
启动日志
配置加载日志
异常堆栈
Debug 日志
```

都有可能泄漏 Secret。

因此生产环境应该：

```
避免打印敏感环境变量
避免把 Secret 写入日志
避免异常信息暴露 Secret
```

------

### 12.9.4 Secret 可能出现在 CI/CD 中

例如：

```
kubectl create secret generic app-secret \
  --from-literal=password=MyPassword123
```

如果把命令直接放到某些 CI/CD 日志中：

```
Command
    ↓
CI Log
    ↓
Password 泄漏
```

因此 CI/CD 中应该使用：

```
Secret Variables
Credential Store
External Secret Manager
```

而不是把密码硬编码到脚本中。

------

### 12.9.5 Git 中不要提交真正的 Secret

例如：

```
stringData:
  DB_PASSWORD: "production-password"
```

如果提交到：

```
Git
```

就意味着：

```
Git History
    ↓
永久留下密码痕迹
```

即使后来删除文件：

```
Git commit history
```

仍然可能保留。

生产环境应该使用：

```
External Secret Manager
Sealed Secrets
SOPS
Vault
云 Secret Manager
```

等方案。

------

## 12.10 Base64 ≠ 加密

这是 Kubernetes Secret 最重要的认知之一。

假设：

```
password
```

Base64 编码：

```
echo -n 'password' | base64
```

得到：

```
cGFzc3dvcmQ=
```

反编码：

```
echo 'cGFzc3dvcmQ=' | base64 -d
```

立即得到：

```
password
```

所以：

```
Base64
    ↓
Encoding
```

而不是：

```
Base64
    ↓
Encryption
```

------

### 12.10.1 Kubernetes Secret 中为什么使用 Base64

例如：

```
data:
  password: cGFzc3dvcmQ=
```

Base64 的主要作用是：

> **让任意二进制数据能够以字符串形式通过 Kubernetes API/YAML 传输。**

它不是为了提供安全性。

例如 TLS：

```
证书
私钥
```

都是二进制/文本数据，需要一种统一的数据表达方式。

------

### 12.10.2 Secret 真正的安全边界在哪里

需要综合考虑：

```
RBAC
API Server
etcd
Encryption at Rest
TLS
Node 权限
Container 权限
日志
CI/CD
Git
Secret Manager
```

尤其重要的是：

```
etcd
```

Kubernetes 的 API 对象最终需要持久化。

生产集群应该考虑：

> **对 Secret 在 etcd 中进行静态加密（Encryption at Rest）。**

否则不能简单认为：

```
Secret 对象
    ↓
已经安全加密
```

------

## 12.11 生产环境 Secret 管理

生产环境真正需要解决的不是：

> “怎么创建一个 Secret？”

而是：

> **如何安全地创建、存储、分发、轮换、审计和撤销 Secret？**

------

### 12.11.1 基础方案

小规模环境可能直接使用：

```
Kubernetes Secret
+
RBAC
+
etcd Encryption at Rest
```

例如：

```
Developer
    │
    ▼
CI/CD
    │
    ▼
Kubernetes API
    │
    ▼
Secret
    │
    ▼
Pod
```

这种方式可以工作。

------

### 12.11.2 更成熟的方案

生产环境通常会进一步引入：

```
External Secret Manager
```

例如：

```
HashiCorp Vault
AWS Secrets Manager
Azure Key Vault
Google Secret Manager
```

然后：

```
Secret Manager
       │
       ▼
External Secrets
       │
       ▼
Kubernetes Secret
       │
       ▼
Pod
```

这样 Kubernetes 不再成为唯一的 Secret 来源。

------

### 12.11.3 Secret Rotation

假设生产数据库密码：

```
old-password
```

长期不变是一个安全风险。

更合理的是：

```
old-password
      ↓
rotation
      ↓
new-password
```

例如：

```
数据库密码
   │
   ▼
Secret Manager
   │
   ▼
Kubernetes Secret
   │
   ▼
Application
```

轮换时还要考虑：

```
旧密码什么时候失效？
应用什么时候重新读取？
Pod 是否需要重启？
连接池如何刷新？
```

所以 Secret Rotation 不只是：

```
kubectl edit secret
```

而是一个完整的生产运维流程。

------

### 12.11.4 不同环境使用不同 Secret

不要这样：

```
开发环境
      │
      ▼
生产数据库密码
```

应该：

```
Development
   ↓
dev secrets

Test
   ↓
test secrets

Production
   ↓
production secrets
```

不同环境应该具有独立的权限边界。

------

### 12.11.5 生产环境的基本原则

可以总结为：

```
1. 不提交 Secret 到 Git
2. 使用 RBAC 限制读取权限
3. 开启 etcd Encryption at Rest
4. 避免 Secret 出现在日志
5. CI/CD 使用安全凭证管理
6. 定期轮换敏感凭证
7. 不同环境使用不同 Secret
8. 优先考虑外部 Secret Manager
9. 遵循最小权限原则
10. 对 Secret 读取进行审计
```

------

## 12.12 External Secrets / Vault 的基本认知

当 Kubernetes Secret 管理需求变复杂以后，可以引入专门的 Secret 管理系统。

这里需要理解两个概念：

```
External Secrets
Vault
```

它们不是完全相同的东西。

------

### 12.12.1 External Secrets 是什么

External Secrets Operator（ESO）可以理解为：

> **负责把外部 Secret 管理系统中的 Secret 同步到 Kubernetes Secret。**

例如：

```
AWS Secrets Manager
        │
        │
        ▼
External Secrets Operator
        │
        ▼
Kubernetes Secret
        │
        ▼
Pod
```

外部系统保存：

```
DB_PASSWORD=xxx
```

Kubernetes 中最终可能得到：

```
apiVersion: v1
kind: Secret
metadata:
  name: database-secret
```

应用仍然可以使用普通 Kubernetes Secret。

------

### 12.12.2 为什么需要 External Secrets

如果所有 Secret 都直接写：

```
kind: Secret
stringData:
  DB_PASSWORD: ...
```

就会产生：

```
Git
   ↓
Kubernetes Secret
```

问题是 Secret 可能进入 Git。

External Secrets 的思路变成：

```
Git
  ↓
ExternalSecret 配置
  ↓
External Secret Manager
  ↓
Kubernetes Secret
  ↓
Pod
```

Git 中保存的是：

```
“我要哪个 Secret”
```

而不是：

```
“Secret 的实际密码是什么”
```

------

### 12.12.3 Vault 是什么

HashiCorp Vault 是一个专门用于 Secret 管理和安全凭证管理的系统。

它可以负责：

```
Secret Storage
Secret Access Control
Secret Rotation
Dynamic Credentials
Audit
Encryption
```

架构可以理解成：

```
                  Vault
                   │
        ┌──────────┼──────────┐
        ▼          ▼          ▼
    DB Secret   API Key    Dynamic Credential
        │
        ▼
 Kubernetes / Application
```

------

### 12.12.4 Vault 与 Kubernetes

Vault 可以和 Kubernetes 身份认证机制结合。

例如：

```
Pod
 │
 │ Kubernetes ServiceAccount
 ▼
Vault
 │
 │ Authentication
 ▼
Secret
```

这样应用可以根据自己的 Kubernetes 身份获取对应 Secret。

这比：

```
所有应用共享一个超级密码
```

安全得多。

------

### 12.12.5 External Secrets 与 Vault 的关系

可以把它们理解成不同层次：

```
Secret Manager
    │
    ├── Vault
    ├── AWS Secrets Manager
    ├── Azure Key Vault
    └── Google Secret Manager
```

而：

```
External Secrets Operator
```

更像一个：

```
Kubernetes ↔ External Secret Manager
```

之间的桥梁。

例如：

```
AWS Secrets Manager
        │
        ▼
External Secrets Operator
        │
        ▼
Kubernetes Secret
        │
        ▼
Pod
```

或者：

```
Vault
  │
  ▼
External Secrets Operator
  │
  ▼
Kubernetes Secret
  │
  ▼
Pod
```

------

### 12.12.6 什么时候需要 External Secrets / Vault

并不是所有集群一开始就需要 Vault。

可以按照规模理解：

```
学习环境
    ↓
Kubernetes Secret

小型生产环境
    ↓
Kubernetes Secret
+ RBAC
+ Encryption at Rest

中大型生产环境
    ↓
External Secret Manager
+ External Secrets / Vault

高安全要求
    ↓
专门 Secret Management
+ Rotation
+ Audit
+ Dynamic Credentials
+ 最小权限
```

核心不是：

> “生产环境一定要上 Vault。”

而是：

> **Secret 的生命周期和安全要求达到一定复杂度后，应该把 Secret 管理从 Kubernetes 本身进一步独立出来。**

------

## 本章核心知识

Secret 最重要的知识可以归纳成下面这张图：

```
                         Secret
                            │
             ┌──────────────┼──────────────┐
             ▼              ▼              ▼
          Opaque       Docker Registry      TLS
             │              │              │
             ▼              ▼              ▼
        Application      Image Pull       HTTPS
             │
       ┌─────┴─────┐
       ▼           ▼
 Environment     Volume
       │           │
       ▼           ▼
    Application  Secret Files
```

需要牢牢记住：

| 知识点             | 核心结论                                |
| ------------------ | --------------------------------------- |
| Secret             | Kubernetes 中用于敏感数据的对象         |
| ConfigMap          | 普通配置                                |
| Opaque             | 最常见的通用 Secret 类型                |
| Registry Secret    | 用于私有镜像仓库认证                    |
| TLS Secret         | 保存 TLS 证书和私钥                     |
| `secretKeyRef`     | 精确注入 Secret                         |
| `secretRef`        | 批量注入 Secret                         |
| Secret Volume      | 将 Secret 作为文件提供给 Pod            |
| Base64             | **编码，不是加密**                      |
| RBAC               | 限制谁可以读取 Secret                   |
| Encryption at Rest | 保护 Secret 在 etcd 中的静态数据        |
| Secret Rotation    | 定期更换凭证                            |
| External Secrets   | 将外部 Secret Manager 同步到 Kubernetes |
| Vault              | 专业的 Secret 管理平台                  |

最终建立正确的生产思维：

```
                 Secret Management
                        │
        ┌───────────────┼────────────────┐
        ▼               ▼                ▼
   Kubernetes       External          Vault /
     Secret         Secret Manager     Secret System
        │               │                │
        └───────────────┼────────────────┘
                        ▼
                       Pod
                        │
                ┌───────┴───────┐
                ▼               ▼
           Environment       Volume
                │               │
                └───────┬───────┘
                        ▼
                   Application
```

**最关键的一句话：**

> **Kubernetes Secret 是“敏感数据的 Kubernetes 对象”，而不是“自动加密的密码保险箱”。**

生产环境真正的 Secret 安全，需要同时依赖 **RBAC、etcd 静态加密、最小权限、审计、Secret Rotation，以及必要时的 External Secret Manager / Vault**。

# 第 13 章：Kubernetes 存储

前面学习 Deployment、StatefulSet、ConfigMap 和 Secret 时，我们一直在处理一个核心问题：

```
Pod
 └── Container
```

但是 Container 有一个非常明显的特点：

> **Container 本身并不适合承担持久化数据存储的职责。**

例如数据库：

```
MySQL
PostgreSQL
Redis
```

如果数据库直接把数据写在 Container 的文件系统里，那么一旦 Container 被删除、重建或者迁移到其他 Node，就可能遇到严重的数据问题。

因此 Kubernetes 提供了一整套存储体系：

```
Pod
 │
 ├── Volume
 │
 └── PersistentVolume
          │
          ▼
   实际存储系统
   ├── 云盘
   ├── NAS
   ├── Ceph
   └── 其他存储
```

本章的重点不是记住各种 YAML，而是建立一个非常重要的生产思维：

> **Pod 是临时的，数据通常不是。**

------

## 13.1 Container 为什么不适合直接保存数据

### 13.1.1 Container 文件系统的特点

一个 Container 启动以后，会拥有自己的文件系统。

例如：

```
Container
└── /
    ├── app/
    ├── etc/
    ├── tmp/
    └── data/
```

应用可以直接写：

```
/data/user.db
```

看起来完全没问题。

但是 Container 的生命周期和数据的生命周期并不一定相同。

------

### 13.1.2 Container 删除后怎么办

例如：

```
Container A
    │
    ├── /data/a.db
    └── /data/b.db
```

如果 Container 被删除：

```
Container A
    ↓
删除
```

它自己的可写层也会随之消失。

于是：

```
/data/a.db
/data/b.db
```

也可能随之消失。

------

### 13.1.3 Kubernetes 中 Pod 会经常变化

这是生产环境必须接受的事实。

例如 Deployment：

```
Pod A
   ↓
运行中
```

因为：

```
升级
Node 故障
Pod 崩溃
扩缩容
调度变化
```

可能变成：

```
Pod A
   ↓
删除

Pod B
   ↓
重新创建
```

Pod B 并不是 Pod A。

即使：

```
Deployment
replicas: 1
```

也不能认为：

```
Pod 永远不变
```

------

### 13.1.4 数据和计算应该解耦

生产环境更合理的架构：

```
                 Application
                     │
                     ▼
                    Pod
                     │
                     │
                     ▼
                  Volume
                     │
                     ▼
              Persistent Storage
                     │
        ┌────────────┼────────────┐
        ▼            ▼            ▼
       云盘          NAS          Ceph
```

这样：

```
Pod
```

可以被删除、重建。

而：

```
Data
```

继续存在。

------

### 13.1.5 什么数据可以直接放 Container

并不是 Container 文件系统完全不能用。

例如：

```
/tmp
缓存
临时计算文件
临时下载文件
程序运行时生成的临时数据
```

这些数据本身就不要求长期保存。

但：

```
数据库文件
用户上传文件
业务核心数据
订单数据
持久化日志
```

通常不应该只依赖 Container 文件系统。

------

## 13.2 Volume

### 13.2.1 Volume 是什么

Volume 是 Kubernetes 提供给 Pod 使用的存储抽象。

Pod 可以声明：

```
“我需要一个 Volume”
```

Container 再把它挂载到：

```
/data
```

例如：

```
apiVersion: v1
kind: Pod
metadata:
  name: volume-demo
spec:
  containers:
    - name: app
      image: nginx:1.27
      volumeMounts:
        - name: data
          mountPath: /data

  volumes:
    - name: data
      emptyDir: {}
```

这里：

```
volumes
```

定义 Volume。

而：

```
volumeMounts
```

定义 Container 把它挂在哪里。

------

### 13.2.2 Volume 的工作原理

可以理解成：

```
Pod
 │
 ├── Container
 │      │
 │      └── /data
 │
 └── Volume
        │
        ▼
      Storage
```

Container 看到：

```
/data
```

实际上这个目录来自：

```
Volume
```

------

### 13.2.3 Volume 和 Container 文件系统的区别

Container 文件系统：

```
Container
   │
   └── Writable Layer
```

Volume：

```
Container
   │
   ▼
Volume
   │
   ▼
独立存储
```

因此 Volume 可以让数据生命周期与 Container 解耦。

------

### 13.2.4 Volume 的生命周期

Kubernetes 中 Volume 的生命周期通常和 Pod 有关。

例如：

```
Pod
 │
 └── emptyDir
```

Pod 被删除：

```
Pod
 ↓
Volume 删除
```

但不同 Volume 类型的行为完全不同。

所以不能简单说：

> “Volume 一定会保留数据。”

必须看具体 Volume 类型。

------

## 13.3 `emptyDir`

### 13.3.1 什么是 emptyDir

`emptyDir` 是 Kubernetes 最简单的 Volume 类型之一。

例如：

```
volumes:
  - name: cache
    emptyDir: {}
```

Pod 创建时：

```
Pod
 ↓
创建 emptyDir
```

Pod 中的 Container 可以使用：

```
/cache
```

------

### 13.3.2 emptyDir 的主要用途

非常适合：

```
临时文件
缓存
Container 之间共享文件
构建过程临时目录
应用运行时临时数据
```

例如一个 Pod 有两个 Container：

```
Pod
├── Container A
│
└── Container B
```

它们可以共享：

```
emptyDir
```

架构：

```
Container A
     │
     ▼
 /shared
     ▲
     │
Container B
```

------

### 13.3.3 示例

```
apiVersion: v1
kind: Pod
metadata:
  name: emptydir-demo
spec:
  containers:
    - name: writer
      image: busybox:1.36
      command:
        - sh
        - -c
        - |
          while true; do
            date >> /shared/data.txt
            sleep 5
          done
      volumeMounts:
        - name: shared
          mountPath: /shared

    - name: reader
      image: busybox:1.36
      command:
        - sh
        - -c
        - |
          while true; do
            cat /shared/data.txt
            sleep 10
          done
      volumeMounts:
        - name: shared
          mountPath: /shared

  volumes:
    - name: shared
      emptyDir: {}
```

两个 Container 访问的是同一个：

```
/shared
```

------

### 13.3.4 Pod 删除后怎么办

`emptyDir` 的重要特点：

> **Pod 被删除后，emptyDir 中的数据也会被删除。**

例如：

```
Pod A
 │
 └── emptyDir
       └── data
```

Pod A 删除：

```
Pod A
 ↓
删除
 ↓
emptyDir 删除
 ↓
data 消失
```

所以：

> `emptyDir` 不能用于真正的持久化业务数据。

------

### 13.3.5 emptyDir 的内存模式

还可以：

```
emptyDir:
  medium: Memory
```

这意味着使用：

```
tmpfs
```

把数据放在内存中。

适合：

```
临时高速缓存
临时敏感文件
高性能临时数据
```

但必须注意：

> 它会消耗 Node/Pod 可用内存，因此生产环境必须控制容量。

可以设置：

```
emptyDir:
  medium: Memory
  sizeLimit: 256Mi
```

------

## 13.4 `hostPath`

### 13.4.1 什么是 hostPath

`hostPath` 是直接使用 Node 主机上的目录。

例如：

```
volumes:
  - name: host-data
    hostPath:
      path: /data/app
      type: DirectoryOrCreate
```

Container：

```
volumeMounts:
  - name: host-data
    mountPath: /data
```

关系：

```
Node
└── /data/app
       ▲
       │
       ▼
Container
└── /data
```

------

### 13.4.2 为什么 hostPath 有风险

假设 Pod 当前运行：

```
Node A
```

数据：

```
Node A
└── /data/app
```

如果 Pod 被调度到：

```
Node B
```

那么：

```
Node B
└── /data/app
```

可能是另外一份数据，甚至根本不存在。

因此：

> `hostPath` 强依赖具体 Node。

------

### 13.4.3 hostPath 什么时候使用

生产环境中不建议拿它作为普通业务数据库的持久化方案。

但是它仍然有实际用途：

```
Node 日志
Node 级 Agent
监控 Agent
系统级组件
容器运行时相关数据
特殊本地存储场景
```

例如：

```
DaemonSet
    ↓
每个 Node
    ↓
读取 Node 上的日志目录
```

这时 `hostPath` 非常常见。

------

### 13.4.4 hostPath 的生产风险

主要包括：

```
Node 强绑定
数据隔离困难
权限风险
安全风险
调度困难
Node 故障导致数据不可用
```

因此如果只是想：

> “给应用一个持久化磁盘。”

通常应该优先考虑：

```
PVC
```

而不是直接使用：

```
hostPath
```

------

## 13.5 PersistentVolume

前面的：

```
emptyDir
hostPath
```

对于生产持久化场景都存在明显限制。

Kubernetes 提供了：

> **PersistentVolume（PV）**

------

### 13.5.1 PV 是什么

PersistentVolume 是 Kubernetes 集群中的一块**持久化存储资源**。

可以把它理解成：

```
PV
 ↓
“集群里有一块可用于持久化数据的存储”
```

例如：

```
PV
容量：100Gi
访问模式：ReadWriteOnce
StorageClass：fast
```

------

### 13.5.2 PV 与实际存储

PV 本身是 Kubernetes 对存储的抽象。

背后可能是真正的：

```
云硬盘
NAS
Ceph
本地磁盘
其他 CSI 存储
```

结构：

```
Kubernetes
     │
     ▼
PersistentVolume
     │
     ▼
实际 Storage
```

------

### 13.5.3 静态创建 PV

早期 Kubernetes 中可以手工创建：

```
apiVersion: v1
kind: PersistentVolume
metadata:
  name: pv-demo
spec:
  capacity:
    storage: 10Gi

  accessModes:
    - ReadWriteOnce

  persistentVolumeReclaimPolicy: Retain

  hostPath:
    path: /data/pv-demo
```

查看：

```
kubectl get pv
```

可能看到：

```
NAME       CAPACITY   ACCESS MODES   STATUS      CLAIM
pv-demo    10Gi       RWO            Available
```

------

### 13.5.4 生产环境不应该大量手工创建 PV

在现代 Kubernetes 环境中，更常见的是：

```
PVC
 ↓
StorageClass
 ↓
Dynamic Provisioning
 ↓
CSI
 ↓
真实存储
```

也就是自动创建 PV。

因此理解 PV 很重要，但生产环境通常不希望运维人员每天手工创建大量 PV。

------

## 13.6 PersistentVolumeClaim

### 13.6.1 PVC 是什么

PVC，也就是 PersistentVolumeClaim，可以理解为：

> **Pod/应用对持久化存储提出的申请。**

PV：

```
“我有 100Gi 存储。”
```

PVC：

```
“我需要 20Gi 存储。”
```

------

### 13.6.2 PV 和 PVC 的关系

可以理解为：

```
              Storage
                 │
                 ▼
                 PV
                 ▲
                 │ Bind
                 │
                 ▼
                PVC
                 ▲
                 │
                 ▼
                Pod
```

即：

```
Pod
 ↓
PVC
 ↓
PV
 ↓
Storage
```

------

### 13.6.3 PVC 示例

```
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: app-data
spec:
  accessModes:
    - ReadWriteOnce

  resources:
    requests:
      storage: 10Gi
```

查看：

```
kubectl get pvc
```

可能看到：

```
NAME       STATUS   VOLUME     CAPACITY   ACCESS MODES
app-data   Bound    pv-demo    10Gi       RWO
```

------

### 13.6.4 Pod 使用 PVC

```
apiVersion: v1
kind: Pod
metadata:
  name: pvc-demo
spec:
  containers:
    - name: app
      image: nginx:1.27
      volumeMounts:
        - name: data
          mountPath: /data

  volumes:
    - name: data
      persistentVolumeClaim:
        claimName: app-data
```

最终：

```
Pod
 │
 ▼
PVC
 │
 ▼
PV
 │
 ▼
实际存储
```

Container 使用：

```
/data
```

------

### 13.6.5 为什么需要 PVC

如果 Pod 直接绑定具体存储：

```
Pod
 ↓
某块具体磁盘
```

应用和基础设施会强耦合。

PVC 提供了一个抽象层：

```
Application
     │
     ▼
    PVC
     │
     ▼
  Storage
```

应用只需要表达：

```
“我要 100Gi 存储。”
```

而不需要知道：

```
“这块磁盘在什么服务器？”
```

这就是 Kubernetes 存储抽象非常重要的地方。

------

## 13.7 StorageClass

### 13.7.1 什么是 StorageClass

StorageClass 可以理解成：

> **存储类型/存储策略的定义。**

例如一个生产集群可能有：

```
fast-ssd
standard
high-iops
ceph-rbd
nfs
```

不同 StorageClass 对应不同存储后端和性能特征。

------

### 13.7.2 为什么需要 StorageClass

假设你需要：

```
100Gi
```

传统方式：

```
管理员手工创建 PV
```

大量应用会导致：

```
PV-001
PV-002
PV-003
PV-004
...
```

维护成本非常高。

StorageClass 配合 Dynamic Provisioning 可以做到：

```
PVC
 ↓
StorageClass
 ↓
自动创建存储
 ↓
PV
 ↓
Pod
```

------

### 13.7.3 PVC 指定 StorageClass

例如：

```
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: app-data
spec:
  storageClassName: fast-ssd

  accessModes:
    - ReadWriteOnce

  resources:
    requests:
      storage: 100Gi
```

这里：

```
storageClassName: fast-ssd
```

告诉 Kubernetes：

> 我要使用 `fast-ssd` 这种存储。

------

### 13.7.4 查看 StorageClass

```
kubectl get storageclass
```

简写：

```
kubectl get sc
```

查看详细信息：

```
kubectl describe storageclass fast-ssd
```

------

## 13.8 Dynamic Provisioning

### 13.8.1 什么是 Dynamic Provisioning

Dynamic Provisioning，也就是**动态供给**。

它解决的问题是：

> PVC 创建以后，Kubernetes 自动为它创建所需的持久化存储。

传统方式：

```
管理员
 ↓
创建 PV
 ↓
应用创建 PVC
 ↓
绑定
```

动态方式：

```
应用
 ↓
创建 PVC
 ↓
StorageClass
 ↓
CSI Provisioner
 ↓
自动创建 Storage
 ↓
PV
 ↓
PVC Bound
```

------

### 13.8.2 完整过程

例如：

```
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: mysql-data
spec:
  storageClassName: fast-ssd
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 100Gi
```

执行：

```
kubectl apply -f pvc.yaml
```

然后：

```
kubectl get pvc
```

Kubernetes 发现：

```
PVC
 ↓
需要 100Gi
 ↓
StorageClass = fast-ssd
```

存储系统自动创建实际存储。

然后 Kubernetes 创建/绑定 PV：

```
PVC
 ↓
PV
 ↓
Storage
```

------

### 13.8.3 为什么生产环境非常重要

动态供给让应用部署更加自动化：

```
Developer
   ↓
Deployment / StatefulSet
   +
PVC
   ↓
Kubernetes
   ↓
Storage 自动创建
```

不需要运维人员每次部署数据库时：

```
手工创建磁盘
手工创建 PV
手工绑定
```

这也是 Kubernetes 云原生存储的重要能力。

------

## 13.9 CSI

### 13.9.1 CSI 是什么

CSI：

> **Container Storage Interface**

它是一套标准接口，用于让 Kubernetes 与各种存储系统对接。

可以理解成：

```
Kubernetes
     │
     │ CSI
     ▼
Storage System
```

这样 Kubernetes 不需要为每种存储系统写一套完全不同的存储逻辑。

------

### 13.9.2 为什么需要 CSI

生产环境存储类型非常多：

```
AWS EBS
Azure Disk
Google Persistent Disk
Ceph
NFS
各种云厂商存储
企业 SAN
```

如果 Kubernetes 本身为每种存储写大量特殊代码，会非常复杂。

CSI 提供统一接口：

```
Kubernetes
    │
    ▼
   CSI
    │
 ┌──┼───────┬──────┐
 ▼  ▼       ▼      ▼
云盘 Ceph   NAS   其他存储
```

------

### 13.9.3 CSI Driver

实际生产环境中会部署：

```
CSI Driver
```

例如：

```
云厂商 CSI Driver
Ceph CSI
NFS CSI
```

它负责把 Kubernetes 的存储操作转换成具体存储系统的操作。

例如：

```
PVC 创建
   ↓
CSI Controller
   ↓
创建云盘
   ↓
PV
```

然后 Pod 调度到 Node：

```
Pod
 ↓
Node
 ↓
CSI Node Plugin
 ↓
Attach / Mount
 ↓
Container
```

------

### 13.9.4 CSI 的两个重要部分

通常可以粗略理解为：

```
Controller
    ↓
负责存储资源管理

Node Plugin
    ↓
负责 Node 上的挂载
```

整体：

```
                 Kubernetes
                     │
             ┌───────┴───────┐
             ▼               ▼
        CSI Controller   CSI Node Plugin
             │               │
             ▼               ▼
      创建/删除存储       Attach/Mount
```

不同 CSI Driver 的具体实现有所不同，但这个模型非常重要。

------

## 13.10 云盘 / NAS / Ceph

Kubernetes 本身并不是一个存储系统。

它更像：

```
Storage Orchestrator
```

真正的数据最终还是需要放到实际存储系统。

------

### 13.10.1 云盘

例如：

```
AWS EBS
Azure Managed Disk
Google Persistent Disk
```

典型特点：

```
高可靠
云平台托管
与 Node/Zone 存在拓扑关系
通常支持 RWO 等访问模式
```

架构：

```
Pod
 ↓
PVC
 ↓
StorageClass
 ↓
CSI Driver
 ↓
Cloud Disk
```

适合：

```
MySQL
PostgreSQL
Redis
单实例数据库
需要块存储的应用
```

------

### 13.10.2 NAS

NAS 是网络文件存储。

典型：

```
NFS
```

结构：

```
Pod A ──┐
        │
Pod B ──┼──> NAS
        │
Pod C ──┘
```

适合：

```
共享文件
上传文件
静态资源
多个 Pod 共享数据
```

常见访问模式：

```
ReadWriteMany
```

------

### 13.10.3 Ceph

Ceph 是非常常见的分布式存储系统。

它可以提供：

```
Block Storage
File Storage
Object Storage
```

Kubernetes 中常见：

```
Ceph RBD
CephFS
```

架构：

```
Kubernetes
     │
     ▼
 Ceph CSI
     │
 ┌───┴────┐
 ▼        ▼
RBD      CephFS
 │         │
Block     File
```

适合：

```
私有云
企业 Kubernetes
大规模集群
需要统一分布式存储的环境
```

------

### 13.10.4 如何选择

可以先形成这样的认知：

| 存储     | 典型用途          |
| -------- | ----------------- |
| 云盘     | 数据库、块存储    |
| NAS/NFS  | 共享文件          |
| Ceph RBD | 分布式块存储      |
| CephFS   | 分布式共享文件    |
| hostPath | Node 本地特殊场景 |
| emptyDir | 临时数据          |

生产环境选择时还需要考虑：

```
性能
IOPS
吞吐
可靠性
故障域
备份
快照
成本
ReadWriteMany
ReadWriteOnce
地域/可用区
```

------

## 13.11 StatefulSet + PVC

StatefulSet 是上一章学习的有状态应用控制器。

它和 Kubernetes 存储结合非常重要。

例如：

```
StatefulSet
    │
    ├── Pod-0
    │     └── PVC
    │
    ├── Pod-1
    │     └── PVC
    │
    └── Pod-2
          └── PVC
```

------

### 13.11.1 volumeClaimTemplates

StatefulSet 可以使用：

```
volumeClaimTemplates
```

自动为每个 Pod 创建独立 PVC。

例如：

```
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: web
spec:
  serviceName: web
  replicas: 3

  selector:
    matchLabels:
      app: web

  template:
    metadata:
      labels:
        app: web

    spec:
      containers:
        - name: app
          image: nginx:1.27

          volumeMounts:
            - name: data
              mountPath: /data

  volumeClaimTemplates:
    - metadata:
        name: data
      spec:
        accessModes:
          - ReadWriteOnce

        resources:
          requests:
            storage: 10Gi
```

------

### 13.11.2 最终会发生什么

假设：

```
replicas: 3
```

StatefulSet 创建：

```
web-0
web-1
web-2
```

同时生成类似：

```
data-web-0
data-web-1
data-web-2
```

三个独立 PVC。

关系：

```
web-0 → data-web-0
web-1 → data-web-1
web-2 → data-web-2
```

因此：

> **每个 StatefulSet Pod 都可以拥有自己的持久化数据。**

------

### 13.11.3 为什么 StatefulSet 特别适合数据库

例如 PostgreSQL：

```
postgres-0
    ↓
postgres-0 数据

postgres-1
    ↓
postgres-1 数据
```

Pod 被重新创建：

```
postgres-0
    ↓
删除

新的 postgres-0
    ↓
重新使用原来的 PVC
```

于是：

```
Pod 生命周期
```

和：

```
数据生命周期
```

被分离。

------

## 13.12 数据持久化生命周期

这是生产环境非常重要的概念。

需要区分至少四个对象：

```
Pod
PVC
PV
实际 Storage
```

它们不是同一个东西。

------

### 13.12.1 生命周期关系

```
Pod
 │
 ▼
PVC
 │
 ▼
PV
 │
 ▼
Storage
```

例如：

```
Pod postgres-0
       │
       ▼
PVC data-postgres-0
       │
       ▼
PV pvc-xxxx
       │
       ▼
Cloud Disk / Ceph / NAS
```

------

### 13.12.2 删除 Pod

```
Pod
 ↓
删除
```

通常：

```
PVC
 ↓
仍然存在

PV
 ↓
仍然存在

实际数据
 ↓
仍然存在
```

这就是 Kubernetes 持久化存储的核心价值之一。

------

### 13.12.3 删除 PVC

情况就复杂很多。

PVC 删除之后：

```
PVC
 ↓
删除
```

PV 后续如何处理取决于：

```
persistentVolumeReclaimPolicy
```

常见策略：

```
Retain
Delete
```

------

### 13.12.4 Retain

如果：

```
persistentVolumeReclaimPolicy: Retain
```

删除 PVC 后：

```
PVC
 ↓
删除

PV
 ↓
保留

Storage
 ↓
通常保留
```

这是一种比较保守的策略。

适合：

```
重要生产数据
需要人工确认后再删除
```

------

### 13.12.5 Delete

如果：

```
persistentVolumeReclaimPolicy: Delete
```

PVC 删除后，PV 对应的存储资源可能也会被删除。

例如：

```
PVC
 ↓
删除
 ↓
PV 删除
 ↓
Cloud Disk 删除
```

具体行为取决于：

```
CSI Driver
StorageClass
底层存储系统
```

因此：

> **不能看到 `Delete` 就机械理解成“任何情况下磁盘都会瞬间消失”。**

但生产环境必须把它视为潜在的数据删除操作。

------

## 13.13 删除 Pod 后数据还在吗？

答案：

> **取决于你使用的存储类型。**

------

### 13.13.1 emptyDir

```
Pod
 ↓
emptyDir
 ↓
删除 Pod
 ↓
数据删除
```

所以：

**不保留。**

------

### 13.13.2 hostPath

```
Pod
 ↓
hostPath
 ↓
删除 Pod
```

Node 上的：

```
/data/app
```

通常仍然存在。

所以：

**通常会保留。**

但是：

> 如果 Pod 被调度到其他 Node，它可能访问不到原来的数据。

因此不能把 hostPath 简单当成可靠的集群级持久化存储。

------

### 13.13.3 PVC

```
Pod
 ↓
PVC
 ↓
PV
 ↓
Storage
```

删除 Pod：

```
Pod
 ↓
删除
```

通常：

```
PVC
 ↓
保留

PV
 ↓
保留

Storage
 ↓
保留
```

因此：

**通常会保留。**

这正是 PVC 的重要意义。

------

## 13.14 删除 PVC 后数据还在吗？

这个问题不能只回答：

```
是
```

或者：

```
否
```

必须看 PV 的回收策略。

------

### 13.14.1 Retain

```
PVC
 ↓
删除

PV
 ↓
保留

底层 Storage
 ↓
通常保留
```

因此：

> 数据通常不会因为删除 PVC 而立即自动删除。

但后续可能需要人工处理 PV 和存储资源。

------

### 13.14.2 Delete

```
PVC
 ↓
删除

PV
 ↓
删除

底层 Storage
 ↓
可能删除
```

因此：

> **删除 PVC 在生产环境必须被视为潜在的数据删除操作。**

------

### 13.14.3 StatefulSet 删除时尤其需要注意

例如：

```
StatefulSet
 ├── Pod-0
 ├── Pod-1
 └── Pod-2

PVC
 ├── data-0
 ├── data-1
 └── data-2
```

删除 StatefulSet：

```
kubectl delete statefulset postgres
```

并不等同于：

```
自动删除所有 PVC
```

PVC 的生命周期需要单独关注。

因此生产环境执行：

```
kubectl delete pvc ...
```

之前一定要确认：

```
数据是否已经备份？
是否还需要恢复？
PV Reclaim Policy 是什么？
底层 Storage 是否会被删除？
```

------

## 13.15 Kubernetes 存储故障排查

生产环境存储问题非常常见。

典型现象：

```
Pod Pending
Pod ContainerCreating
MountVolume Error
AttachVolume Error
PVC Pending
I/O Error
Read-only filesystem
```

排查时不要直接猜。

应该按照：

```
Pod
 ↓
PVC
 ↓
PV
 ↓
StorageClass
 ↓
CSI
 ↓
Node
 ↓
实际 Storage
```

逐层排查。

------

### 13.15.1 第一步：查看 Pod

```
kubectl get pod
```

例如：

```
NAME       READY   STATUS
mysql-0    0/1     Pending
```

详细信息：

```
kubectl describe pod mysql-0
```

重点看：

```
Events
```

例如：

```
FailedMount
FailedAttachVolume
FailedScheduling
```

------

### 13.15.2 第二步：查看 PVC

```
kubectl get pvc
```

例如：

```
NAME         STATUS    VOLUME
mysql-data   Pending
```

如果：

```
STATUS=Pending
```

说明 PVC 还没有正常绑定。

查看：

```
kubectl describe pvc mysql-data
```

重点关注 Events。

------

### 13.15.3 PVC Pending 常见原因

例如：

```
StorageClass 不存在
StorageClass 配置错误
没有匹配的 PV
CSI Driver 异常
容量不足
Access Mode 不支持
拓扑约束
```

首先：

```
kubectl get storageclass
```

确认 StorageClass 是否存在。

------

### 13.15.4 查看 PV

```
kubectl get pv
```

关注：

```
STATUS
CLAIM
CAPACITY
STORAGECLASS
```

例如：

```
Available
Bound
Released
Failed
```

------

### 13.15.5 查看 StorageClass

```
kubectl get sc
```

详细：

```
kubectl describe sc <storage-class-name>
```

重点看：

```
provisioner
reclaimPolicy
volumeBindingMode
```

例如：

```
provisioner: ...
reclaimPolicy: Delete
volumeBindingMode: WaitForFirstConsumer
```

------

### 13.15.6 检查 CSI

查看 CSI 相关 Pod：

```
kubectl get pods -A | grep -i csi
```

也可以：

```
kubectl get csidrivers
```

查看：

```
kubectl get csinodes
```

如果 CSI Controller 或 Node Plugin 异常，就可能出现：

```
ProvisioningFailed
AttachVolume failed
MountVolume failed
```

------

### 13.15.7 Node 层排查

如果：

```
PVC = Bound
```

但 Pod：

```
ContainerCreating
```

并且 Event：

```
MountVolume.SetUp failed
```

就需要进一步检查：

```
Node
CSI Node Plugin
挂载点
网络
权限
存储系统
```

查看 Pod 被调度到了哪个 Node：

```
kubectl get pod mysql-0 -o wide
```

然后：

```
kubectl describe node <node-name>
```

------

### 13.15.8 常见故障现象对应关系

| 现象                 | 优先检查                         |
| -------------------- | -------------------------------- |
| PVC Pending          | StorageClass / PV / CSI          |
| Pod Pending          | 调度、PVC、拓扑                  |
| ContainerCreating    | Volume Mount / CSI               |
| FailedAttachVolume   | CSI / Node / Storage             |
| FailedMount          | CSI / 权限 / 文件系统            |
| I/O Error            | 底层 Storage / Node              |
| Read-only filesystem | 文件系统 / 存储故障              |
| 数据消失             | PVC/PV 生命周期 / Reclaim Policy |

------

### 13.15.9 一套可以直接使用的排查命令

假设 Pod：

```
mysql-0
```

先：

```
kubectl get pod mysql-0 -o wide
```

然后：

```
kubectl describe pod mysql-0
```

查看 PVC：

```
kubectl get pvc
```

再：

```
kubectl describe pvc <pvc-name>
```

查看 PV：

```
kubectl get pv
```

查看 StorageClass：

```
kubectl get sc
```

查看 CSI：

```
kubectl get csidrivers
kubectl get csinodes
```

查看所有 CSI Pod：

```
kubectl get pods -A | grep -i csi
```

最后再根据 Events 和 CSI 日志继续向下排查。

```
emptyDir
    ↓
临时数据

hostPath
    ↓
Node 本地数据

PVC
    ↓
持久化存储声明

PV
    ↓
持久化存储资源

StorageClass
    ↓
存储类型和动态供给策略

CSI
    ↓
Kubernetes 与实际存储之间的标准接口
```

最重要的生命周期关系：

```
删除 Pod
   │
   ├── emptyDir → 数据通常消失
   │
   └── PVC → PVC 通常保留 → 数据通常保留
```

而：

```
删除 PVC
   │
   ├── Retain → PV/底层数据通常保留
   │
   └── Delete → PV/底层存储可能被删除
```

因此生产环境必须牢记：

> **Pod 是计算资源，PVC 是数据需求，PV 是持久化资源，StorageClass 是存储策略，CSI 是连接 Kubernetes 与真实存储的标准接口。**

最终形成一个非常重要的生产架构认知：

```
                 Kubernetes
                     │
              ┌──────┴──────┐
              │             │
           Compute        Storage
              │             │
             Pod           PVC
              │             │
              │             ▼
              │             PV
              │             │
              │             ▼
              │        StorageClass
              │             │
              │             ▼
              │            CSI
              │             │
              │      ┌──────┼──────┐
              │      ▼      ▼      ▼
              │    Cloud   NAS    Ceph
              │     Disk
              │
              └──── Application
```

**一句话记忆：**

> **Pod 可以随时消失，但真正需要长期保存的数据，应该通过 PVC 脱离 Pod 生命周期，并最终落到可靠的持久化存储上。**
