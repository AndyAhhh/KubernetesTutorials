# 第 35 章：Kubernetes 实战故障实验室

本章的目标不是继续学习新的 Kubernetes 对象，而是建立一套真正适用于生产环境的**故障排查方法论**。

前面的章节解决了：

```
Kubernetes 是什么
        ↓
如何部署应用
        ↓
如何暴露服务
        ↓
如何存储数据
        ↓
如何扩缩容
        ↓
如何监控和发布
```

本章解决的是生产环境最重要的问题之一：

> **当系统出问题时，你能不能快速、系统地找到根因？**

核心方法固定为：

```
现象
 ↓
判断
 ↓
定位
 ↓
处理
 ↓
验证
 ↓
复盘
```

------

## 35.1 实验环境准备

### 35.1.1 建立独立实验 Namespace

不要直接在生产 Namespace 制造故障。

创建：

```
kubectl create namespace k8s-lab
```

确认：

```
kubectl get namespace k8s-lab
```

后面的实验原则上都在：

```
k8s-lab
```

中进行。

------

### 35.1.2 创建基础测试 Deployment

先创建一个正常应用：

```
apiVersion: apps/v1
kind: Deployment
metadata:
  name: demo
  namespace: k8s-lab

spec:
  replicas: 2

  selector:
    matchLabels:
      app: demo

  template:
    metadata:
      labels:
        app: demo

    spec:
      containers:
        - name: nginx
          image: nginx:1.29-alpine
          ports:
            - containerPort: 80
```

执行：

```
kubectl apply -f demo.yaml
```

检查：

```
kubectl get pods -n k8s-lab
kubectl get deployment -n k8s-lab
```

正常情况下：

```
NAME                     READY   STATUS
demo-xxxxxxxxxx-xxxxx    1/1     Running
demo-xxxxxxxxxx-yyyyy    1/1     Running
```

------

### 35.1.3 建立标准排障工具集

日常最常用：

```
kubectl get pods -o wide
kubectl describe pod <pod>
kubectl logs <pod>
kubectl logs <pod> --previous
kubectl get events
kubectl describe node <node>
kubectl get svc
kubectl get endpoints
kubectl get endpointslices
kubectl get ingress
kubectl get pvc
kubectl get hpa
```

排障时不要一上来就：

```
kubectl delete pod
```

因为：

> **删除 Pod 有时是在掩盖问题，而不是解决问题。**

首先应该获取现场信息。

## 35.2 Pod 无法启动

### 35.2.1 制造故障

故意使用不存在的镜像：

```
apiVersion: apps/v1
kind: Deployment
metadata:
  name: bad-start
  namespace: k8s-lab

spec:
  replicas: 1

  selector:
    matchLabels:
      app: bad-start

  template:
    metadata:
      labels:
        app: bad-start

    spec:
      containers:
        - name: app
          image: nginx:this-image-does-not-exist
kubectl apply -f bad-start.yaml
```

------

### 35.2.2 观察现象

```
kubectl get pods -n k8s-lab
```

可能看到：

```
NAME                         READY   STATUS
bad-start-xxxxxxxxxx-xxxxx   0/1     ErrImagePull
```

或者：

```
ImagePullBackOff
```

------

### 35.2.3 标准定位

第一步：

```
kubectl describe pod <pod> -n k8s-lab
```

重点看：

```
Events:
```

例如：

```
Failed to pull image
```

排障思路：

```
Pod Pending/异常
 ↓
kubectl describe pod
 ↓
Events
 ↓
确定是 Image / Scheduling / Volume / Config / Probe？
```

------

## 35.3 镜像无法拉取

### 35.3.1 常见原因

ImagePullBackOff 常见原因：

```
镜像名称错误
镜像 Tag 不存在
Registry 不可达
私有 Registry 未认证
ImagePullSecret 错误
Node 无法访问 Registry
TLS/证书问题
```

------

### 35.3.2 定位命令

```
kubectl describe pod <pod> -n k8s-lab
```

例如：

```
Failed to pull image
```

进一步确认：

```
kubectl get pod <pod> -n k8s-lab -o yaml
```

查看：

```
spec:
  containers:
    - image: ...
```

------

### 35.3.3 私有 Registry

如果需要认证：

```
spec:
  imagePullSecrets:
    - name: registry-secret
```

检查 Secret：

```
kubectl get secret registry-secret -n k8s-lab
```

如果 Secret 不存在：

```
Pod
 ↓
拉取私有镜像
 ↓
认证失败
 ↓
ImagePullBackOff
```

------

### 35.3.4 修复

修改正确镜像：

```
kubectl set image deployment/bad-start \
  app=nginx:1.29-alpine \
  -n k8s-lab
```

然后：

```
kubectl rollout status deployment/bad-start -n k8s-lab
```

验证：

```
kubectl get pods -n k8s-lab
```

## 35.4 Pod 无限重启

### 35.4.1 制造故障

创建一个启动后立即退出的容器：

```
apiVersion: apps/v1
kind: Deployment
metadata:
  name: crash-demo
  namespace: k8s-lab

spec:
  replicas: 1

  selector:
    matchLabels:
      app: crash-demo

  template:
    metadata:
      labels:
        app: crash-demo

    spec:
      containers:
        - name: app
          image: busybox:1.36
          command:
            - sh
            - -c
            - "echo application failed; exit 1"
```

------

### 35.4.2 观察

```
kubectl get pods -n k8s-lab
```

可能：

```
CrashLoopBackOff
```

------

### 35.4.3 正确排查

首先：

```
kubectl describe pod <pod> -n k8s-lab
```

然后：

```
kubectl logs <pod> -n k8s-lab
```

由于容器已经重启，还要看：

```
kubectl logs <pod> -n k8s-lab --previous
```

重点：

> **CrashLoopBackOff 不是根因。**

它只是告诉你：

```
Container
 ↓
启动
 ↓
退出
 ↓
Kubernetes 重启
 ↓
再次退出
 ↓
反复发生
```

真正原因需要看：

```
应用日志
退出码
Container State
Events
```

## 35.5 内存 OOM

### 35.5.1 OOM 的本质

当容器超过可使用的内存限制时，可能被 Linux OOM Killer 终止。

例如：

```
resources:
  limits:
    memory: 32Mi
```

应用实际需要：

```
100Mi
```

就可能：

```
32Mi limit
   ↓
内存不足
   ↓
OOMKilled
```

------

### 35.5.2 观察

```
kubectl get pods -n k8s-lab
```

然后：

```
kubectl describe pod <pod> -n k8s-lab
```

查看：

```
Last State:
  Reason: OOMKilled
```

------

### 35.5.3 排查路径

```
OOMKilled
 ↓
确认 limits.memory
 ↓
确认实际 Memory 使用
 ↓
查看应用日志
 ↓
判断正常增长还是异常增长
 ↓
调整应用 / Resource / 内存泄漏
```

不要看到 OOM 就简单地：

```
memory limit × 10
```

否则可能只是把问题推迟。

## 35.6 CPU 100%

### 35.6.1 观察

如果 Metrics Server 已部署：

```
kubectl top pods -n k8s-lab
```

例如：

```
NAME        CPU(cores)   MEMORY(bytes)
api-xxx     980m         300Mi
```

说明 CPU 接近：

```
1 CPU
```

------

### 35.6.2 判断 CPU 高的原因

CPU 高不一定是故障。

可能是：

```
正常流量增加
CPU 密集型业务
死循环
代码 Bug
频繁 GC
大量重试
下游故障导致请求堆积
```

所以：

```
CPU 100%
```

只是**现象**。

------

### 35.6.3 进一步排查

```
kubectl top pod <pod> -n k8s-lab
kubectl describe pod <pod> -n k8s-lab
kubectl logs <pod> -n k8s-lab
```

同时检查：

```
Application Metrics
Request Rate
Latency
Error Rate
```

最终要找到：

```
为什么 CPU 高？
```

而不是只知道：

```
CPU 很高。
```

## 35.7 Service 无法访问

### 35.7.1 创建 Service

```
apiVersion: v1
kind: Service

metadata:
  name: demo
  namespace: k8s-lab

spec:
  selector:
    app: demo

  ports:
    - port: 80
      targetPort: 80
```

------

### 35.7.2 第一层：Service 是否存在

```
kubectl get svc -n k8s-lab
```

------

### 35.7.3 第二层：Selector 是否正确

```
kubectl describe svc demo -n k8s-lab
```

检查：

```
Selector:
  app=demo
```

然后：

```
kubectl get pods -n k8s-lab --show-labels
```

如果 Pod：

```
app=frontend
```

而 Service：

```
app=demo
```

那么：

```
Service
 ↓
Selector 匹配不到 Pod
 ↓
Endpoints = 0
```

------

### 35.7.4 第三层：Endpoint

```
kubectl get endpoints demo -n k8s-lab
```

以及：

```
kubectl get endpointslice -n k8s-lab
```

如果没有后端：

```
Service
 ↓
没有 Endpoint
 ↓
没有 Pod 可以转发
```

------

### 35.7.5 第四层：Pod 是否真的监听端口

进入测试 Pod：

```
kubectl run test-client \
  -n k8s-lab \
  --rm -it \
  --image=curlimages/curl \
  -- sh
```

然后：

```
curl http://demo
```

这样可以判断问题到底发生在：

```
Client
 ↓
Service
```

还是：

```
Service
 ↓
Pod
```

### 35.8.1 Service DNS

例如：

```
demo.k8s-lab.svc.cluster.local
```

可以在测试 Pod：

```

  -n k8s-lab \

```

测试：

```

```

### 35.8.2 DNS 排查层次

```
应用
 ↓
Pod DNS 配置
 ↓
CoreDNS Service
 ↓
CoreDNS Pods
 ↓
Kubernetes API / DNS Records
```

检查：

```
kubectl get pods -n kube-system
```

找到 CoreDNS。

然后：

```
kubectl logs -n kube-system \
```

### 35.8.3 常见问题

```

```

所以：

> DNS 故障不能只检查 CoreDNS。

## 35.9 Ingress 502

Ingress 502 是生产环境非常常见的问题。

典型链路：

```
Internet
 ↓
LoadBalancer
 ↓
Ingress Controller
 ↓
Service
 ↓
Pod
 ↓
Application
```

因此 502 不能直接判断为 Ingress 本身的问题。

------

### 35.9.1 第一层：Ingress

```
kubectl get ingress -n k8s-lab
kubectl describe ingress <name> -n k8s-lab
```

确认：

```
Host
Path
Backend
TLS
```

------

### 35.9.2 第二层：Service

```
kubectl get svc -n k8s-lab
kubectl get endpoints -n k8s-lab
```

如果：

```
Endpoints = <none>
```

问题已经不在 Ingress。

------

### 35.9.3 第三层：Pod

```
kubectl get pods -n k8s-lab
kubectl logs <pod> -n k8s-lab
```

------

### 35.9.4 第四层：直接访问 Service

```
kubectl run curl \
  -n k8s-lab \
  --rm -it \
  --image=curlimages/curl \
  -- curl http://demo
```

如果：

```
Service 正常
```

再继续检查：

```
Ingress Controller
Ingress Rule
TLS
DNS
```

## 35.14 Secret 配置错误

### 35.14.1 常见现象

例如 API 启动：

```
Database connection failed
```

但 Pod：

```
Running
```

这时很容易误以为 Kubernetes 没问题。

实际上：

```
Pod Running
≠
Application Healthy
```

------

### 35.14.2 检查 Secret

```
kubectl get secret api-secret -n k8s-lab
```

查看 key：

```
kubectl describe secret api-secret -n k8s-lab
```

`describe` 不会直接显示 Secret value。

如果需要在实验环境检查：

```
kubectl get secret api-secret \
  -n k8s-lab \
  -o jsonpath='{.data.password}' | base64 -d
```

------

### 35.14.3 检查 Pod 是否引用正确

```
kubectl get pod <pod> \
  -n k8s-lab \
  -o yaml
```

重点：

```
secretKeyRef:
  name: api-secret
  key: password
```

检查：

```
Secret 名称
Key 名称
Namespace
环境变量名称
```

是否一致。

## 35.17 节点宕机

这是第一个真正接近生产事故的实验。

### 35.17.1 事故模型

假设：

```
Node 1
 ├── API Pod
 ├── Frontend Pod
 └── Redis Pod
```

Node 1 突然：

```
DOWN
```

------

### 35.17.2 Kubernetes 会发生什么

对于 Deployment：

```
API Pod
 ↓
Node 故障
 ↓
Pod 不可用
 ↓
Controller 发现副本不足
 ↓
在其他可调度 Node 创建新 Pod
```

但是否能够恢复取决于：

```
剩余 Node 是否有资源
Pod 是否有调度约束
PVC 是否能够重新挂载
应用是否真正支持 HA
```

------

### 35.17.3 观察

```
kubectl get nodes
kubectl get pods -o wide -n k8s-lab
```

重点观察：

```
Pod 原来在哪个 Node
 ↓
Node 故障
 ↓
Pod 是否重新调度
```

------

### 35.17.4 重要结论

```
Deployment replicas: 3
```

不代表：

```
3 个 Pod 一定在 3 个 Node
```

如果三个 Pod 全部在：

```
Node 1
```

Node 1 挂掉：

```
3 个 Pod
 ↓
全部消失
```

所以需要结合：

```
Pod Anti-Affinity
Topology Spread Constraints
```

实现真正的故障域分散。

## 35.18 Pod 大面积迁移

### 35.18.1 为什么会发生

例如：

```
Node 故障
```

或者：

```
Node Drain
```

会导致：

```
Pod
 ↓
原 Node 不可用
 ↓
重新调度
 ↓
其他 Node
```

------

### 35.18.2 观察

```
kubectl get pods -A -o wide
```

重点观察：

```
NODE
```

字段。

------

### 35.18.3 大规模迁移的风险

如果大量 Pod 同时迁移：

```
Node A
 ↓
大量 Pod Eviction
 ↓
Node B/C
 ↓
CPU / Memory 突然升高
```

可能产生：

```
资源不足
Pod Pending
启动风暴
数据库连接暴增
缓存冷启动
Ingress 502/503
```

所以：

> **故障恢复本身也可能制造第二次故障。**

------

### 35.18.4 PodDisruptionBudget

生产环境可以使用：

```
apiVersion: policy/v1
kind: PodDisruptionBudget

metadata:
  name: api-pdb
  namespace: k8s-lab

spec:
  minAvailable: 2

  selector:
    matchLabels:
      app: api
```

它主要用于控制**自愿中断**情况下可同时被驱逐的 Pod 数量。

注意：

> PDB 不能阻止 Node 突然宕机。

它主要保护：

```
kubectl drain
Cluster Upgrade
Node Maintenance
```

等场景。

## 35.19 应用发布导致线上故障

这是最接近真实生产事故的一类问题。

### 35.19.1 典型事故

```
Developer
 ↓
发布 v2
 ↓
Deployment RollingUpdate
 ↓
新 Pod Ready
 ↓
旧 Pod 逐渐退出
 ↓
线上开始 5xx
```

为什么 Kubernetes 认为新 Pod 正常？

可能因为：

```
Readiness Probe 设计错误
```

例如：

```
/health
```

只检查：

```
HTTP Server 是否启动
```

却没有检查：

```
Database
Redis
Required Dependency
```

于是：

```
Pod = Ready
```

但真实业务：

```
不可用
```

------

### 35.19.2 标准发布验证

发布之后至少检查：

```
kubectl rollout status deployment/api -n production
```

然后：

```
kubectl get pods -l app=api -n production
```

再检查：

```
5xx
Latency
Request Rate
Application Logs
Database
Redis
```

不能只检查：

```
kubectl get pods
```

------

### 35.19.3 发布失败立即回滚

```
kubectl rollout history deployment/api -n production
```

回滚：

```
kubectl rollout undo deployment/api -n production
```

然后：

```
kubectl rollout status deployment/api -n production
```

最终验证：

```
Pod
 ↓
Service
 ↓
Ingress
 ↓
真实 HTTP 请求
 ↓
业务指标
```

全部恢复。

## 35.20 统一排障模型

前面所有事故都可以归纳为一个模型：

```
                    用户看到的现象
                           │
                           ▼
                    ┌─────────────┐
                    │ Application │
                    └──────┬──────┘
                           │
                           ▼
                         Pod
                           │
                           ▼
                        Service
                           │
                           ▼
                       Ingress
                           │
                           ▼
                         Node
                           │
                           ▼
                      Kubernetes
                           │
                           ▼
                    Infrastructure
```

但是实际排障不一定永远从上往下。

应该根据现象选择入口。

例如：

```
Pod Pending
    ↓
Scheduler / Node / Resource
ImagePullBackOff
    ↓
Image / Registry / Secret
CrashLoopBackOff
    ↓
Container / Application
Service 无访问
    ↓
Selector / Endpoint / Pod / Network
Ingress 502
    ↓
Ingress → Service → Pod → Application
PVC Pending
    ↓
PVC → StorageClass → CSI → Storage
Node NotReady
    ↓
Node → kubelet → Runtime → Network → Disk
```

## 35.21 Event → Pod → Node → Application 逐层排查

这是本章最重要的一套生产排障路径。

### 35.21.1 第一层：Event

首先：

```
kubectl get events -A --sort-by=.lastTimestamp
```

或者：

```
kubectl get events -n k8s-lab --sort-by=.lastTimestamp
```

Event 经常直接告诉你：

```
FailedScheduling
FailedMount
FailedAttachVolume
FailedPull
Unhealthy
BackOff
Evicted
```

因此：

> **Event 是 Kubernetes 故障现场的重要入口。**

------

### 35.21.2 第二层：Pod

```
kubectl get pod -n k8s-lab -o wide
```

然后：

```
kubectl describe pod <pod> -n k8s-lab
```

重点：

```
Status
Conditions
Container State
Last State
Restart Count
Events
Node
Resources
Probe
Volume
```

------

### 35.21.3 第三层：Node

如果 Pod 的问题看起来与节点有关：

```
kubectl get nodes
```

然后：

```
kubectl describe node <node>
```

重点：

```
Ready
MemoryPressure
DiskPressure
PIDPressure
Allocatable
Conditions
Events
```

如果能够登录 Node：

```
systemctl status kubelet
journalctl -u kubelet
```

------

### 35.21.4 第四层：Application

Kubernetes 正常：

```
Pod Running
Service 正常
Node Ready
```

但业务仍然失败，就必须进入应用层。

例如：

```
kubectl logs <pod> -n k8s-lab
```

如果发生过重启：

```
kubectl logs <pod> -n k8s-lab --previous
```

继续检查：

```
Application Logs
Application Metrics
Database
Redis
External API
Configuration
```

最终：

> Kubernetes 是运行平台，不是业务问题的终点。

## 35.23 CPU / Memory 故障的固定排查路径

### CPU

```
CPU 高
 ↓
kubectl top
 ↓
哪个 Pod？
 ↓
哪个 Container？
 ↓
流量是否增加？
 ↓
Application Metrics
 ↓
是否存在异常请求？
 ↓
代码 / GC / 重试 / 下游依赖
```

------

### Memory

```
Memory 高
 ↓
kubectl top
 ↓
是否 OOMKilled？
 ↓
Memory Limit
 ↓
应用内存增长趋势
 ↓
GC / Cache / Memory Leak
 ↓
修复应用或调整资源
```

重点是：

> **Resource Metrics 负责告诉你“发生了什么”，Application Metrics 和 Logs 才更可能告诉你“为什么发生”。**

## 35.27 建立 Kubernetes 故障分类

经过本章实验，可以把生产事故快速归类。

| 现象                | 第一检查点                          |
| ------------------- | ----------------------------------- |
| Pod Pending         | Scheduler / Events                  |
| ImagePullBackOff    | Image / Registry                    |
| CrashLoopBackOff    | Logs / Previous Logs                |
| OOMKilled           | Memory / Limits                     |
| CPU 高              | `kubectl top` / Application Metrics |
| Service 无访问      | Selector / Endpoint                 |
| DNS 失败            | CoreDNS / NetworkPolicy             |
| Ingress 502         | Ingress → Service → Pod             |
| PVC Pending         | StorageClass / CSI                  |
| Node NotReady       | Node / kubelet                      |
| Deployment 发布失败 | ReplicaSet / Events / Rollout       |
| HPA 不扩容          | Metrics Server / HPA                |
| Secret 错误         | Secret / Key / Application          |
| Readiness 失败      | Probe / Application Port            |
| 网络不通            | NetworkPolicy / DNS / Service       |
| Node 宕机           | Node / Scheduling / Replica         |
| Pod 大面积迁移      | Node / Scheduler / Resources        |
| 发布后业务异常      | Deployment / Probe / Metrics / Logs |

## 35.29 最终形成的 Kubernetes 排障方法论

经过这一章，面对 Kubernetes 故障时，不应该再是：

```
“Pod 挂了，重启一下。”
```

而应该变成：

```
                    现象
                      │
                      ▼
                 确认影响范围
                      │
                      ▼
                   Event
                      │
                      ▼
                    Pod
                      │
             ┌────────┴────────┐
             ▼                 ▼
           Logs             Describe
             │                 │
             └────────┬────────┘
                      ▼
                    Node
                      │
                      ▼
                Application
                      │
                      ▼
                   根因
                      │
                      ▼
                    处理
                      │
                      ▼
                    验证
                      │
                      ▼
                    复盘
```

最重要的是区分：

```
现象 ≠ 根因
```

例如：

```
CrashLoopBackOff
```

不是根因。

```
OOMKilled
```

也可能只是结果。

```
502
```

也不能直接认为是 Ingress 故障。

```
CPU 100%
```

更不能直接认为是 Kubernetes 故障。

真正的运维工程师需要不断向下追：

```
发生了什么？
        ↓
在哪里发生？
        ↓
哪一层发生？
        ↓
为什么发生？
        ↓
什么证据证明？
```

最终形成固定思维：

> **现象 → 判断 → 定位 → 处理 → 验证 → 复盘**

这套流程比记住多少条 `kubectl` 命令更加重要。
