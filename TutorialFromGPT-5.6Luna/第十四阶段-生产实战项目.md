## 34.1 项目整体架构

### 34.1.1 业务组件

我们设计一个简单的业务系统：

```
┌────────────────────────────────────────────────────┐
│                    Internet                        │
└──────────────────────┬─────────────────────────────┘
                       │
                       ▼
                LoadBalancer
                       │
                       ▼
                   Ingress
                 /          \
                /            \
               ▼              ▼
        Vue Frontend       .NET API
                              │
             ┌────────────────┼────────────────┐
             │                │                │
             ▼                ▼                ▼
          Redis          PostgreSQL        Other API
```

各组件职责：

| 组件       | 作用                | Kubernetes 资源                 |
| ---------- | ------------------- | ------------------------------- |
| Vue        | 前端页面            | Deployment                      |
| Nginx      | 托管 Vue 静态文件   | Container                       |
| .NET API   | 核心业务 API        | Deployment                      |
| Redis      | Cache               | StatefulSet                     |
| PostgreSQL | 数据库              | StatefulSet                     |
| Other API  | 外部/内部第三方服务 | Service/External Service        |
| Ingress    | HTTP/HTTPS 入口     | Ingress                         |
| Prometheus | 指标采集            | Operator/Deployment             |
| Grafana    | 指标可视化          | Deployment                      |
| Loki       | 日志存储            | Stateful/Distributed components |
| Argo CD    | GitOps 部署         | Deployment                      |

------

### 34.1.2 Kubernetes 资源关系

整个业务系统可以抽象成：

```
                         Ingress
                            │
              ┌─────────────┴─────────────┐
              ▼                           ▼
         frontend-svc                 api-svc
              │                           │
              ▼                           ▼
        frontend Pods                 API Pods
                                          │
                              ┌───────────┼───────────┐
                              ▼           ▼           ▼
                         redis-svc   postgres-svc   other-api
                              │           │
                              ▼           ▼
                         Redis Pods   PostgreSQL Pods
                                          │
                                          ▼
                                         PVC
```

这里再次体现 Kubernetes 中几个核心对象的职责：

```
Deployment
    ↓
管理无状态应用

StatefulSet
    ↓
管理需要稳定身份/存储的应用

Service
    ↓
提供稳定访问入口

Ingress
    ↓
提供 HTTP/HTTPS 外部入口

PVC
    ↓
申请持久化存储
```

## 34.3 Vue Frontend

### 34.3.1 为什么使用 Nginx

Vue 编译之后通常产生：

```
HTML
CSS
JavaScript
Images
```

例如：

```
npm run build
```

生成：

```
dist/
├── index.html
├── assets/
└── ...
```

生产环境通常不会让 Node.js 开发服务器直接承担静态文件服务。

更常见的是：

```
Vue
 ↓
npm build
 ↓
dist
 ↓
Nginx
 ↓
Browser
```

------

### 34.3.2 Vue Dockerfile

例如：

```
FROM node:22-alpine AS build

WORKDIR /app

COPY package*.json ./
RUN npm ci

COPY . .
RUN npm run build


FROM nginx:1.29-alpine

COPY --from=build /app/dist /usr/share/nginx/html

EXPOSE 80
```

这是典型的：

```
多阶段构建
```

最终镜像只需要：

```
Nginx
+
Vue 静态文件
```

不需要把整个 Node.js 构建环境带进生产镜像。

------

### 34.3.3 Vue Deployment

```
apiVersion: apps/v1
kind: Deployment
metadata:
  name: frontend
spec:
  replicas: 2

  selector:
    matchLabels:
      app: frontend

  template:
    metadata:
      labels:
        app: frontend

    spec:
      containers:
        - name: frontend
          image: registry.example.com/business/frontend:1.0.0

          ports:
            - containerPort: 80

          resources:
            requests:
              cpu: 100m
              memory: 128Mi
            limits:
              cpu: 500m
              memory: 256Mi

          readinessProbe:
            httpGet:
              path: /
              port: 80

          livenessProbe:
            httpGet:
              path: /
              port: 80
```

这里综合使用了：

```
Deployment
replicas
Resources
Readiness Probe
Liveness Probe
```

## 34.4 .NET API

### 34.4.1 .NET API Dockerfile

例如：

```
FROM mcr.microsoft.com/dotnet/sdk:8.0 AS build

WORKDIR /src

COPY . .

RUN dotnet restore

RUN dotnet publish \
    -c Release \
    -o /app/publish \
    --no-restore


FROM mcr.microsoft.com/dotnet/aspnet:8.0

WORKDIR /app

COPY --from=build /app/publish .

EXPOSE 8080

ENTRYPOINT ["dotnet", "MyApi.dll"]
```

生产环境应该尽量使用：

```
SDK Image
    ↓
只负责 Build

Runtime Image
    ↓
只负责运行
```

这样可以减少最终镜像内容。

------

### 34.4.2 API Deployment

```
apiVersion: apps/v1
kind: Deployment

metadata:
  name: api

spec:
  replicas: 3

  strategy:
    type: RollingUpdate

    rollingUpdate:
      maxUnavailable: 0
      maxSurge: 1

  selector:
    matchLabels:
      app: api

  template:
    metadata:
      labels:
        app: api

    spec:
      serviceAccountName: api

      containers:
        - name: api
          image: registry.example.com/business/api:1.0.0

          ports:
            - name: http
              containerPort: 8080

          envFrom:
            - configMapRef:
                name: api-config

          env:
            - name: ConnectionStrings__Default
              valueFrom:
                secretKeyRef:
                  name: api-secret
                  key: database-connection-string

          resources:
            requests:
              cpu: 200m
              memory: 256Mi

            limits:
              cpu: "1"
              memory: 512Mi

          startupProbe:
            httpGet:
              path: /health/startup
              port: 8080
            failureThreshold: 30
            periodSeconds: 5

          readinessProbe:
            httpGet:
              path: /health/ready
              port: 8080
            periodSeconds: 10

          livenessProbe:
            httpGet:
              path: /health/live
              port: 8080
            periodSeconds: 20
```

这里综合了：

```
Deployment
RollingUpdate
ServiceAccount
ConfigMap
Secret
Resource Requests
Resource Limits
StartupProbe
ReadinessProbe
LivenessProbe
```

## 34.5 Service

### 34.5.1 API Service

API 不应该直接让 Pod IP 暴露给其他组件。

创建：

```
apiVersion: v1
kind: Service

metadata:
  name: api

spec:
  type: ClusterIP

  selector:
    app: api

  ports:
    - name: http
      port: 80
      targetPort: 8080
```

于是：

```
frontend
   │
   ▼
api.default.svc.cluster.local
   │
   ▼
Service
   │
   ├── API Pod 1
   ├── API Pod 2
   └── API Pod 3
```

------

### 34.5.2 为什么不直接访问 Pod

Pod IP：

```
10.x.x.x
```

不是稳定地址。

Pod 可能：

```
删除
重建
迁移 Node
```

IP 会发生变化。

Service 提供：

```
稳定 DNS
+
稳定虚拟 IP
+
负载均衡
```

所以应用应该：

```
访问 Service
```

而不是：

```
访问 Pod IP
```

## 34.7 Secret

数据库连接字符串属于敏感信息。

不要：

```
image: myapi
env:
  - name: DB_PASSWORD
    value: "123456"
```

应该：

```
apiVersion: v1
kind: Secret

metadata:
  name: api-secret

type: Opaque

stringData:
  database-connection-string: >-
    Host=postgres;
    Port=5432;
    Database=business;
    Username=business;
    Password=change-me
```

然后：

```
env:
  - name: ConnectionStrings__Default
    valueFrom:
      secretKeyRef:
        name: api-secret
        key: database-connection-string
```

注意：

> Kubernetes Secret 本身并不等于完整的生产级密钥管理系统。

真实生产环境应结合：

```
KMS
Vault
External Secrets
云 Secret Manager
```

等方案。

## 34.8 Redis：StatefulSet

### 34.8.1 为什么 Redis 使用 StatefulSet

Redis 是否一定需要 StatefulSet？

**不一定。**

如果 Redis 只是：

```
临时 Cache
```

并且允许数据丢失，可以考虑：

```
Deployment
```

但是如果需要：

```
持久化
稳定身份
```

则可以考虑：

```
StatefulSet
+
PVC
```

------

### 34.8.2 Redis Service

```
apiVersion: v1
kind: Service

metadata:
  name: redis

spec:
  clusterIP: None

  selector:
    app: redis

  ports:
    - port: 6379
      targetPort: 6379
```

这是：

```
Headless Service
```

------

### 34.8.3 Redis StatefulSet

```
apiVersion: apps/v1
kind: StatefulSet

metadata:
  name: redis

spec:
  serviceName: redis
  replicas: 1

  selector:
    matchLabels:
      app: redis

  template:
    metadata:
      labels:
        app: redis

    spec:
      containers:
        - name: redis
          image: redis:7.4-alpine

          args:
            - redis-server
            - --appendonly
            - "yes"

          ports:
            - containerPort: 6379

          volumeMounts:
            - name: data
              mountPath: /data

          resources:
            requests:
              cpu: 100m
              memory: 256Mi

            limits:
              cpu: 500m
              memory: 512Mi

  volumeClaimTemplates:
    - metadata:
        name: data

      spec:
        accessModes:
          - ReadWriteOnce

        resources:
          requests:
            storage: 10Gi
```

它会形成：

```
redis-0
  │
  └── data PVC
```

## 34.9 PostgreSQL：StatefulSet + PVC

### 34.9.1 为什么 PostgreSQL 更需要持久化

数据库数据不能放在：

```
Container Writable Layer
```

否则：

```
Pod 删除
 ↓
Container 删除
 ↓
数据可能丢失
```

因此需要：

```
PostgreSQL
    ↓
PVC
    ↓
PV
    ↓
Storage
```

------

### 34.9.2 PostgreSQL Service

```
apiVersion: v1
kind: Service

metadata:
  name: postgres

spec:
  clusterIP: None

  selector:
    app: postgres

  ports:
    - port: 5432
      targetPort: 5432
```

------

### 34.9.3 PostgreSQL StatefulSet

教学环境可以用简化配置：

```
apiVersion: apps/v1
kind: StatefulSet

metadata:
  name: postgres

spec:
  serviceName: postgres
  replicas: 1

  selector:
    matchLabels:
      app: postgres

  template:
    metadata:
      labels:
        app: postgres

    spec:
      containers:
        - name: postgres
          image: postgres:16

          env:
            - name: POSTGRES_DB
              value: business

            - name: POSTGRES_USER
              value: business

            - name: POSTGRES_PASSWORD
              valueFrom:
                secretKeyRef:
                  name: postgres-secret
                  key: password

          ports:
            - containerPort: 5432

          volumeMounts:
            - name: data
              mountPath: /var/lib/postgresql/data

          resources:
            requests:
              cpu: 250m
              memory: 512Mi

            limits:
              cpu: "1"
              memory: 1Gi

  volumeClaimTemplates:
    - metadata:
        name: data

      spec:
        accessModes:
          - ReadWriteOnce

        resources:
          requests:
            storage: 50Gi
```

这里必须强调：

> **这个 StatefulSet 只是展示 Kubernetes 部署机制，并不等于生产级 PostgreSQL 高可用方案。**

真正生产数据库还需要考虑：

```
Replication
Backup
Restore
Failover
WAL
Monitoring
Upgrade
Disaster Recovery
```

必要时应该使用成熟的 Database Operator 或托管数据库服务。

## 34.10 Ingress

### 34.10.1 外部访问架构

最终：

```
Internet
   │
   ▼
LoadBalancer
   │
   ▼
Ingress Controller
   │
   ├── example.com
   │       ↓
   │    frontend
   │
   └── api.example.com

          api
```

------

### 34.10.2 Ingress YAML

例如：

```
apiVersion: networking.k8s.io/v1
kind: Ingress

metadata:
  name: business-ingress

spec:
  ingressClassName: nginx

  tls:
    - hosts:
        - example.com
        - api.example.com
      secretName: business-tls

  rules:
    - host: example.com
      http:
        paths:
          - path: /
            pathType: Prefix

            backend:
              service:
                name: frontend
                port:
                  number: 80

    - host: api.example.com
      http:
        paths:
          - path: /
            pathType: Prefix

            backend:
              service:
                name: api
                port:
                  number: 80
```

最终：

```
https://example.com
        ↓
frontend

https://api.example.com
        ↓
api
```

## 34.12 HPA

### 34.12.1 为什么 API 需要 HPA

假设平时：

```
API Pods = 3
```

流量突然增加：

```
CPU
20%
 ↓
70%
 ↓
90%
```

可以让 HPA 自动增加 Pod。

------

### 34.12.2 HPA

```
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler

metadata:
  name: api

spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: api

  minReplicas: 3
  maxReplicas: 10

  behavior:
    scaleUp:
      stabilizationWindowSeconds: 0

    scaleDown:
      stabilizationWindowSeconds: 300

  metrics:
    - type: Resource

      resource:
        name: cpu

        target:
          type: Utilization
          averageUtilization: 70
```

架构：

```
Metrics Server
      │
      ▼
     HPA
      │
      ▼
Deployment
      │
      ▼
Pods
```

注意：

> HPA 不是“CPU 超过 70% 就立即增加一个 Pod”。

它根据当前指标、目标值、当前副本数等计算期望副本数。

## 34.13 Resource Limits

API：

```
resources:
  requests:
    cpu: 200m
    memory: 256Mi

  limits:
    cpu: "1"
    memory: 512Mi
```

它们的意义：

```
requests
 ↓
调度时需要的资源

limits
 ↓
容器允许使用的上限
```

生产环境不能简单地给所有 Pod：

```
requests = limits = 超大值
```

也不能全部不设置。

应该根据：

```
实际负载
监控数据
性能测试
峰值流量
```

逐步调整。

------

## 34.14 Probe

API 至少应该考虑：

```
Startup
Readiness
Liveness
```

推荐理解为：

```
Startup
 ↓
应用是否已经启动完成？

Readiness
 ↓
现在能不能接收流量？

Liveness
 ↓
应用是否已经失去正常工作能力？
```

例如：

```
Pod
 │
 ├── Startup Probe
 │
 ├── Readiness Probe
 │
 └── Liveness Probe
```

最关键的是：

> **Readiness 失败时，Kubernetes 不应该继续把新的 Service 流量发送给这个 Pod。**

## 34.15 RBAC

### 34.15.1 API ServiceAccount

API 不应该默认使用：

```
default
```

可以创建：

```
apiVersion: v1

metadata:
  name: api
```

Deployment：

```
spec:
  template:
    spec:
      serviceAccountName: api
```

------

### 34.15.2 最小权限

如果 API 根本不需要访问 Kubernetes API：

```
不授予任何额外权限
```

如果确实需要：

```
Role
+
RoleBinding
```

只授予：

```
get
list
watch
```

中真正需要的权限。

原则：

> **不要因为方便，给业务 Pod `cluster-admin`。**

## 34.16 NetworkPolicy

### 34.16.1 默认拒绝

生产环境可以采用：

```
Default Deny
+
Explicit Allow
```

例如：

```
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy

metadata:
  name: api-ingress

spec:
  podSelector:
    matchLabels:
      app: api

  policyTypes:
    - Ingress

  ingress:
    - from:
        - podSelector:
            matchLabels:
              app: frontend

      ports:
        - protocol: TCP
          port: 8080
```

表示：

```
frontend
   │
   │ allowed
   ▼
api

其他 Pod
   │
   X
   │
   ▼
api
```

实际生产规则还应该结合：

```
Namespace
Pod Labels
Egress
DNS
Database
Monitoring
```

完整设计。

## 34.19 Loki

### 34.19.1 日志链路

我们的系统：

```
Pod
 │
 └── stdout/stderr
          │
          ▼
      Log Collector
          │
          ▼
         Loki
          │
          ▼
       Grafana
```

例如 API：

```
INFO Request started
INFO User authenticated
ERROR Database timeout
```

不建议把日志主要存储在：

```
Pod 本地磁盘
```

而应该集中收集。

------

### 34.19.2 日志与 Metrics 配合

例如 Grafana：

```
CPU ↑
    │
    └── 对应时间
          ↓
      API Error ↑
          ↓
      Loki Logs
          ↓
      Database timeout
```

这样可以形成：

```
Metrics
+
Logs
+
Traces
```

完整的 Observability 体系。

## 34.28 生产环境必须特别注意的地方

### 34.28.1 不要直接把本章 YAML 原样用于生产

本章的 YAML 是为了把各个 Kubernetes 知识点组合起来。

真正生产环境还需要根据实际环境调整：

```
镜像仓库
StorageClass
Ingress Controller
TLS
数据库方案
资源规格
HPA 参数
NetworkPolicy
RBAC
监控
日志
备份
灾备
```

尤其是：

```
PostgreSQL
Redis
```

不能因为：

```
StatefulSet + PVC
```

就认为已经实现了数据库高可用。

------

### 34.28.2 数据库和业务 Pod 的 HA 是两回事

例如：

```
API
replicas: 3
```

可以比较容易做到：

```
API Pod 1
API Pod 2
API Pod 3
```

但 PostgreSQL：

```
PostgreSQL
replicas: 3
```

**并不意味着 PostgreSQL 自动拥有正确的数据库高可用能力。**

数据库需要额外解决：

```
Replication
Leader Election
Failover
Consistency
Backup
Restore
Storage
```

所以生产数据库通常应该使用：

```
托管数据库
```

或者：

```
成熟 Database Operator
```

而不是简单复制 StatefulSet。
