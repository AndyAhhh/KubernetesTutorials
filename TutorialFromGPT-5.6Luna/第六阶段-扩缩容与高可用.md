# 第 17 章：Horizontal Pod Autoscaler

前面我们学习了资源管理与 Pod 健康检查。

现在进入扩缩容。

在生产环境中，一个应用的负载通常不是固定的：

```
凌晨
10 个请求/秒

上午
100 个请求/秒

中午
500 个请求/秒

活动期间
5000 个请求/秒
```

如果始终运行固定数量的 Pod：

```
replicas: 3
```

可能出现两种问题：

```
Pod 太少
→ CPU/Memory 压力过大
→ 响应变慢
→ 请求失败

Pod 太多
→ 资源浪费
→ 云服务器成本增加
```

HPA（Horizontal Pod Autoscaler）就是 Kubernetes 用来解决这个问题的核心机制。

------

## 17.1 HPA 是什么

### 17.1.1 HPA 的定义

HPA：

> **Horizontal Pod Autoscaler，水平 Pod 自动扩缩容。**

它会根据当前应用负载，自动调整工作负载的 Pod 副本数量。

例如：

```
Deployment
replicas = 3
```

当负载增加：

```
CPU 80%
    ↓
HPA
    ↓
replicas = 6
```

负载下降：

```
CPU 20%
    ↓
HPA
    ↓
replicas = 3
```

因此：

```
Horizontal
    ↓
水平方向增加/减少 Pod 数量
```

而不是：

```
Vertical
    ↓
增加单个 Pod 的 CPU / Memory
```

------

### 17.1.2 HPA 操作的对象

HPA 通常不会直接管理 Pod。

它管理的是一个可扩缩的 workload，例如：

```
Deployment
StatefulSet
```

最常见的是：

```
HPA
 ↓
Deployment
 ↓
ReplicaSet
 ↓
Pods
```

例如：

```
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: api-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: api

  minReplicas: 2
  maxReplicas: 10

  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70
```

这里 HPA 的目标是：

```
Deployment/api
```

而不是某一个具体 Pod。

------

### 17.1.3 HPA 的核心逻辑

可以先把 HPA 简化理解成：

```
监控指标
   ↓
HPA Controller
   ↓
计算需要多少 Pod
   ↓
修改 workload 的 replicas
   ↓
Deployment 创建/删除 Pod
```

例如：

```
CPU = 90%
    ↓
HPA 判断当前副本不足
    ↓
replicas 3 → 5
    ↓
Deployment 创建 2 个 Pod
```

------

## 17.2 为什么需要自动扩容

### 17.2.1 流量具有波动性

现实生产环境中很少存在：

```
24 小时固定负载
```

更常见的是：

```
          流量
           ▲
           │              ╭───╮
           │          ╭───╯   ╰───╮
           │     ╭────╯            ╰──╮
           │─────╯                    ╰────
           └──────────────────────────────→ 时间
```

例如电商：

```
凌晨       低流量
白天       正常
晚间       高流量
促销       极高流量
```

如果固定：

```
replicas: 10
```

就意味着低峰期间也一直占用 10 个 Pod。

------

### 17.2.2 手动扩容的问题

没有 HPA 时，可以：

```
kubectl scale deployment api --replicas=10
```

但是这需要人工判断。

例如凌晨突然流量增加：

```
流量暴涨
 ↓
CPU 暴涨
 ↓
应用变慢
 ↓
运维人员发现
 ↓
执行 kubectl scale
```

已经存在明显延迟。

HPA 可以自动完成这个过程。

------

### 17.2.3 自动扩容解决的是“副本数量”

这一点非常重要。

HPA 解决：

```
Pod 数量不够
```

它不直接解决：

```
Node 数量不够
```

例如：

```
HPA
3 Pod → 10 Pod
```

但集群只有：

```
2 个 Node
```

而 Node 已经没有足够 CPU：

```
10 Pod
    ↓
部分 Pod Pending
```

这时候需要的是：

```
Cluster Autoscaler
```

也就是说：

```
HPA
→ 扩 Pod

Cluster Autoscaler
→ 扩 Node
```

二者可以配合，但不是同一个东西。

------

## 17.3 CPU HPA

### 17.3.1 CPU HPA 是什么

CPU HPA 根据 Pod 的 CPU 使用情况进行扩缩容。

例如目标：

```
CPU 平均使用率 = 70%
```

当前：

```
平均 CPU = 90%
```

HPA 会倾向于增加 Pod。

当前：

```
平均 CPU = 30%
```

HPA 会倾向于减少 Pod。

------

### 17.3.2 CPU Utilization 与 Requests 的关系

这是 CPU HPA 最容易出错的地方。

假设：

```
resources:
  requests:
    cpu: "500m"
```

实际使用：

```
250m
```

CPU Utilization：

```
250m / 500m = 50%
```

如果：

```
averageUtilization: 70
```

那么：

```
50% < 70%
```

不会因为 CPU utilization 达到目标而扩容。

------

### 17.3.3 为什么必须配置 CPU Request

CPU HPA 使用 `Utilization` 时，需要以：

```
CPU Request
```

作为计算基准。

例如：

```
resources:
  requests:
    cpu: "500m"

  limits:
    cpu: "1"
```

HPA：

```
metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 70
```

因此：

```
CPU Request = 500m
目标 = 70%

目标使用量 ≈ 350m
```

如果 Pod 平均使用：

```
500m
```

则：

```
500 / 500 = 100%
```

已经超过目标。

------

### 17.3.4 CPU HPA 示例

完整示例：

```
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api
spec:
  replicas: 2

  selector:
    matchLabels:
      app: api

  template:
    metadata:
      labels:
        app: api

    spec:
      containers:
        - name: api
          image: nginx:1.27

          resources:
            requests:
              cpu: "100m"
              memory: "128Mi"

            limits:
              cpu: "500m"
              memory: "512Mi"

          ports:
            - containerPort: 80
---
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: api-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: api

  minReplicas: 2
  maxReplicas: 10

  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70
```

应用：

```
kubectl apply -f api-hpa.yaml
```

查看：

```
kubectl get hpa
```

可能看到：

```
NAME      REFERENCE          TARGETS   MINPODS   MAXPODS   REPLICAS
api-hpa   Deployment/api     35%/70%   2         10        2
```

------

## 17.4 Memory HPA

### 17.4.1 Memory HPA 是什么

HPA 也可以根据 Memory 使用情况扩缩容。

例如：

```
metrics:
  - type: Resource
    resource:
      name: memory
      target:
        type: Utilization
        averageUtilization: 70
```

表示：

```
Memory 使用率目标 = 70%
```

------

### 17.4.2 Memory Utilization 同样与 Request 有关

例如：

```
resources:
  requests:
    memory: "512Mi"
```

实际使用：

```
384Mi
```

那么：

```
384 / 512 = 75%
```

如果：

```
target = 70%
```

那么已经超过目标。

------

### 17.4.3 CPU 和 Memory 可以同时作为指标

例如：

```
metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 70

  - type: Resource
    resource:
      name: memory
      target:
        type: Utilization
        averageUtilization: 70
```

HPA 会分别计算：

```
CPU 需要多少副本
Memory 需要多少副本
```

然后选择能够满足更高扩容需求的结果。

例如：

```
CPU → 4 Pods
Memory → 7 Pods
```

最终可能扩容到：

```
7 Pods
```

------

### 17.4.4 Memory HPA 的生产注意事项

Memory 与 CPU 有一个重要区别：

CPU 通常是：

```
可压缩资源
```

Memory 通常是：

```
不可压缩资源
```

如果内存持续增加：

```
Memory
 ↓
越来越高
 ↓
OOMKilled
```

所以：

> **Memory HPA 不能替代合理的内存管理。**

尤其对于：

```
.NET
Java
Node.js
```

应用，需要同时关注：

```
Heap
GC
缓存
内存泄漏
Native Memory
Container Memory
```

否则可能出现：

```
Memory 增长
 ↓
HPA 扩容
 ↓
新 Pod 也逐渐增长
 ↓
继续扩容
 ↓
最终整个集群资源耗尽
```

------

## 17.5 Custom Metrics

### 17.5.1 为什么 CPU / Memory 不够

CPU 和 Memory 是基础资源指标。

但是业务系统真正的压力有时候不是 CPU。

例如：

```
HTTP QPS
```

可能：

```
CPU = 30%
QPS = 5000
```

或者：

```
MQ Queue Length = 100000
```

这时候 CPU 并不能准确反映任务堆积程度。

------

### 17.5.2 Custom Metrics 是什么

Custom Metrics：

> **自定义指标。**

例如：

```
HTTP 请求数
请求延迟
Queue Length
Active Connections
业务任务数量
```

可以让 HPA 根据业务指标进行扩缩容。

------

### 17.5.3 示例

假设：

```
每个 Pod 最适合处理：
100 QPS
```

目标：

```
每 Pod 平均 100 QPS
```

那么：

```
200 QPS
→ 2 Pods

500 QPS
→ 5 Pods

1000 QPS
→ 10 Pods
```

这种扩容比单纯：

```
CPU > 70%
```

更贴近业务实际容量。

------

### 17.5.4 Custom Metrics 的实现体系

Kubernetes 原生 HPA 可以消费 Metrics API。

生产环境常见指标体系包括：

```
Application
    ↓
Prometheus
    ↓
Prometheus Adapter
    ↓
Custom Metrics API
    ↓
HPA
```

或者通过其他 metrics adapter 暴露：

```
custom.metrics.k8s.io
```

例如：

```
HTTP QPS
Queue Length
```

转换成 Kubernetes 可以理解的指标。

------

### 17.5.5 Custom Metrics 的生产价值

例如订单系统：

```
CPU = 25%
Memory = 40%
MQ Queue = 50,000
```

CPU 看起来非常健康。

但是：

```
订单队列已经严重堆积
```

如果使用：

```
Queue Length
```

作为扩缩容指标：

```
Queue Length ↑
       ↓
HPA
       ↓
Pod ↑
       ↓
消费速度 ↑
       ↓
Queue Length ↓
```

这才是更合理的自动扩容方式。

------

## 17.6 HPA 工作原理

### 17.6.1 HPA Controller

HPA 的核心组件是：

> **kube-controller-manager 中的 HPA Controller。**

它会周期性检查：

```
当前指标
当前副本数
目标指标
```

然后计算期望副本数。

------

### 17.6.2 基本计算公式

对于资源利用率类指标，可以简单理解为：

```
期望副本数
≈
当前副本数 × 当前指标 / 目标指标
```

例如：

```
当前副本数 = 3
当前 CPU = 90%
目标 CPU = 60%
```

计算：

```
3 × 90 / 60
= 4.5
```

最终会向上取整到合适的整数：

```
5 Pods
```

所以：

```
3 Pods
 ↓
CPU 90%
 ↓
目标 60%
 ↓
HPA
 ↓
约 5 Pods
```

实际控制过程还会受到：

```
minReplicas
maxReplicas
tolerance
behavior
指标采集延迟
Pod readiness
```

等因素影响。

------

### 17.6.3 HPA 不直接创建 Pod

这个概念非常重要。

实际上：

```
HPA
 ↓
修改 Deployment replicas
 ↓
Deployment Controller
 ↓
ReplicaSet
 ↓
创建 Pod
```

所以 HPA 的本质是：

> **自动修改 workload 的期望副本数。**

------

### 17.6.4 HPA 的完整链路

CPU HPA：

```
Container
   ↓
CPU Usage
   ↓
Metrics Server
   ↓
Metrics API
   ↓
HPA Controller
   ↓
Deployment replicas
   ↓
ReplicaSet
   ↓
Pod
```

可以理解成：

```
监控
 ↓
判断
 ↓
计算
 ↓
调整 replicas
 ↓
创建/删除 Pod
```

------

## 17.7 Metrics Server

### 17.7.1 Metrics Server 是什么

Metrics Server 是 Kubernetes 生态中用于提供：

> **资源使用指标**

的组件。

典型包括：

```
CPU
Memory
```

例如：

```
kubectl top nodes
```

可能看到：

```
NAME     CPU(cores)   CPU%   MEMORY(bytes)   MEMORY%
node-1   350m         17%    2Gi            25%
node-2   800m         40%    4Gi            50%
```

Pod：

```
kubectl top pods
```

可能看到：

```
NAME       CPU(cores)   MEMORY(bytes)
api-xxx    120m         180Mi
api-yyy    250m         220Mi
```

------

### 17.7.2 Metrics Server 的作用

简单理解：

```
Kubelet
   ↓
节点/容器资源数据
   ↓
Metrics Server
   ↓
Metrics API
   ↓
kubectl top
HPA
```

因此：

```
kubectl top
```

和：

```
CPU/Memory HPA
```

通常都依赖资源指标 API。

------

### 17.7.3 Metrics Server 不是 Prometheus

这两个非常容易混淆。

Metrics Server：

```
主要用于 Kubernetes 资源使用指标
CPU
Memory
```

Prometheus：

```
完整监控系统
应用指标
业务指标
HTTP QPS
Latency
错误率
数据库指标
Node 指标
```

简单理解：

```
Metrics Server
→ Kubernetes 基础资源指标

Prometheus
→ 更完整的监控与业务指标体系
```

生产环境通常可能：

```
Metrics Server
+
Prometheus
```

同时存在。

------

### 17.7.4 Metrics Server 故障的表现

如果执行：

```
kubectl top pods
```

出现类似：

```
error: Metrics API not available
```

那么 HPA 也可能无法正常获取资源指标。

检查：

```
kubectl get apiservice | grep metrics
```

以及：

```
kubectl get pods -n kube-system
```

查看 Metrics Server。

```
apiVersion: autoscaling/v2
```

```
  maxReplicas: 10

    - type: Resource

        name: cpu
        target:
          type: Utilization
          averageUtilization: 70

    - type: Resource
      resource:
        name: memory
        target:
          type: Utilization
          averageUtilization: 80
```

------

### 17.8.2 查看 HPA

```
kubectl get hpa
```

详细信息：

```
kubectl describe hpa api-hpa
```

重点查看：

```
Metrics
Conditions
Events
Current Replicas
Desired Replicas
```

### 17.8.3 查看 HPA YAML

```
kubectl get hpa api-hpa -o yaml
```

这在生产排障中非常有用。

------

### 17.8.4 查看 Deployment

```
kubectl get deployment api
```

观察：

```
READY
UP-TO-DATE
AVAILABLE
```

再：

```
kubectl get pods -l app=api
```

观察实际 Pod 数量。

------

### 17.8.5 HPA 与 Deployment replicas 的关系

这里有一个非常重要的实践问题。

如果已经使用：

```
HPA
```

那么不要再依赖人工或 GitOps 系统持续把：

```
spec:
  replicas: 2
```

强制覆盖成固定值。

例如：

```
HPA
想要 8 replicas
```

但是 GitOps 每隔一段时间又应用：

```
replicas: 2
```

可能形成：

```
HPA → 8
GitOps → 2
HPA → 8
GitOps → 2
```

造成控制器互相“打架”。

生产环境需要明确：

> **谁负责管理 replicas。**

通常让 HPA 动态控制。

## 17.9 扩容与缩容行为

### 17.9.1 扩容

假设：

```
minReplicas = 2
maxReplicas = 10
CPU target = 70%
```

当前：

```
2 Pods
CPU = 95%
```

HPA 判断需要更多 Pod：

```
2
 ↓
4
 ↓
6
```

实际具体步长由计算结果和行为策略决定。

------

### 17.9.2 为什么扩容不是瞬间完成

HPA 只能做：

```
修改 replicas
```

后面还需要：

```
Scheduler
 ↓
找到 Node
 ↓
拉镜像
 ↓
创建 Container
 ↓
Startup Probe
 ↓
Readiness Probe
 ↓
Ready
```

所以：

```
HPA 扩容
```

不等于：

```
Pod 立即可以处理流量
```

完整链路：

```
负载增加
 ↓
指标上升
 ↓
Metrics Server 采集
 ↓
HPA 发现
 ↓
计算
 ↓
修改 replicas
 ↓
Scheduler 调度
 ↓
Pod 启动
 ↓
Readiness 成功
 ↓
Service 开始发送流量
```

这意味着：

> **HPA 是有反应时间的。**

生产系统不能假设它可以瞬间应对流量暴涨。

------

### 17.9.3 缩容

负载下降：

```
CPU = 20%
```

目标：

```
70%
```

HPA 会逐步降低副本数。

例如：

```
10
 ↓
8
 ↓
6
 ↓
4
 ↓
2
```

缩容通常不会像扩容一样激进。

原因是：

> **避免负载刚下降就大量删除 Pod，随后流量又上升导致频繁扩缩容。**

这就是所谓：

```
Flapping
```

也叫：

```
扩缩容抖动
```

------

### 17.9.4 stabilization

HPA 支持：

```
behavior:
```

控制扩缩容行为。

例如：

```
behavior:
  scaleDown:
    stabilizationWindowSeconds: 300
```

可以理解成：

> 缩容前观察一段时间，避免负载短暂下降就立即缩容。

------

### 17.9.5 控制扩容速度

例如：

```
behavior:
  scaleUp:
    policies:
      - type: Percent
        value: 100
        periodSeconds: 60

    selectPolicy: Max
```

表示在指定时间窗口内限制扩容速度。

实际生产环境需要根据：

```
业务流量
Pod 启动速度
镜像大小
应用初始化时间
Node 资源
```

进行调整。

------

### 17.9.6 一个生产级示例

```
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: api-hpa

spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: api

  minReplicas: 3
  maxReplicas: 20

  behavior:
    scaleUp:
      stabilizationWindowSeconds: 0

      policies:
        - type: Percent
          value: 100
          periodSeconds: 60

        - type: Pods
          value: 4
          periodSeconds: 60

      selectPolicy: Max

    scaleDown:
      stabilizationWindowSeconds: 300

      policies:
        - type: Percent
          value: 25
          periodSeconds: 60

      selectPolicy: Max

  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70

    - type: Resource
      resource:
        name: memory
        target:
          type: Utilization
          averageUtilization: 80
```

这里的思路是：

```
扩容
→ 可以相对积极

缩容
→ 更谨慎
→ 等待 300 秒稳定观察
```

实际生产值不能照抄，需要根据业务压测结果调整。

------

## 17.10 HPA 常见问题

### 17.10.1 HPA 显示 `<unknown>`

例如：

```
kubectl get hpa
```

看到：

```
NAME      REFERENCE       TARGETS         MINPODS   MAXPODS
api-hpa   Deployment/api  <unknown>/70%   2         10
```

常见原因：

```
Metrics Server 不正常
Metrics API 不可用
Pod 没有 CPU Request
指标获取异常
```

先检查：

```
kubectl top pods
```

如果：

```
kubectl top pods
```

本身就失败：

```
Metrics Server / Metrics API
```

是重点排查方向。

------

### 17.10.2 没有设置 CPU Request

例如：

```
resources:
  limits:
    cpu: "1"
```

但是：

```
requests:
  cpu:
```

没有设置。

如果 HPA 使用：

```
type: Utilization
```

那么 CPU 利用率无法按照正常 Request 基准计算。

正确做法通常是：

```
resources:
  requests:
    cpu: "200m"
    memory: "256Mi"

  limits:
    cpu: "1"
    memory: "512Mi"
```

------

### 17.10.3 HPA 不扩容

排查：

```
kubectl get hpa
```

然后：

```
kubectl describe hpa api-hpa
```

重点看：

```
Metrics
Conditions
Events
```

再看：

```
kubectl top pods
```

确认实际资源使用。

然后：

```
kubectl get deployment api
```

确认 HPA 目标是否正确。

------

### 17.10.4 HPA 想扩容，但是 Pod Pending

例如：

```
HPA
 ↓
replicas = 10
```

但是：

```
Pod
Pending
```

查看：

```
kubectl get pods
kubectl describe pod <pod-name>
```

如果看到：

```
Insufficient cpu
```

或者：

```
Insufficient memory
```

说明：

> **HPA 已经正常工作，但集群没有足够 Node 资源容纳新的 Pod。**

这时候问题不是 HPA，而是：

```
Cluster Capacity
```

生产环境可能需要：

```
HPA
+
Cluster Autoscaler
```

协同工作。

------

### 17.10.5 HPA 不缩容

可能原因：

```
当前指标仍然高
缩容稳定窗口尚未结束
minReplicas 已经达到
其他指标仍然要求更多副本
```

例如：

```
CPU = 20%
Memory = 85%
```

虽然 CPU 很低：

```
CPU → 可以缩容
```

但：

```
Memory → 不能缩容
```

最终 HPA 会综合指标选择更高的副本需求。

------

### 17.10.6 HPA 频繁扩缩容

例如：

```
3 → 8 → 3 → 8 → 3 → 8
```

这通常意味着：

> **扩缩容系统存在抖动。**

可能原因：

```
目标值设置不合理
Pod 启动时间过长
业务流量本身波动很大
指标采集存在延迟
缩容过于激进
应用启动后 CPU 突然升高
```

可以考虑：

```
behavior:
  scaleDown:
    stabilizationWindowSeconds: 300
```

同时重新评估：

```
minReplicas
maxReplicas
CPU target
Memory target
Pod 启动时间
```

------

### 17.10.7 HPA 与 Deployment 冲突

例如：

```
Deployment
replicas: 3
```

HPA：

```
desiredReplicas: 8
```

如果某个自动化系统不断执行：

```
kubectl apply -f deployment.yaml
```

把：

```
replicas: 3
```

重新写回去，就可能造成：

```
HPA → 8
Deployment YAML → 3
HPA → 8
Deployment YAML → 3
```

因此生产环境需要避免多个控制器同时管理：

```
replicas
```

------

### 17.10.8 HPA 并不能保证高可用

这是非常重要的一点。

假设：

```
minReplicas: 2
maxReplicas: 10
```

HPA 只能保证：

```
负载高 → 尝试增加 Pod
```

它不能保证：

```
Pod 一定分布在不同 Node
```

例如：

```
Node 1
├── Pod A
└── Pod B

Node 2
```

如果 Node 1 挂掉：

```
Pod A
Pod B
↓
全部丢失
```

因此：

> **HPA 负责弹性，调度机制负责分布，高可用需要多个机制共同完成。**

这也是生产环境设计时必须建立的整体认识：

```
HPA
→ Pod 数量

Scheduler / Affinity / Topology Spread
→ Pod 分布

Cluster Autoscaler
→ Node 数量

Readiness Probe
→ 流量接入

Liveness Probe
→ 异常恢复
```

------

### 17.10.9 生产环境使用 HPA 的基本原则

一个比较可靠的生产架构通常是：

```
                 Internet
                    │
                    ▼
                 Ingress
                    │
                    ▼
                 Service
                    │
          ┌─────────┼─────────┐
          ▼         ▼         ▼
        Pod       Pod       Pod
          │         │         │
          └─────────┼─────────┘
                    │
                 Deployment
                    ▲
                    │
                   HPA
                    ▲
                    │
             Metrics / Metrics Server
```

如果进一步实现集群级自动扩容：

```
                    HPA
                     │
                     ▼
                Pod 数量增加
                     │
                     ▼
                Node 资源不足
                     │
                     ▼
             Cluster Autoscaler
                     │
                     ▼
                Node 数量增加
```

因此需要明确区分：

```
HPA
Horizontal Pod Autoscaler
→ 扩 Pod

VPA
Vertical Pod Autoscaler
→ 调整 Pod 资源

Cluster Autoscaler
→ 扩 Node
```

三者解决的是不同层级的问题。

对于生产环境，一个比较合理的 HPA 思路通常是：

```
Deployment
  │
  ├── 合理 requests / limits
  │
  ├── Startup Probe
  ├── Readiness Probe
  └── Liveness Probe
       │
       ▼
      HPA
       │
       ├── minReplicas
       ├── maxReplicas
       ├── CPU / Memory
       └── Custom Metrics
```

最终形成：

```
流量增加
   ↓
应用负载增加
   ↓
Metrics
   ↓
HPA
   ↓
replicas 增加
   ↓
Deployment 创建 Pod
   ↓
Scheduler 调度
   ↓
Pod 启动
   ↓
Readiness 成功
   ↓
Service 接入流量
```

而流量下降：

```
负载下降
   ↓
Metrics
   ↓
HPA
   ↓
等待稳定窗口
   ↓
replicas 减少
   ↓
Pod 优雅终止
```

## 本章核心知识

> **HPA 不是“监控 CPU 然后自动创建 Pod”的独立系统，而是 Kubernetes 控制器根据指标计算期望副本数，并通过修改 workload 的 replicas，让 Kubernetes 自身完成扩缩容。**

同时必须牢记：

```
CPU / Memory
→ 基础资源指标

Custom Metrics
→ 业务指标

Metrics Server
→ 提供 CPU / Memory 等资源指标

HPA
→ 决定 Pod 副本数量

Deployment
→ 实际负责创建/删除 Pod

Cluster Autoscaler
→ 解决 Node 容量不足
```

这样才能真正理解 HPA 在生产 Kubernetes 集群中的位置。

# 第 18 章：高可用设计

高可用（High Availability，HA）是生产 Kubernetes 环境非常重要的能力。

前面的章节我们已经分别学习了：

- Deployment：管理无状态应用副本
- Service：提供稳定的服务访问入口
- StatefulSet：运行有状态应用
- Resource：控制 Pod 的资源使用
- Scheduler：决定 Pod 运行在哪个 Node
- Probe：判断应用是否健康
- HPA：根据负载自动调整 Pod 数量

现在需要把这些能力组合起来。

一个生产 API 服务不能只考虑：

```
Pod 挂了怎么办？
```

而应该考虑整个故障链：

```
Container 故障
      ↓
Pod 故障
      ↓
Node 故障
      ↓
机房 / Availability Zone 故障
      ↓
Service / Ingress 故障
      ↓
整个应用还能不能继续提供服务？
```

所以：

> **Kubernetes 高可用不是某一个 Kubernetes 对象，而是一套从应用、Pod、Node、网络、存储到基础设施的整体设计。**

------

## 18.1 Kubernetes 高可用到底是什么

### 18.1.1 什么是高可用

高可用的核心目标是：

> **当部分组件发生故障时，系统仍然能够继续提供服务。**

例如一个 API 服务：

```
正常：

             Service
                │
       ┌────────┼────────┐
       ▼        ▼        ▼
     Pod A    Pod B    Pod C
```

如果 Pod A 挂掉：

```
             Service
                │
          ┌─────┴─────┐
          ▼           ▼
        Pod B       Pod C

        Pod A ×
```

只要还有健康 Pod：

```
Pod B
Pod C
```

Service 就可以继续处理请求。

这就是最基础的高可用。

------

### 18.1.2 高可用不是“永远不故障”

这是初学者非常容易产生的误解。

不存在：

```
100% 永不故障
```

高可用真正追求的是：

```
故障发生
   ↓
快速发现
   ↓
自动恢复 / 切换
   ↓
减少服务中断时间
```

例如：

```
Node-1 故障
     ↓
Pod 消失
     ↓
Deployment 发现副本不足
     ↓
创建新 Pod
     ↓
Scheduler 调度到 Node-2
     ↓
Readiness Probe 成功
     ↓
Service 恢复流量
```

整个过程中可能会存在短暂影响，但系统能够自动恢复。

------

### 18.1.3 Kubernetes 高可用的几个层次

可以把生产环境高可用分成：

```
应用层
 ↓
Pod 层
 ↓
Node 层
 ↓
Service / Ingress 层
 ↓
Availability Zone 层
 ↓
Cluster / Region 层
```

不同层解决不同故障。

例如：

| 故障                       | 主要解决机制                    |
| -------------------------- | ------------------------------- |
| Container 崩溃             | RestartPolicy / kubelet         |
| Pod 故障                   | Deployment                      |
| Node 故障                  | Scheduler + Deployment          |
| Pod 集中在一个 Node        | Anti-Affinity / Topology Spread |
| 维护导致 Pod 被驱逐        | PDB                             |
| Pod 更新                   | Rolling Update                  |
| 单个 Service Endpoint 故障 | Service + Readiness             |
| 一个 AZ 故障               | 多 AZ                           |
| 整个集群故障               | 多集群 / 灾备                   |

------

## 18.2 Pod 高可用

### 18.2.1 单 Pod 为什么不高可用

假设：

```
spec:
  replicas: 1
```

实际上：

```
Service
   │
   ▼
Pod A
```

如果：

```
Pod A
  ↓
Crash
```

在新 Pod Ready 之前：

```
Service
   │
   X
```

因此：

> **单副本 Pod 本身不是高可用架构。**

------

### 18.2.2 多副本

最基本的高可用方式：

```
spec:
  replicas: 3
```

形成：

```
             Service
          ┌────┼────┐
          ▼    ▼    ▼
        Pod A Pod B Pod C
```

如果 Pod A 挂掉：

```
             Service
              │
          ┌───┴───┐
          ▼       ▼
        Pod B   Pod C
```

Deployment 会尝试重新创建缺失副本。

------

### 18.2.3 为什么生产环境通常至少 2～3 副本

假设：

```
replicas = 1
```

一个 Pod 故障：

```
可用 Pod = 0
```

如果：

```
replicas = 2
```

一个 Pod 故障：

```
可用 Pod = 1
```

如果：

```
replicas = 3
```

一个 Pod 故障：

```
可用 Pod = 2
```

因此：

```
replicas = 3
```

通常比：

```
replicas = 1
```

具有明显更好的故障容忍能力。

但不能简单认为：

> 副本越多，高可用越高。

还需要考虑：

```
Pod 分布
Node 数量
AZ 数量
数据库容量
连接数
成本
```

------

### 18.2.4 多副本不等于真正高可用

例如：

```
Node-1
├── Pod A
├── Pod B
└── Pod C
```

虽然：

```
replicas = 3
```

但是三个 Pod 都在同一个 Node。

如果：

```
Node-1
   ↓
宕机
```

结果：

```
Pod A ×
Pod B ×
Pod C ×
```

所以：

> **副本数量只是第一步，副本分布同样重要。**

------

## 18.3 Node 高可用

### 18.3.1 Node 是什么角色

Pod 最终运行在 Node 上：

```
Cluster
 │
 ├── Node-1
 │    ├── Pod
 │    └── Pod
 │
 ├── Node-2
 │    ├── Pod
 │    └── Pod
 │
 └── Node-3
      └── Pod
```

如果只有一个 Node：

```
Cluster
 │
 └── Node-1
      ├── Pod A
      ├── Pod B
      └── Pod C
```

那么：

```
Node-1 故障
     ↓
所有 Pod 都无法运行
```

因此生产集群至少应该具备多个 Node。

------

### 18.3.2 Node 故障时发生什么

假设：

```
Node-1
   ├── Pod A
   └── Pod B

Node-2
   └── Pod C
```

Node-1 故障：

```
Node-1 ×

Pod A ×
Pod B ×
```

Deployment 发现：

```
desired replicas = 3
available replicas = 1
```

于是 Kubernetes 会创建新的 Pod：

```
Node-2
   ├── Pod C
   ├── Pod A'
   └── Pod B'
```

如果 Node-2 有足够资源，就可以恢复。

如果没有：

```
Pod A' → Pending
Pod B' → Pending
```

这说明：

> **Node 高可用不仅需要多个 Node，还需要足够的集群容量。**

------

## 18.4 Service 高可用

### 18.4.1 Service 本身解决什么问题

Service 提供一个稳定的访问入口：

```
Client
  ↓
Service
  ↓
Pod
```

Pod 可以不断变化：

```
Pod A → 删除
Pod B → 创建
Pod C → 重建
```

但 Service 地址保持稳定。

------

### 18.4.2 Service 与高可用

例如：

```
             Service
          /     |     \
         /      |      \
      Pod A   Pod B   Pod C
```

如果 Pod A 不健康：

```
             Service
              /   \
             /     \
          Pod B   Pod C
```

Service 不应该继续把正常流量发送给：

```
Pod A
```

这里就依赖：

```
Readiness Probe
```

例如：

```
readinessProbe:
  httpGet:
    path: /health/ready
    port: 8080

  initialDelaySeconds: 5
  periodSeconds: 5
```

应用未 Ready：

```
Pod
 ↓
NotReady
 ↓
EndpointSlice 移除 / 不再作为正常流量目标
```

所以：

> **Service 高可用的关键之一，是只把流量发送给真正可以处理请求的 Pod。**

------

## 18.5 Deployment 高可用

### 18.5.1 Deployment 为什么能够提高可用性

Deployment 管理：

```
ReplicaSet
   ↓
Pods
```

例如：

```
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api

spec:
  replicas: 3

  selector:
    matchLabels:
      app: api

  template:
    metadata:
      labels:
        app: api

    spec:
      containers:
        - name: api
          image: nginx:1.27
```

Deployment 的目标是：

```
desired = 3
```

如果：

```
actual = 2
```

Deployment 会尝试恢复：

```
2 → 3
```

因此它具有：

```
副本管理
故障恢复
版本更新
```

等能力。

------

### 18.5.2 Deployment 本身不是完整高可用方案

Deployment 能够：

```
保证副本数量
```

但它不能单独保证：

```
副本分布
Node 高可用
AZ 高可用
数据库高可用
```

所以生产设计必须组合其他 Kubernetes 机制。

------

## 18.6 多副本

### 18.6.1 多副本的基本原则

对于无状态 API：

```
replicas >= 2
```

通常是高可用的起点。

例如：

```
spec:
  replicas: 3
```

完整示例：

```
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api

spec:
  replicas: 3

  selector:
    matchLabels:
      app: api

  template:
    metadata:
      labels:
        app: api

    spec:
      containers:
        - name: api
          image: my-api:1.0.0
          ports:
            - containerPort: 8080

          readinessProbe:
            httpGet:
              path: /health/ready
              port: 8080

          livenessProbe:
            httpGet:
              path: /health/live
              port: 8080
```

------

### 18.6.2 多副本的前提

多副本 API 必须尽量做到：

```
Pod A
Pod B
Pod C
```

之间：

```
无本地状态依赖
```

例如不要把用户 Session 只存：

```
Pod A 内存
```

否则：

```
请求 1 → Pod A
Session → Pod A Memory

请求 2 → Pod B
Session 找不到
```

更合理的是使用：

```
Redis
Database
External Session Store
```

等共享状态存储。

这也是为什么：

> **无状态应用非常适合 Deployment + HPA。**

------

## 18.7 Pod Anti-Affinity

### 18.7.1 为什么需要 Anti-Affinity

前面我们已经看到：

```
3 Pod
```

并不意味着：

```
3 个不同 Node
```

可以通过：

```
Pod Anti-Affinity
```

告诉 Scheduler：

> 尽量不要把这些 Pod 放在一起。

------

### 18.7.2 基本示例

假设：

```
app=api
```

使用：

```
affinity:
  podAntiAffinity:
    preferredDuringSchedulingIgnoredDuringExecution:
      - weight: 100
        podAffinityTerm:
          topologyKey: kubernetes.io/hostname

          labelSelector:
            matchExpressions:
              - key: app
                operator: In
                values:
                  - api
```

这里：

```
topologyKey: kubernetes.io/hostname
```

意味着以：

```
Node
```

为拓扑边界。

Scheduler 会尽量让：

```
api Pod
```

分散到不同 Node。

------

### 18.7.3 preferred 和 required

有两种常见模式。

#### preferred

```
preferredDuringSchedulingIgnoredDuringExecution:
```

意思是：

> **尽量遵守，但实在无法满足也可以调度。**

适合生产环境中比较灵活的分布要求。

------

#### required

```
requiredDuringSchedulingIgnoredDuringExecution:
```

意思是：

> **必须满足，否则不允许调度。**

例如：

```
同一个 Node 绝对不能出现两个 API Pod
```

但是如果只有一个 Node：

```
Pod A → Node-1
Pod B → 无法调度
```

这可能导致 Pod Pending。

所以：

> **强制 Anti-Affinity 必须结合实际 Node 数量设计。**

------

## 18.8 PodDisruptionBudget

### 18.8.1 PDB 是什么

PDB：

> **PodDisruptionBudget**

用于限制：

> **在自愿中断（Voluntary Disruption）期间，同时可以被中断的 Pod 数量。**

例如：

```
replicas = 3
```

设置：

```
minAvailable: 2
```

意思是：

```
至少保持 2 个 Pod 可用
```

------

### 18.8.2 为什么需要 PDB

生产环境经常需要：

```
Node 升级
Node Drain
集群维护
节点迁移
```

例如：

```
kubectl drain node-1
```

如果没有合理保护：

```
Pod A
Pod B
Pod C
```

可能同时被驱逐。

这样：

```
可用 Pod = 0
```

服务中断。

PDB 可以告诉 Kubernetes：

```
最多只能同时中断一部分 Pod
```

------

### 18.8.3 PDB 示例

```
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: api-pdb

spec:
  minAvailable: 2

  selector:
    matchLabels:
      app: api
```

配合：

```
replicas: 3
```

可以形成：

```
3 Pods
 │
 ├── Pod A
 ├── Pod B
 └── Pod C

PDB:
至少保持 2 个可用
```

------

### 18.8.4 maxUnavailable

也可以写：

```
spec:
  maxUnavailable: 1
```

意思是：

```
最多允许 1 个 Pod 同时因为自愿中断而不可用
```

二者选择一种即可。

例如：

```
minAvailable: 2
```

或者：

```
maxUnavailable: 1
```

对于：

```
replicas = 3
```

两者在这个例子中的效果类似。

------

### 18.8.5 PDB 不是什么

PDB **不是**：

```
Pod 故障自动恢复机制
```

也不是：

```
Node 故障保护机制
```

它主要保护：

```
Voluntary Disruption
```

例如：

```
kubectl drain
节点维护
部分集群运维操作
```

如果：

```
Node 突然断电
```

这属于：

```
Involuntary Disruption
```

PDB 不能阻止这种故障。

------

## 18.9 Rolling Update

### 18.9.1 Rolling Update 是什么

Rolling Update：

> **滚动更新。**

更新应用版本时：

```
旧版本 Pod
```

不会全部同时删除，而是：

```
旧版本
 ↓
逐渐减少

新版本
 ↓
逐渐增加
```

例如：

```
v1:
Pod A
Pod B
Pod C
```

更新到 v2：

```
v1: Pod B
v1: Pod C
v2: Pod D
```

然后：

```
v1: Pod C
v2: Pod D
v2: Pod E
```

最终：

```
v2: Pod D
v2: Pod E
v2: Pod F
```

------

### 18.9.2 RollingUpdate 配置

Deployment 默认使用 RollingUpdate。

可以显式设置：

```
strategy:
  type: RollingUpdate

  rollingUpdate:
    maxUnavailable: 0
    maxSurge: 1
```

含义：

```
maxUnavailable: 0
```

尽量保证更新期间原有可用副本不减少。

```
maxSurge: 1
```

允许临时多创建一个 Pod。

------

### 18.9.3 为什么生产环境很重要

例如：

```
3 个 API Pod
```

如果使用：

```
Recreate
```

可能变成：

```
旧 Pod 全部删除
      ↓
新 Pod 创建
```

中间可能出现：

```
0 个 Pod
```

导致服务中断。

Rolling Update 则尽量保持：

```
旧 Pod + 新 Pod
```

共同工作。

------

### 18.9.4 Rolling Update 的前提

Rolling Update 要真正实现无感更新，需要：

```
Readiness Probe
+
合理的 maxUnavailable
+
合理的 maxSurge
+
应用能够兼容新旧版本
```

尤其是：

> **数据库 Schema 必须考虑向前/向后兼容。**

否则：

```
v1 API
 ↓
旧数据库结构

v2 API
 ↓
新数据库结构
```

更新过程中可能出现兼容性问题。

------

## 18.10 多节点

生产 Kubernetes 集群至少要考虑：

```
多个 Node
```

例如：

```
Node-1
Node-2
Node-3
```

API：

```
Pod A → Node-1
Pod B → Node-2
Pod C → Node-3
```

此时：

```
Node-1 故障
```

还有：

```
Pod B
Pod C
```

继续提供服务。

------

### 18.10.1 Node 数量与 Pod 副本数量的关系

例如：

```
3 Pods
3 Nodes
```

比较理想：

```
Pod A → Node-1
Pod B → Node-2
Pod C → Node-3
```

但是如果：

```
3 Pods
1 Node
```

那么：

```
Node-1
├── Pod A
├── Pod B
└── Pod C
```

Node 一挂：

```
全部消失
```

因此：

> **Pod 副本数和 Node 数量必须一起考虑。**

------

### 18.10.2 Node 容量也必须考虑

假设：

```
3 Nodes
```

每个 Node 只能容纳：

```
2 个 API Pod
```

那么最多：

```
6 Pods
```

如果 HPA：

```
3 → 10
```

其中：

```
6 Running
4 Pending
```

所以高可用必须同时考虑：

```
副本数量
+
Node 数量
+
Node 容量
```

------

## 18.11 多可用区

### 18.11.1 为什么需要多 AZ

单 Node 高可用还不够。

假设云厂商：

```
Region
└── AZ-A
    ├── Node-1
    ├── Node-2
    └── Node-3
```

如果整个：

```
AZ-A
```

发生故障：

```
Node-1 ×
Node-2 ×
Node-3 ×
```

即使 Pod 分散到三个 Node：

```
全部失效
```

因此更高级的高可用设计是：

```
Region
│
├── AZ-A
│   ├── Node-1
│   └── Node-2
│
├── AZ-B
│   ├── Node-3
│   └── Node-4
│
└── AZ-C
    ├── Node-5
    └── Node-6
```

------

### 18.11.2 Topology Spread

生产环境推荐结合：

```
Topology Spread Constraints
```

让 Pod 尽量均匀分布到：

```
Node
AZ
```

例如：

```
topologySpreadConstraints:
  - maxSkew: 1

    topologyKey: topology.kubernetes.io/zone

    whenUnsatisfiable: DoNotSchedule

    labelSelector:
      matchLabels:
        app: api
```

含义：

```
api Pod
 ↓
尽量均匀分布在不同 Zone
```

例如：

```
AZ-A: 2 Pods
AZ-B: 2 Pods
AZ-C: 1 Pod
```

而不是：

```
AZ-A: 5 Pods
AZ-B: 0 Pods
AZ-C: 0 Pods
```

------

### 18.11.3 多 AZ 的成本

多 AZ 并不是没有代价。

通常会增加：

```
Node 成本
跨 AZ 网络成本
负载均衡成本
存储复杂度
运维复杂度
```

所以生产环境要根据：

```
SLA
业务重要程度
RTO
RPO
成本
```

决定是否需要多 AZ。

------

## 18.12 故障场景演练

真正理解高可用，不能只看 YAML。

需要进行故障演练。

------

### 18.12.1 场景一：Pod 被删除

当前：

```
Deployment
replicas = 3
```

查看：

```
kubectl get pods -l app=api
```

手动删除一个：

```
kubectl delete pod <pod-name>
```

观察：

```
kubectl get pods -l app=api -w
```

你会看到：

```
Pod A
Pod B
Pod C
```

删除：

```
Pod A ×
```

然后 Deployment 创建：

```
Pod A' → Pending → Running
```

最终恢复：

```
Pod B
Pod C
Pod A'
```

这验证了：

> Deployment 的副本自愈能力。

------

### 18.12.2 场景二：应用进程崩溃

如果容器主进程退出：

```
Container
   ↓
Exit
```

kubelet 会根据：

```
restartPolicy
```

决定是否重新启动。

Deployment 还会保证：

```
Pod Replica 数量
```

所以：

```
Container Recovery
+
Pod Recovery
```

共同构成应用自愈能力。

------

### 18.12.3 场景三：Pod 不健康

例如 Readiness Probe：

```
readinessProbe:
  httpGet:
    path: /health/ready
    port: 8080
```

如果接口返回：

```
500
```

Pod 会变成：

```
NotReady
```

Service 不应该继续向它发送正常业务流量。

因此：

```
Pod 还活着
```

不代表：

```
Pod 可以接收流量
```

这是生产环境非常重要的区别。

------

### 18.12.4 场景四：Node 故障

假设：

```
Node-1
├── Pod A
└── Pod B

Node-2
└── Pod C
```

Node-1 故障。

最终目标：

```
Node-2
├── Pod C
├── Pod A'
└── Pod B'
```

前提是：

```
Node-2
```

有足够资源。

如果没有：

```
Pod A' → Pending
Pod B' → Pending
```

这说明：

> **高可用设计必须保留故障后的容量余量。**

------

### 18.12.5 场景五：Node Drain

模拟维护：

```
kubectl drain <node-name> \
  --ignore-daemonsets \
  --delete-emptydir-data
```

观察：

```
kubectl get pods -o wide -w
```

PDB 可以限制：

```
同时被驱逐的 Pod 数量
```

如果：

```
replicas = 3
minAvailable = 2
```

那么维护过程中应该尽量保证：

```
≥ 2 个 Pod
```

可用。

------

### 18.12.6 场景六：整个 AZ 故障

假设：

```
AZ-A
├── Pod A
├── Pod B
└── Pod C

AZ-B
├── Pod D
└── Pod E
```

如果：

```
AZ-A ×
```

剩余：

```
Pod D
Pod E
```

还可以提供服务。

但是，如果所有 Pod 都在：

```
AZ-A
```

那么：

```
AZ-A ×
→ 服务整体不可用
```

这就是多 AZ 的核心价值。

------

## 18.13 如何设计一个真正高可用的 API 服务

现在把整个章节组合起来。

假设我们要部署：

```
订单 API
```

目标：

```
生产环境
高可用
支持自动扩容
支持滚动更新
能够容忍单 Pod 故障
能够容忍单 Node 故障
```

------

### 18.13.1 第一层：Deployment

```
apiVersion: apps/v1
kind: Deployment
metadata:
  name: order-api

spec:
  replicas: 3

  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 0
      maxSurge: 1

  selector:
    matchLabels:
      app: order-api

  template:
    metadata:
      labels:
        app: order-api

    spec:
      containers:
        - name: order-api
          image: example/order-api:1.0.0

          ports:
            - containerPort: 8080

          resources:
            requests:
              cpu: "250m"
              memory: "256Mi"

            limits:
              cpu: "1"
              memory: "512Mi"

          startupProbe:
            httpGet:
              path: /health/startup
              port: 8080
            failureThreshold: 30
            periodSeconds: 2

          readinessProbe:
            httpGet:
              path: /health/ready
              port: 8080
            periodSeconds: 5

          livenessProbe:
            httpGet:
              path: /health/live
              port: 8080
            periodSeconds: 10
```

这里已经组合了：

```
3 副本
+
Rolling Update
+
Resource
+
Startup Probe
+
Readiness Probe
+
Liveness Probe
```

------

### 18.13.2 第二层：Pod 分散

进一步加入：

```
topologySpreadConstraints:
  - maxSkew: 1
    topologyKey: kubernetes.io/hostname
    whenUnsatisfiable: DoNotSchedule
    labelSelector:
      matchLabels:
        app: order-api
```

使 Pod 尽量分散到不同 Node。

如果集群支持多 AZ，还可以：

```
topologySpreadConstraints:
  - maxSkew: 1
    topologyKey: topology.kubernetes.io/zone
    whenUnsatisfiable: DoNotSchedule
    labelSelector:
      matchLabels:
        app: order-api
```

这样形成：

```
AZ-A                  AZ-B                  AZ-C
 │                     │                     │
Node-1                Node-3                Node-5
 │                     │                     │
Pod A                 Pod B                 Pod C
```

------

### 18.13.3 第三层：Service

```
apiVersion: v1
kind: Service
metadata:
  name: order-api

spec:
  selector:
    app: order-api

  ports:
    - port: 80
      targetPort: 8080

  type: ClusterIP
```

形成：

```
Client
  ↓
Service
  ↓
┌───────────────┐
│               │
Pod A          Pod B          Pod C
```

Readiness Probe 保证：

```
只有 Ready Pod
```

正常接收业务流量。

------

### 18.13.4 第四层：PDB

```
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: order-api-pdb

spec:
  minAvailable: 2

  selector:
    matchLabels:
      app: order-api
```

这样：

```
3 Pods
```

维护期间尽量保证：

```
≥ 2 Pods
```

可用。

------

### 18.13.5 第五层：HPA

例如：

```
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: order-api-hpa

spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: order-api

  minReplicas: 3
  maxReplicas: 20

  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70
```

于是：

```
正常流量
→ 3 Pods

高流量
→ 5 Pods

更高流量
→ 10 Pods

峰值
→ 最多 20 Pods
```

------

### 18.13.6 第六层：Node 容量

假设：

```
3 AZ
```

每个 AZ：

```
2 Nodes
```

形成：

```
Region
│
├── AZ-A
│   ├── Node-1
│   └── Node-2
│
├── AZ-B
│   ├── Node-3
│   └── Node-4
│
└── AZ-C
    ├── Node-5
    └── Node-6
```

API：

```
Pod A → AZ-A
Pod B → AZ-B
Pod C → AZ-C
```

这样可以同时降低：

```
Pod 故障
Node 故障
AZ 故障
```

对整体服务的影响。

------

### 18.13.7 最终生产架构

整体可以理解为：

```
                    Internet
                       │
                       ▼
                    Ingress
                       │
                       ▼
                    Service
                       │
          ┌────────────┼────────────┐
          │            │            │
          ▼            ▼            ▼
       Pod A         Pod B        Pod C
       AZ-A          AZ-B         AZ-C
          │            │            │
          └────────────┼────────────┘
                       │
                  Deployment
                       ▲
                       │
                      HPA
                       ▲
                       │
                 Metrics Server


Pod Distribution
        │
        ├── Topology Spread
        └── Anti-Affinity

Node Maintenance
        │
        └── PDB

Application Update
        │
        └── Rolling Update
```

------

### 18.13.8 真正的高可用还要考虑应用本身

Kubernetes 能够解决：

```
Pod
Node
Service
Deployment
```

层面的很多问题。

但是 Kubernetes 无法自动解决：

```
代码 Bug
数据库故障
Redis 故障
第三方 API 故障
数据损坏
错误的数据库 Migration
错误配置
业务逻辑异常
```

例如：

```
API Pod ×
```

Kubernetes 可以重新创建。

但如果：

```
Database ×
```

所有 API Pod 都可能变成：

```
无法处理请求
```

所以真正生产级的高可用架构通常是：

```
                 Load Balancer
                       │
                    Ingress
                       │
                    Service
                       │
          ┌────────────┼────────────┐
          ▼            ▼            ▼
        API-1        API-2        API-3
          │            │            │
          └────────────┼────────────┘
                       │
                 Database Cluster
                       │
                 Redis Cluster
                       │
                Message Queue
```

也就是说：

> **不能只让 Kubernetes 高可用，而忽略 Kubernetes 外部依赖。**

------

### 18.13.9 一个真正高可用 API 至少应该考虑什么

可以用下面这张清单检查：

```
应用
□ 是否无状态？
□ Session 是否外置？
□ 是否可以同时运行多个版本？

Pod
□ replicas 是否 >= 2？
□ 是否配置 Readiness Probe？
□ 是否配置 Liveness Probe？
□ 是否配置 Startup Probe？
□ 是否设置 requests / limits？

Deployment
□ 是否使用 RollingUpdate？
□ maxUnavailable 是否合理？
□ maxSurge 是否合理？

调度
□ Pod 是否分散到不同 Node？
□ 是否分散到不同 AZ？
□ 是否配置 Anti-Affinity / Topology Spread？

维护
□ 是否配置 PDB？
□ Node drain 时是否仍然保持足够副本？

扩缩容
□ 是否配置 HPA？
□ minReplicas 是否合理？
□ maxReplicas 是否合理？
□ Node 是否有足够容量？

网络
□ Service 是否正确？
□ Readiness 是否能够阻止异常 Pod 接收流量？

基础设施
□ Node 是否有冗余？
□ 是否跨 AZ？
□ 整个 AZ 故障是否可以容忍？

依赖
□ Database 是否高可用？
□ Redis 是否高可用？
□ MQ 是否高可用？
□ 外部 API 故障是否有降级机制？

发布
□ 是否支持 Rolling Update？
□ 是否支持快速 Rollback？
□ 数据库 Migration 是否兼容新旧版本？
```

最终应该建立这样一个完整认识：

```
                    高可用
                      │
        ┌─────────────┼─────────────┐
        │             │             │
       Pod           Node         Network
        │             │             │
   多副本          多节点         Service
        │             │             │
 Anti-Affinity       多 AZ       Ingress
        │
Topology Spread
        │
       PDB
        │
 Rolling Update
        │
       HPA
```

其中每个机制解决的问题不同：

| 机制            | 主要解决的问题               |
| --------------- | ---------------------------- |
| Deployment      | Pod 副本与故障恢复           |
| 多副本          | 单 Pod 故障                  |
| Anti-Affinity   | 避免 Pod 集中                |
| Topology Spread | 跨 Node / AZ 分布            |
| PDB             | 维护期间避免同时中断过多 Pod |
| Rolling Update  | 发布期间降低中断             |
| Service         | 稳定访问与流量分发           |
| Readiness Probe | 避免流量进入异常 Pod         |
| HPA             | 负载增加时自动增加 Pod       |
| 多 Node         | 容忍 Node 故障               |
| 多 AZ           | 容忍 AZ 故障                 |

## 本章核心思想

> **Kubernetes 高可用不是简单地设置 `replicas: 3`。**

真正的高可用设计应该回答：

```
一个 Pod 挂了怎么办？
一个 Node 挂了怎么办？
多个 Pod 同时挂了怎么办？
Node 维护怎么办？
发布新版本怎么办？
流量突然增加怎么办？
一个 AZ 挂了怎么办？
数据库挂了怎么办？
```

如果你的架构能够针对这些故障分别设计恢复机制，才是真正意义上的生产级 Kubernetes 高可用。
